\chapter{GamerServices and Local Identity}
\label{ch:gamerservices}

Real XNA's \cnans{GamerServices} namespace is Xbox-Live-only, and FNA --- targeting PC XNA
--- does not implement it at all. CNA goes further than FNA here on purpose: rather than
stub the whole namespace out, it built a real, locally-backed implementation held to the
actual Xbox~360 XNA~4.0 reference behavior as its fidelity bar, not to ``does nothing on a
PC.'' This chapter is organized around the resulting three-way split this namespace's own
documentation uses throughout: \textbf{Implemented} (real in-memory behavior matching the
reference), \textbf{Locally persisted} (real, disk-backed, but with no live online service
behind it), and \textbf{documented stub} (no local equivalent exists to build against at
all).

\section{Gamer, SignedInGamer, and a real aliasing hazard}

\cnaclass{Gamer} is the abstract base for \cnaclass{SignedInGamer}; \texttt{GetFromGamertag}
and \texttt{GetPartnerToken} (and their async pairs) are explicitly documented as ``not
supported in this platform's implementation'' --- the genuinely inert corners even this
locally-backed namespace did not attempt to reproduce, since they have no meaning without a
live Xbox Live service to query. One structural detail is worth knowing before writing any
code against this namespace: a \cnaclass{Gamer}'s \cnaclass{LeaderboardWriter}
(\S\ref{sec:leaderboards}) captures its owning \texttt{Gamer*} at construction, and because
neither \cnaclass{Gamer} nor \cnaclass{SignedInGamer} define custom copy or move
constructors, that captured pointer is copied verbatim by any ordinary copy or move of a
\cnaclass{Gamer} --- for instance, pushing a prvalue into a \texttt{std::vector}. Once a
\cnaclass{Gamer}'s \cnaclass{LeaderboardWriter} may actually be used, that \cnaclass{Gamer}'s
address must never move again; heap allocation is the documented, recommended way to avoid
this hazard entirely.

\cnaclass{SignedInGamer} is where the real, locally-persisted behavior lives:
\texttt{AwardAchievement} and \texttt{GetAchievements} are genuinely real, not stubs, backed
by a local persistence store. \texttt{IsFriend} always returns false, and
\texttt{GetFriends()} always returns an empty \cnaclass{FriendCollection} --- not because
\cnaclass{FriendGamer} / \cnaclass{FriendCollection} are unimplemented (they are fully real,
functioning classes), but because nothing anywhere in the codebase actually populates them;
this is the one honestly-acknowledged, still-open gap in this namespace's population story,
not a design limitation like the Xbox-Live-only methods above.

One further CNAEXT detail worth knowing: real XNA's own \texttt{Presence} property is get-only,
but it returns a \cnaclass{GamerPresence} \emph{reference type}, so real game code writes
\texttt{gamer.Presence.PresenceMode = ...} and mutates the same live object the getter
returned. A plain \texttt{const}-only C++ accessor would make that usage pattern impossible to
reproduce, so \cnaclass{SignedInGamer} additionally exposes a non-\texttt{const} overload of
\texttt{getPresenceProperty()} purely to preserve that idiom in C++.

\begin{lstlisting}
// Worked example: awarding an achievement synchronously, then reading
// the achievement list back (empty in this platform's implementation,
// per GetAchievements()'s own documented contract).
SignedInGamer* gamer = /* obtained from SignedInGamer::SignedIn, etc. */;
gamer->AwardAchievement("ACH_FIRST_BOSS_DEFEATED");
AchievementCollection achievements = gamer->GetAchievements();

// Mutating rich presence through the get-only-looking property, matching
// the real XNA reference-type idiom this CNAEXT overload exists to preserve.
gamer->getPresenceProperty().setPresenceModeProperty(GamerPresenceMode::SinglePlayer);
\end{lstlisting}

\section{Leaderboards: real persistence, CNA-original policy}
\label{sec:leaderboards}

\cnaclass{LeaderboardReader} / \texttt{Writer} / \texttt{Entry} are genuinely disk-backed --- a
deliberate expansion beyond FNA, whose own reference \cnaclass{LeaderboardReader}/%
\texttt{Writer} are identically all-\texttt{NotSupportedException} stubs, meaning there was
no real behavior to port here even if CNA had wanted to stay minimal. Because no reference
sort or paging policy existed to match, CNA's own policy is explicitly original rather than
derived: entries sort by rating descending; paging around a specific pivot gamer falls back
to the top of the board if that gamer has no entry at all; and a persisted gamertag with no
currently signed-in matching \cnaclass{Gamer*} is simply skipped, since a
\cnaclass{LeaderboardEntry} needs a live gamer object to attach itself to. Every
\texttt{Begin} / \texttt{End} async pair on this class completes synchronously, matching the
project-wide pattern already seen for \cnaclass{NetworkSession} in
Chapter~\ref{ch:networking}. One genuinely subtle, load-bearing detail: real XNA's own
\cnaclass{LeaderboardWriter} has no explicit submit or commit method at all, so CNA treats
assigning \texttt{Rating} as the closest honest equivalent of ``I'm finished, persist this''
--- but only for an entry actually obtained through a \cnaclass{LeaderboardWriter}, since only
those have a persistence hook installed; setting \texttt{Rating} on an entry obtained from a
\cnaclass{LeaderboardReader} is deliberately a no-op.

\begin{lstlisting}
// Worked example: submitting a new best score. Assigning Rating is the
// whole "commit" step -- there is no separate Submit()/Flush() call to
// remember, matching real XNA's own LeaderboardWriter API shape exactly.
LeaderboardWriter& writer = gamer->getLeaderboardWriterProperty();
LeaderboardIdentity boardId = LeaderboardIdentity::Create(
    LeaderboardKey::BestScoreLifeTime);

LeaderboardEntry* entry = writer.GetLeaderboard(boardId);
entry->setRatingProperty(newHighScore);  // persists immediately
\end{lstlisting}

\section{Achievements}

\cnaclass{Achievement} and \cnaclass{AchievementCollection} are real and locally persisted,
following the same pattern as leaderboards. One method is a deliberate, faithful exception to
that: \texttt{Achievement::GetPicture()} always throws \texttt{NotImplementedException},
matching FNA's own unimplemented stub --- real Xbox~360 achievement artwork streamed from
Xbox Live on request and has no meaningful local substitute, so this is treated the same way
this book's other chapters treat a genuinely unreachable capability: named and left throwing,
not quietly worked around.

\subsection{A worked example: what GetAchievements() actually gives back}

The worked example at the top of this chapter calls \texttt{AwardAchievement} and then
\texttt{GetAchievements}, and it is worth being precise about exactly which fields of the
returned \cnaclass{Achievement} objects are genuinely real data versus which stay at a fixed
default --- a distinction this namespace's own tracking documentation states plainly, and
which is easy to assume away if you only read the method names. \texttt{Key},
\texttt{IsEarned} (always \texttt{true} for anything \texttt{GetAchievements} returns at all,
since the local store only ever records achievements that were actually earned), and
\texttt{EarnedDateTime} are all real, locally persisted data, round-tripped correctly across
process runs. \texttt{Name}, \texttt{Description}, \texttt{GamerScore}, and
\texttt{DisplayBeforeEarned}, by contrast, stay at fixed construction-time defaults (empty
string, \texttt{0}, and \texttt{true} respectively) on every single \cnaclass{Achievement}
\texttt{GetAchievements} returns:

\begin{lstlisting}
gamer->AwardAchievement("ACH_FIRST_BOSS_DEFEATED");
AchievementCollection achievements = gamer->GetAchievements();

const Achievement& earned = achievements[0];
// earned.Key == "ACH_FIRST_BOSS_DEFEATED", IsEarned == true, EarnedDateTime is real --
// but earned.Name, earned.Description, and earned.GamerScore are all still empty/zero.
// A HUD that tries to render "<Name> (+<GamerScore>G)" straight from this object will
// render a blank name and "+0G" for every single achievement, regardless of which one.
\end{lstlisting}

This is not a bug or an oversight --- it is a documented, deliberate consequence of what real
XNA's own \texttt{AwardAchievement(string achievementKey)} signature actually carries: a bare
key string, nothing else. On the real Xbox~360, the display name, description, and point value
a player sees came from Xbox LIVE's own achievement catalog, fetched out-of-band from the
running game entirely; CNA's local, offline persistence store has no equivalent catalog to draw
that metadata from, so it genuinely cannot populate those fields honestly. A game that wants to
show a real achievement name and point value in its own toast/HUD needs to maintain that
catalog itself --- exactly the pattern the project's own \texttt{demo\_achievement\_showcase}
sample uses, keeping a small hardcoded table of achievement metadata entirely separate from
\cnaclass{SignedInGamer}, and looking a returned \texttt{Key} up in its own table rather than
expecting \cnaclass{Achievement} itself to already know its own display name.

\section{Guide: mostly a stub, with two real, CNA-built exceptions}

\cnaclass{Guide} is where this namespace's ``real versus stub'' distinction is sharpest. Most
of its surface --- \texttt{ShowFriends}, \texttt{ShowMarketplace}, \texttt{ShowGamerCard},
\texttt{ShowSignIn}, \texttt{ShowParty}, and the rest of the \texttt{Show*} family --- is a
genuine, documented no-op: there is no system UI to show for any of them, matching FNA's own
minimal PC-side stub. Two specific methods are the deliberate exception, and are real, CNA-built
overlay UI, not stubs at all: \texttt{BeginShowMessageBox} / \texttt{EndShowMessageBox} and
\texttt{BeginShowKeyboardInput} / \texttt{EndShowKeyboardInput}. Unlike almost everything else
in this namespace, these do \emph{not} complete synchronously --- they remain genuinely
pending until the game's own \texttt{Draw()} loop calls a dedicated render hook once per
frame, which draws the message box or keyboard prompt using a caller-supplied
\cnaclass{SpriteBatch} / \cnaclass{SpriteFont}, and polls real keyboard/mouse input to detect a
click, Enter, or Escape. The keyboard-input path captures real UTF-16 text safely across
surrogate pairs, and its password-mode masking only affects the \emph{displayed} text --- the
value actually returned is always the real typed text, never the masked version.
\texttt{Guide.IsVisible} is correspondingly real (not the fixed ``always false'' constant FNA
itself uses off Xbox) --- true exactly when one of these two real overlays is currently
pending.

\begin{lstlisting}
// Worked example: a real, rendered "Quit to menu?" confirmation, driven
// entirely by this platform's own CNA-built overlay, not a system dialog.
System::IAsyncResult* pending = Guide::BeginShowMessageBox(
    "Quit?", "Return to the main menu?",
    {"Yes", "No"}, /* focusButton */ 1, MessageBoxIcon::Warning,
    nullptr, std::any{});

// In Game::Draw(), called once per frame, after drawing the game's own scene:
Guide::RenderPendingMessageBoxEXT(*graphicsDevice, spriteBatch, uiFont, whitePixel);

// Later, once the player has actually clicked a button (poll or check a flag):
if (!Guide::getHasPendingMessageBoxEXTProperty())
{
    std::optional<int> chosen = Guide::EndShowMessageBox(pending);
    delete pending;
    if (chosen == 0) { /* "Yes" was clicked -- return to the main menu */ }
}
\end{lstlisting}

\subsection{A worked example: password-masked keyboard input, and a self-correcting audit}

The keyboard-input half of \cnaclass{Guide} is worth its own worked example, alongside a real
finding about how it reached its current, real state --- an instance of this project's own
recurring ``don't trust a checked-off task list'' discipline (Chapter~\ref{ch:sharp-runtime-namespaces}
covers the identical pattern for \texttt{sharp-runtime}), this time applied to one of its own
prior phases rather than another repository entirely. A later, independent post-completion audit
of this exact feature found that an earlier phase's own ``complete'' write-up had understated
what was actually still missing: \texttt{BeginShowKeyboardInput}'s \texttt{title}/%
\texttt{description} parameters were, at the time, literally unused in the implementation (commented
out in the parameter list); \texttt{Guide.IsVisible} was hardcoded to always return \texttt{false}
regardless of whether an overlay was genuinely pending; the password-masking flag was stored but
never actually consulted anywhere, so a password-mode keyboard input rendered its typed text in
the clear; and there was no cancel path at all, only Enter. None of those four gaps had been
disclosed in the phase's own original sign-off. All four are real now, fixed the same day they
were found:

\begin{lstlisting}
// Worked example: password-masked keyboard input, rendered via its own
// dedicated overlay hook, with a real cancel path this feature did not
// originally have.
System::IAsyncResult* pending = Guide::BeginShowKeyboardInput(
    PlayerIndex::One, "Enter Passphrase", "Used to protect your save file",
    /* defaultText */ "", nullptr, std::any{}, /* usePasswordMode */ true);

// In Game::Draw(), called once per frame: renders the title/description
// and the typed-so-far text, masked as '*' per character on screen --
// the masking is display-only, never applied to the value EndShowKeyboardInput
// actually returns.
Guide::RenderPendingKeyboardInputEXT(*graphicsDevice, spriteBatch, uiFont, whitePixel);

// Later, once the player has pressed Enter or Escape:
if (!Guide::getIsVisibleProperty())
{
    if (Guide::WasKeyboardInputCanceledEXT(pending))
    {
        // Escape was pressed -- distinct from "confirmed with an empty
        // string," which this port's non-nullable std::string return type
        // could not otherwise represent (real XNA returns null on cancel).
    }
    else
    {
        std::string passphrase = Guide::EndShowKeyboardInput(pending);
    }
    delete pending;
}
\end{lstlisting}

\texttt{WasKeyboardInputCanceledEXT} above is the concrete answer to a real representational gap
this fix had to solve: real XNA's own documented contract returns a null string on cancel, which
a C\texttt{++} \texttt{std::string} return value cannot express directly, since an empty string
is exactly what a player who pressed Enter with nothing typed would also produce. Checking this
method first, before trusting whatever \texttt{EndShowKeyboardInput} returns, is the only way to
tell those two real, distinct outcomes apart.

\section{Dispatcher and component}

\cnaclass{GamerServicesComponent} must be added to \texttt{Game.Components}
(this book's game-loop chapter) before any \cnaclass{Gamer} / \cnaclass{Guide} API is
used, matching real XNA~4.0's own PC requirement exactly. \cnaclass{GamerServicesDispatcher}
is the actual entry point creating and freeing the local, stub-style
\cnaclass{SignedInGamer} set each time it initializes, and pumping the async machinery every
other class in this namespace relies on for its synchronously-completing
\texttt{Begin} / \texttt{End} pairs.

\subsection{A worked example: a real cross-namespace hang, and how it was actually fixed}
\label{sec:gamerservices-hang}

\cnaclass{GamerServicesDispatcher}\texttt{::Update()} is a permanently empty no-op --- verified
directly against the real \texttt{.cpp}, an empty function body with nothing inside it at all.
This is not a CNA shortcut: FNA's own reference source has the identical empty body, confirmed
against the real upstream project, so this is a faithfully-reproduced real XNA/FNA
characteristic, not a porting gap. On its own, an empty \texttt{Update()} is harmless, since
nothing in this namespace's own classes actually depends on it doing anything. The real trouble
starts one level up, in \texttt{UpdateAsync()}:

\begin{lstlisting}
bool GamerServicesDispatcher::UpdateAsync()
{
    if (isInitialized_)
    {
        Update();   // permanently empty
    }
    return isInitialized_;   // never goes back to false, once true
}
\end{lstlisting}

\texttt{isInitialized\_} is set \texttt{true} once, permanently, by \texttt{Initialize()} ---
which every real XNA sample's own \cnaclass{GamerServicesComponent} constructor calls
immediately. So in any game that actually adds this component (which the requirement above says
every game using this namespace must), \texttt{UpdateAsync()} unconditionally returns
\texttt{true} forever, starting from the very first frame. FNA's own
\cnaclass{NetworkSession} relies on \texttt{UpdateAsync()} eventually returning \texttt{false}
to know a pending \texttt{NetworkSessionAction} is safe to complete --- a real, independently
confirmed bug in \emph{FNA itself}, not something this port introduced: calling
\cnaclass{NetworkSession}\texttt{::Create()} / \texttt{Find()} / \texttt{Join()} after
\cnaclass{GamerServicesDispatcher}\texttt{::Initialize()} has already run spins forever in a
tight busy-loop, confirmed to reproduce identically against real FNA reference source. This was
not found by unit-testing either namespace in isolation --- it surfaced while porting a real
sample (\texttt{ClientServerSample}, whose own constructor adds a
\cnaclass{GamerServicesComponent} alongside networking, exactly the combination that triggers
it), and is tracked as \texttt{DEFERRED.md} item~\#19 in the sibling \texttt{cna-samples}
repository. An independent second instance of the identical failure shape was found in
\cnaclass{SignedInGamer}\texttt{::BeginGetAchievements}, whose own polling loop has the same
``wait for \texttt{UpdateAsync()} to return \texttt{false}'' dependency.

The fix does not touch \cnaclass{GamerServicesDispatcher} at all --- \texttt{Update()} stays a
faithful no-op, matching real XNA. Instead, \texttt{NetworkSessionAction}'s own constructor was
changed to mark every action complete \emph{immediately}, at construction, rather than
\texttt{false} the way FNA's own reference does:

\begin{lstlisting}
// Real fix, from NetworkSessionAction's own constructor:
, isCompleted_(true)   // was: false, relying on GamerServicesDispatcher::Update()
                       //      to eventually complete it (never happens)
\end{lstlisting}

This is a correctness fix, not merely a workaround, for a reason specific to this port: CNA's
\texttt{Create} / \texttt{Find} / \texttt{Join} / \texttt{JoinInvited} already perform all of
their real work synchronously inside the matching \texttt{End*} method --- constructing the
\cnaclass{NetworkSession} outright, or calling directly into \texttt{ENetBackend} /
\texttt{ENetDiscoveryService} --- with no multi-frame deferred I/O anywhere in the call chain.
There is no real pending operation for a polling loop to ever be legitimately waiting on, so
marking the action complete immediately does not skip real work; it stops the code from waiting
on a completion signal that FNA's own architecture was already relying on a permanently-broken
mechanism to send.

\subsubsection{The regression coverage this bug earned}

Because both \texttt{isInitialized\_} and the dispatcher's stub-gamer population are
process-lifetime statics with no reset hook, the real regression tests for this bug family
cannot run as ordinary \texttt{TEST()} bodies sharing a test binary with anything else --- doing
so would let one test's call to \texttt{Initialize()} silently change
\texttt{UpdateAsync()}'s behavior for every other test in the same process. Each one instead
spawns \texttt{tools/net/gamerservices\_dispatcher\_harness.cpp} as a genuinely separate OS
process, watched by a 10-second watchdog that \texttt{SIGKILL}s and fails the test if the harness
does not exit on its own --- exactly what happens if either hang above regresses. The same
harness and isolation technique cover three real, independently-discovered bugs in
\texttt{Initialize()} found along the way: a permanent 4-\cnaclass{SignedInGamer} memory leak on
any \emph{second} \texttt{Initialize()} call (\cnaclass{GamerCollection}\texttt{<T>} holds
non-owning raw pointers, and the property setter that replaces the collection only freed the
wrapper, not its contents --- fixed by an explicit free-then-recreate loop, verified via a real
\texttt{GetFreedGamerCountForTesting()} counter); and a full end-to-end check of
\texttt{Initialize()}'s own stub-gamer population (exact names, \cnaclass{PlayerIndex}
assignment, and that \cnaclass{SignedInGamer}\texttt{::OnSignIn} fires exactly once per gamer),
run in the same isolated process as the \texttt{GetAchievements()} fix so the fix is exercised
against a real, fully-initialized dispatcher state rather than a bare mock.
