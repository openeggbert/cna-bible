\chapter{Project Practice and Task Tracking}
\label{ch:project-practice}

Chapter~\ref{ch:design-philosophy} covered the code-level house style CNA
enforces on every file. This chapter covers the surrounding \emph{project} practice --- how
work is planned, tracked, and handed off between sessions --- because reading CNA's own
repository well enough to contribute to it, or even to just trust a specific claim in it,
means knowing this layer exists and how to read it.

\section{Three tiers of tracking document}

CNA's root directory carries three distinct kinds of tracking file, each with a different job,
and confusing one for another is a real way to misread the project's own state.

\textbf{\texttt{NEXT.md}} is a \emph{session handoff} document --- written for whichever
agent or engineer picks up work next, not a historical record. It is explicitly scoped to
whichever development branch is currently active, and is candid about its own staleness in a
way worth quoting directly, since it is a good model of the honesty this book has tried to
carry throughout: one recent revision opens by telling its own reader that everything below a
certain divider is ``stale, D3D9-branch-scoped content\ldots that ended up merged into this
file's history\ldots not about this branch and should not be read as current status here.''
Rather than deleting the stale material, it is left in place as a historical record, with an
explicit warning attached. \texttt{NEXT.md} also carries genuinely operational notes with no
equivalent anywhere else in the project --- for instance, running graphics/window tests
against a dedicated Xvfb display rather than a real one, capping build parallelism well below
the machine's full core count and pausing new heavy work above a specific CPU temperature
threshold when the development machine is shared concurrently with other agents, and a
reminder that \texttt{ctest} changes each test's working directory, which can silently break a
test relying on a path relative to the repository root.

\textbf{\texttt{AUDIT.md}} is a \emph{systematic, per-class comparison} between FNA (as
reference) and CNA (as implementation), using a three-value legend --- done, in progress, not
yet audited --- across every class and enum in every XNA namespace. Unlike \texttt{NEXT.md},
this is meant to be read as a durable, cumulative record of what has actually been checked,
not a snapshot of current work.

\textbf{\texttt{CHECKLIST.md}} is the per-file porting checklist already introduced in
Chapter~\ref{ch:design-philosophy} --- SPDX headers, the \texttt{NOXNA} include requirement,
line-by-line verification against FNA, mandatory \texttt{GetTypeName()} overrides, and full
test coverage including out-ref overloads tested separately from their value-returning
counterparts. It also maintains the project's own table of \emph{accepted} C\texttt{++}
deviations from FNA --- for instance, the inconsistency already named in
Chapter~\ref{ch:math-core-types} between \cnaclass{BoundingBox} throwing
\texttt{System::ArgumentOutOfRangeException} for an out-of-range index versus
\cnaclass{Input::Touch::TouchCollection} throwing \texttt{std::out\_of\_range} for the
identical situation --- flagged explicitly as a known, project-wide inconsistency rather than
silently tolerated or silently ``fixed'' to look more consistent than the codebase's actual
history.

\section{One plan file per subsystem}

Beyond these three root-level files, CNA maintains a separate \texttt{plan\_<subsystem>.md}
file for each major feature area under active or completed development --- at the time of
writing, twenty of them, covering areas as different in scale as \texttt{plan\_ascii.md} (the
ASCII backend, Chapter~\ref{ch:canvas-ascii-backends}) and \texttt{plan\_cnj.md}
(the glTF import pipeline). Each is organized into numbered phases and tasks --- the same
\texttt{Task~123} citation style this book has used throughout both volumes whenever
attributing a specific bug or fix to its source. This is the mechanism that makes a claim
like ``Task~868, fixed 2026-07-09'' (Chapter~\ref{ch:vulkan-backend}) a genuinely checkable
one rather than an unsourced assertion: the task number names an exact entry in an exact
plan file, not a vague reference to ``recent work.''

\section{A worked task entry, quoted almost in full}

The ``Task~123'' citation style is easiest to trust once you have actually seen one such row in
its native habitat rather than only in this book's own paraphrase of it. \texttt{plan\_ascii.md}
(the ASCII/glyph-grid backend's own plan file) records its fortieth task, \texttt{ASCII-40}, like
this, condensed only for length:

\begin{quote}
\small
\textbf{ASCII-40} --- \texttt{Present()} override: draw the quantized grid as textured glyph
quads into the real visible window --- \textbf{status: done} --- \emph{``\ldots{}Real bug
found and fixed: \texttt{presentSpriteBatch\_} never goes through
\texttt{GraphicsDevice::BlendState} (only the real XNA-level \texttt{SpriteBatch} does), so the
SDL renderer's blend mode was left at whatever it happened to default to --- not guaranteed
alpha-aware. Confirmed empirically via the new pixel test: background fills were invisible, with
the glyph's transparent `off' pixels silently overwriting the background with the texture's
stored black RGB instead of leaving it alone. Fixed by calling
\texttt{inner\_->ApplyBlendState(\ldots{})} with real XNA \texttt{BlendState.AlphaBlend} factors
\ldots{} unconditionally before every grid draw, independent of whatever the game's own
\texttt{BlendState} is.''}
\end{quote}

Every element this chapter has described so far is visible in that one row at once: a stable
task identifier a later chapter or a later task can cite by name; a terminal status symbol; a
plain description of the intended change; and, critically, a real bug found and fixed
\emph{while doing the intended work} rather than a separate, later-discovered item --- confirmed
not by inspection alone but by ``the new pixel test,'' the same empirical-proof discipline
Chapter~\ref{ch:testing-philosophy} covers as this project's testing philosophy in full. A reader
who has only seen this book's own \texttt{Task~N} citations in passing can now recognize exactly
what stands behind one of them.

\section{Splitting a task that turns out to be too large}

One further, real convention surfaces specifically in the larger \texttt{plan\_<subsystem>.md}
files, and is worth naming since it is not obvious from the three-tier structure alone: when a
single numbered task is discovered mid-flight to actually span multiple independent backends ---
each needing its own separate fix, at its own separate time --- this project splits it into one
new numbered sub-task per backend, rather than either forcing one task to cover all of them or
silently expanding its own scope. \texttt{plan\_graphics.md} records this exact pattern twice,
citing each other explicitly: Task~868 splits into Task~923 (and its own sibling sub-tasks), and
Task~878 splits into Task~899, each split documented as following ``this project's established
precedent for large multi-backend fixes.'' The original, pre-split task row is not deleted once
this happens --- it is kept in place and rewritten into what this project's own plan files call
a \emph{tracking pointer}: a short note stating that the row itself is no longer attempted as one
unit, with a direct reference to whichever new sub-task numbers now carry the real work. This
matters for the same reason \texttt{NEXT.md}'s own stale-but-retained sections do
(this chapter's opening section already named that pattern): a reader who
encounters the original task number in an old commit message or an old chapter citation is not
left looking at a dead end, but is pointed forward to wherever the work actually landed.

\section{Status symbols, read consistently}

Across \texttt{NEXT.md} and the \texttt{plan\_*.md} files, a small set of symbols recur with
consistent meaning: a hollow marker for work not yet started, a half-filled marker for a
partially complete item, and a checkmark for done --- the same three-state shape
\texttt{AUDIT.md} uses with different symbols. When this book's own chapters describe a
feature as ``open'' or ``BLOCKED'' rather than simply absent, that distinction is drawn
directly from this same convention: an open item is ordinary unstarted or in-progress work; a
BLOCKED item, as Chapter~\ref{ch:sdl-renderer} covered for \texttt{SDL\_RENDERER}'s two
BLOCKED rows, specifically means the work itself is understood but genuinely cannot proceed
without a decision only the project owner can make.

\section{Doxygen \texttt{@note Status:} tags: a secondary, human-readable hint}

\texttt{sharp-runtime} (Chapter~\ref{ch:sharp-runtime-overview}) layers one further,
source-level convention on top of all of this: a \texttt{@note Status: Todo|Stub|Partial|%
Implemented|Verified} Doxygen tag directly on individual classes and methods. Its own
documentation is explicit that this tag is a \emph{secondary}, human-readable hint, not a
source of truth --- the authoritative record of whether a given .NET type counts as ``ported''
lives in \texttt{plan.sqlite3}'s own \texttt{task} table (Chapter~\ref{ch:sharp-runtime-overview}
covers this database in full), and the two are not mechanically kept in sync with each other.
A reader trusting only the source comment risks trusting a claim the project's own
authoritative tracking database might already have superseded.

\section{A pattern confirmed independently, across unrelated subsystems}

The discipline the sections above describe in the abstract is worth grounding in how often it
actually mattered while writing this book, because the same specific shape of finding recurred
independently across subsystems tracked in entirely separate documents, with no cross-reference
between them: a claim that looked settled --- a bug list item marked fixed, a status recorded
as \texttt{CLOSED}, an audit round that had already run --- turned out to be stale once checked
against the current, live source rather than trusted at face value. Four genuinely separate
instances surfaced in the course of this book's own research alone: two oracle-methodology
bugs the \texttt{EasyGL} backend's own bug list still described as ``logged \dots{} not fixed''
had in fact both been closed since (Chapter~\ref{ch:easygl-backend}); a
\texttt{sharp-runtime} concurrency fix already marked \texttt{CLOSED} turned out to hide a
second, deeper race that only a later, dedicated ThreadSanitizer run against real concurrent
load actually caught (Chapter~\ref{ch:devices-sensors}'s Android sensor-bridge finding is the
structurally identical pattern, one repository over); and a \texttt{cna-samples} bug report
describing \texttt{GraphicsDevice::Clear(Color)} as still dropping the depth buffer turned out,
on directly reading the current implementation, to already carry an explicit fix and its own
explanatory comment (Chapter~\ref{ch:samples-and-examples}).

A closely related fifth instance is worth naming precisely because it happened inside this book
itself, not just inside the ecosystem it describes: an earlier pass through this project fixed
the same stale D3D9 oracle-scene count (31, then 36, then the true current figure) in four
locations at once --- Chapter~\ref{ch:testing-philosophy}, Chapter~\ref{ch:direct3d-backends},
Appendix~\ref{ch:feature-matrix}, and this book's own opening prose in
Chapter~\ref{ch:what-is-cna} --- and still missed a fifth: the very same chapter's own
verification-scale summary table, a few sections further down the same file, still read
``31-scene oracle'' until a later pass caught it directly while researching an unrelated
chapter. The fix was not different in kind from the four that came before it --- the same
number, the same underlying cause, the same file even --- it was simply a location the earlier
sweep's own search terms happened not to reach. This is worth stating plainly rather than
smoothing over: distrusting a written claim on principle only helps if the re-check is
actually exhaustive, and a prior successful correction is no guarantee the next mention of the
same fact was found too.

None of these were found by doubting this ecosystem's documentation on principle --- each was
found by doing exactly what this chapter's own account of the tracking layer recommends:
treating a written status as a claim to re-verify against the live, current source rather than
a settled fact, the same discipline every \texttt{NEXT.md} and \texttt{AUDIT.md} in this
ecosystem asks of its own readers. That the pattern recurred independently across graphics,
concurrency, and porting-tooling code, each tracked in its own separate document with its own
separate history, is itself evidence this is a real property of how software drifts out from
under its own status labels generally --- not a quirk specific to any one of these subsystems.

\section{Why this layer is worth knowing, not just tolerating}

None of this is unusual in isolation --- plenty of large projects keep a TODO file and a set
of per-feature planning documents. What is worth taking away from this chapter is the
discipline threading through all of it: every one of these documents is written to be
distrusted a little, and to tell you exactly how to check it against something more
authoritative --- \texttt{NEXT.md} telling you which of its own sections are stale,
\texttt{AUDIT.md} tracking currency per class rather than claiming a single global percentage,
\texttt{CHECKLIST.md} recording known inconsistencies instead of hiding them, and
\texttt{sharp-runtime}'s own Doxygen tags explicitly deferring to a database rather than
claiming to be the final word themselves. This is the same discipline
Chapter~\ref{ch:what-is-cna} named as this project's most distinctive trait in its very first
pages, and it is worth recognizing it here again, now grounded in the specific documents that
actually carry it.
