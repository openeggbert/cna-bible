\chapter{Case Study: Speedy Blupi and Planet Blupi}
\label{ch:blupi-case-study}

Every gap and capability this book has described for \texttt{free-direct}
(Chapter~\ref{ch:freedirect-deep-dive}, and the \texttt{DX3} backend chapter earlier in this book) was
shaped by two real, specific legacy Windows games: \emph{Speedy Blupi} (via the sibling
\texttt{free-eggbert} repository) and \emph{Planet Blupi}. This chapter is a worked example of
the migration methodology from Chapter~\ref{ch:migration-guide}, applied to a real, completed
case rather than a hypothetical one --- and a demonstration of what a genuine call-site audit
looks like in practice, not just in principle.

\section{The methodology: grep both games first, then decide}

The single most important fact about how \texttt{free-direct} came to be shaped the way it is
is procedural: every design decision in its own history is backed by a reproducible audit
against both games' actual source, at named, dated commits, not by guessing at what a
DirectDraw-era game in general might need. This produced numbers precise enough to build an
API surface around: \emph{free-eggbert} calls \texttt{Blt} four times and \texttt{BltFast} six
times; \emph{Planet Blupi} calls \texttt{Blt} three times and \texttt{BltFast} five times. One
\texttt{Blt} call site in each game is the single hottest call in the entire program --- the
once-per-frame back-buffer-to-primary present operation --- which is exactly why
Chapter~\ref{ch:freedirect-deep-dive}'s account of DirectDraw support describes it as the most
complete of the library's three subsystems: it was the subsystem under the most direct,
continuous pressure from real gameplay.

\section{A pixel-format mismatch that never became a visible bug}

Both games request a display mode with an explicit bit depth --- \emph{free-eggbert}
requesting either 8-bit or 16-bit depending on a runtime flag, \emph{Planet Blupi} hardcoding
8-bit --- and \texttt{free-direct}'s own \texttt{SetDisplayMode} silently ignores the
requested depth entirely, always creating a 32-bit primary surface regardless. This looks, on
paper, like exactly the kind of silent parameter-drop bug this book has flagged repeatedly
elsewhere (Chapter~\ref{ch:spritebatch}'s ignored transform matrix, for instance). Here,
though, it never manifested as a visible problem, because every offscreen surface each game
actually draws through takes the identical, separately-hardcoded 32-bit path --- the mismatch
between what was requested and what was delivered is real, but it is internally consistent
across the whole rendering pipeline, so nothing ever observes the difference. This is worth
remembering as a category distinct from an actual bug: a real, confirmed deviation from a
literal request, verified harmless by checking every consumer of the value, not merely
assumed harmless.

\section{Color keying: real code, exercised by a narrower case than it supports}

\emph{Planet Blupi} uses source color-keying at exactly two call sites, both routed through a
shared caching helper, and both constructing what is actually a \emph{degenerate} color-key
range --- a single value, not a genuine low-to-high range --- matched against white via a
real \texttt{GetDC}/\texttt{SetPixel}/\texttt{Lock} round trip rather than a hardcoded palette
index. \texttt{free-direct}'s color-keying implementation itself supports the fuller, ranged
case; the real games it was built against simply never exercise that fuller capability, which
is worth knowing if you are evaluating this library for a third game that might.

\section{A live-gameplay dependency on GetDC, not just a compatibility nicety}

\texttt{GetDC}/\texttt{ReleaseDC} might look, from the outside, like a minor GDI-interop
convenience rarely exercised by a real game. The audit found the opposite for
\emph{Planet Blupi} specifically: its own \texttt{IsIconPixel} function --- a live,
per-mouse-click gameplay hit-test, not a one-time setup call --- depends on
\texttt{GetDC}/\texttt{ReleaseDC} working correctly on both 32-bit surfaces (handled as a
direct, zero-copy wrap) and 8-bit surfaces (expanded through a temporary palette-converted
buffer). This single finding is why \texttt{free-direct}'s own \texttt{GetDC} support had to
be functionally real rather than a thin stub --- a case where a call that looks incidental
from the API surface alone turns out to gate real, moment-to-moment gameplay logic once you
actually check what calls it and why.

\section{Interfaces never exercised at all}

The audit's negative findings are as informative as its positive ones. A full-source grep for
\texttt{QueryInterface} across both games combined found exactly one real call site in
total --- and it belongs to a DirectPlay object, not a DirectDraw one, which is a direct,
concrete reason \texttt{free-direct}'s own \texttt{QueryInterface} implementation across all
four DirectDraw classes is a uniform, hard \texttt{DDERR\_UNSUPPORTED} stub: there was no real
call site anywhere to build a working implementation against. Similarly, \emph{Planet Blupi}
has zero DirectPlay usage of any kind, confirmed by grep --- every DirectPlay design decision
in \texttt{free-direct}'s own history (Chapter~\ref{ch:freedirect-deep-dive}) is driven
exclusively by \emph{free-eggbert}'s own usage, since the other game simply never touches
that subsystem at all.

\section{DirectSound: a real struct-layout hazard, found before it could cause silence}

Both games always populate a \texttt{PCMWAVEFORMAT} structure, not the larger
\texttt{WAVEFORMATEX} structure a more modern DirectSound caller might use --- and this
distinction is why \texttt{free-direct}'s own sound-buffer descriptor deliberately types its
format field as a raw \texttt{void*} rather than a concrete struct pointer, and always
interprets it as \texttt{PCMWAVEFORMAT} specifically: the two struct layouts place
\texttt{wBitsPerSample} at different byte offsets, and reading the wrong layout would silently
read two bytes of structure padding as the bits-per-sample field for every single sound in
both games --- a real, if narrowly averted, silent-audio-corruption risk, caught by checking
what the real games actually populate before choosing an interpretation. A second, confirmed,
call-site-driven fact rounds this out: \texttt{SetPan()} only audibly matters for mono
buffers, and both games only ever pan mono sound effects, so this narrower scope was never a
real limitation for either target.

\section{Dead code, confirmed rather than assumed}

Not every finding required a design decision --- some just needed confirming that a code path
genuinely never runs. \emph{free-eggbert} contains a complete alternate, BASS-library-backed
sound implementation, gated behind a compile-time flag hardcoded to false with no build
override anywhere --- confirmed dead by reading the actual gate, not merely by its
appearance. Both games separately contain a wave-loading source file that is never
\texttt{\#include}d anywhere except by itself, and both call a sound-playback method whose
looping-flags parameter always receives a literal zero at every real call site --- independently
confirming, from the calling side, that DirectSound looping support genuinely cannot be
reached by either game today, the same conclusion Chapter~\ref{ch:freedirect-deep-dive}
already drew from the library's own implementation side.

\section{What this case study demonstrates about porting more generally}

The lesson this chapter offers Chapter~\ref{ch:migration-guide}'s more general advice is
specific: a compatibility layer built to genuinely support two real games, verified by
grepping those games' own source rather than reasoning abstractly about what a game of that
era might do, ends up both narrower and more solid than a layer built to a hypothetical full
specification would be. It correctly implements exactly the DirectDraw/DirectSound/DirectPlay
surface \emph{Speedy Blupi} and \emph{Planet Blupi} actually touch, including at least two
places (\texttt{GetDC}'s live gameplay dependency, the \texttt{PCMWAVEFORMAT} layout hazard)
where a more generic, spec-first implementation might have gotten a plausible-looking detail
wrong precisely because it was never checked against a real, demanding caller.
