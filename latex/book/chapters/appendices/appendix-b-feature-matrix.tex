\chapter{Renderer Registry, Capabilities, and Evidence}
\label{ch:feature-matrix}

CNA exposes \textbf{46 public renderer identities / 42 implementation families} at the pinned
revision.  The four-count difference is exact: five EasyGL profiles share one implementation
family, while every other identity has its own family.  This appendix derives the registry from
\path{docs/renderer-registry.md} and the source-owned factory paths, then reports a narrow set of
capabilities from reachable implementation behavior.  It does not copy the older central feature
matrix, whose names and cells predate the current registry.

\section{Four implementation questions across all 42 families}

The next matrix deliberately asks only four questions that can be answered uniformly from the
pinned source.  ``Native'' means the family owns both ordinary effect-aware \texttt{Draw*Ex}
routes; it does not promise complete stock-effect fidelity.  ``Fallback--reject'' means the
shared parameter-dropping fallback reaches an explicit 3D refusal.  ``Hybrid'' means a
renderer-owned route still has a bounded coloured fallback.  ``Conditional'' names a real
profile/device/extension dependency.  ``Claims yes'' exposes a public capability answer that
contradicts the reachable factory or operation.

The table is a routing audit, not runtime certification.  It was mechanically checked to contain
42 families; EasyGL contributes the remaining four public identities.  Thirty-one families own
both ordinary effect-aware methods and eleven inherit both shared defaults.  Of the inheritors,
nine refuse 3D, \texttt{STUB} intentionally does nothing, and \texttt{DIRECTX10} alone produces
a real coloured draw after silently losing the effect parameters.  Four owner routes---OpenGL
ES~1, OpenGL~4, SDL GPU, and WebGPU---retain narrower coloured tails.

\section{Capability answers require operation-level proof}

\cnaclass{GraphicsDevice::SupportsCapability} is a useful preflight query, but its shared default
is permissive.  At the pin, \texttt{HEADLESS}, \texttt{SOFTWARE}, and \texttt{WEBGPU} report MRT
while rejecting every multi-target set.  \texttt{SDL\_GPU}, \texttt{WEBGPU}, and
\texttt{SOFTWARE} report occlusion-query support while inheriting a null factory; \texttt{HEADLESS}
returns a bookkeeping object with a constant pseudo-count rather than a real GPU query.  These are
tracked defects, not support.

Conversely, a false or absent high-level bit can hide a narrower usable path.  Profile-gated GL
queries, driver-gated wrapper capabilities, fixed-function rendering, CPU rasterization, and
trace validation all need their own labels.  The safe decision sequence is:

\begin{enumerate}
  \item filter by platform/dependency admissibility and the exact public selector;
  \item inspect the factory/resource operation and the draw route for the required feature;
  \item require renderer-owned tests or a retained host artifact at the needed evidence tier;
  \item use a second structurally independent family as a localization control;
  \item retain skips, refusals, and capability/reporting contradictions in the result.
\end{enumerate}

Appendix~\ref{ch:verification-tiers} defines the evidence vocabulary.  The renderer chapters own
the narrower state, shader, texture, readback, and platform qualifications that cannot fit in
this compact matrix.
