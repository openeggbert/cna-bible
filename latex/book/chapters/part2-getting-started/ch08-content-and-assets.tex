\chapter{Content and Assets}
\label{ch:content-and-assets}

Real XNA's content model and CNA's are different, and --- unlike most of the gaps in this
book --- the story here has genuinely changed over the project's own history rather than
settling once. This chapter covers where it stands now: two real, actively-maintained content
formats, tried in a specific order, each with its own reasoning.

\section{Real XNA's own model, briefly}

Real XNA never ships raw asset files inside a game. An offline content-pipeline build step
compiles every texture, model, font, and effect into a proprietary binary format ---
\texttt{.xnb} --- which \cnaclass{ContentManager::Load<T>()} loads at runtime. FNA
reimplements a real \texttt{.xnb} reader, precisely so unmodified, historical XNA content
keeps working unchanged.

\section{CNA's own format: .cnj}
\label{sec:cnj}

CNA's primary, permanent strategic answer is not a \texttt{.xnb} reader at all, but its own
format: \texttt{.cnj} --- ``CNA content JSON,'' a lightweight, human-readable JSON sidecar
format sitting alongside a directly-loadable native asset file (a \texttt{.png}, a
\texttt{.wav}) or standing in for an asset with no native format of its own. This is a
permanent, deliberate strategic choice, not a stopgap awaiting \texttt{.xnb} support --- the
project's own naming history is worth knowing as a small, honest correction in its own right:
the format was originally called \texttt{.cnb} (``CNA content Binary/JSON''), a name that
misleadingly suggested a binary format mirroring XNA's own \texttt{.xnb}, despite always
having been plain JSON. It was renamed project-wide --- the file extension, the internal
envelope type, the version field, the registration template, and the format's own planning
document's task numbering all changed together --- specifically to stop implying something
the format never was.

A \texttt{.cnj} file is a small JSON envelope (a version field, a type name, and a reference
to a source file where applicable) validated against the requested C\texttt{++} type with a
strict version-equality policy, parsed by a real, from-scratch recursive-descent JSON parser.
\cnaclass{SpriteFont}, custom \cnaclass{Effect} parameters for the five stock effects
(Chapter~\ref{ch:stock-effects}), and \cnaclass{Model} (the fallback path from
\S\ref{sec:xnb-and-cnj-model} below) are all reachable through \texttt{.cnj} today, migrated
from older, bespoke loose-file extensions (\texttt{.font.json}, \texttt{.shader.json},
\texttt{.model.json}) that predated the unified format. A registration template lets a game
register several differently-named \texttt{.cnj} ``type'' strings that all resolve to the
same C\texttt{++} type, for data with no dedicated built-in reader at all --- the same
general-purpose extensibility mechanism Chapter~\ref{ch:shader-fx-gap} already noted CNA
deliberately chose over a scripted custom-reader mechanism, for the same reason: a plain,
type-safe C\texttt{++} registration API, not an embedded scripting language.

One asset type is deliberately \emph{not} part of the unified \texttt{.cnj} format, by an
explicit, reasoned decision: the Avatar system's \cnaclass{SkinnedModelEXT}
(Chapter~\ref{ch:avatar}) keeps its own separate \texttt{.skinnedmodel.json} extension, because
real cross-language tooling already depends on that specific extension name, because it already
carried the most mature test coverage of any loose-file reader in the project at the time
\texttt{.cnj} unification happened, and because it is explicitly a distinct,
non-\cnaclass{Model}-shaped system in the first place (Chapter~\ref{ch:avatar} covers exactly
why).

\subsection{Two real \texttt{.cnj} files, quoted directly}

Reading \texttt{cnj.md} (the format's own design reference) turns up two genuinely different
uses of the same envelope, worth seeing side by side rather than only described. First, a
fully self-contained document --- a real \cnaclass{SpriteFont} needs no native payload file at
all, since every field it needs (the glyph atlas reference, layout metrics, per-glyph bounds)
fits directly in JSON:

\begin{lstlisting}
{
  "cnjVersion": 1,
  "type": "SpriteFont",
  "texture": "Fonts/Consolas_atlas.png",
  "lineSpacing": 24,
  "spacing": 0.0,
  "defaultCharacter": "?",
  "glyphs": [
    { "char": 65, "source": [0, 0, 16, 24], "crop": [0, 0, 16, 24], "kerning": [1, 14, 1] }
  ]
}
\end{lstlisting}

Second, the \texttt{sourceFile} metadata-sidecar shape this chapter's resolution-order section
already named in the abstract, quoted here concretely:

\begin{lstlisting}
{
  "cnjVersion": 1,
  "type": "Texture2D",
  "sourceFile": "ahoj.png",
  "colorKey": [255, 0, 255],
  "premultipliedAlpha": true
}
\end{lstlisting}

The distinction between these two is exactly the \texttt{sourceFile} field's presence or
absence, and it changes what the rest of the document \emph{means}: without \texttt{sourceFile}
(the \cnaclass{SpriteFont} case), every other field is the actual data being described. With
\texttt{sourceFile} present (the \cnaclass{Texture2D} case), CNA loads \texttt{ahoj.png}
through the ordinary native-decode path first, and every other field in the \texttt{.cnj}
becomes import metadata layered on top of that already-decoded texture --- here, a magenta
\texttt{colorKey} (pixels matching \texttt{(255, 0, 255)} become transparent, the classic
sprite-sheet convention for games authored before per-pixel alpha channels were universal) and
an explicit premultiplied-alpha hint. This is genuinely new capability the format's own design
notes are explicit about, not a rename of something \cnaclass{Texture2D} could already do:
before \texttt{sourceFile} existed, a native-payload asset type could only ever load a
self-describing file exactly as authored, with no way to attach CNA-specific import intent
(color-key transparency, a premultiplied-alpha override) without baking it into the pixel data
itself or inventing an entirely separate file format just to carry one flag.

\section{The gap, reopened: a real, now largely complete .xnb binary reader}
\label{sec:xnb-and-cnj-model}

Here is the correction this chapter most needs to make plainly: CNA's owner later decided
\texttt{.xnb} should \emph{also} become a real runtime format, alongside --- not instead of
--- \texttt{.cnj}. What began as a growing effort has, since this chapter's own last pass,
reached its own planned completion point: container parsing, binary primitives, real LZX
decompression (verified against real compressed fixtures, including a differential-testing
pass against FNA's own reference decompressor run under Mono, the same technique
Chapter~\ref{ch:what-is-cna} describes for \texttt{tools/fna-reference/}, that found and fixed
a real heap-buffer-overflow in the process), and \cnaclass{SpriteFont}, all five stock
effects, \cnaclass{SoundEffect}, \cnaclass{Song}, and the general
\cnaclass{Texture2D}/\cnaclass{TextureCube} external-reference paths are all real, working \texttt{.xnb} readers
today. \cnaclass{Model}'s own \texttt{.xnb} reader --- described in
Chapter~\ref{ch:models-meshes} as already real and wire-compatible --- was this effort's own
most complete result throughout its development, and remains so.

Writing or producing \texttt{.xnb} files remains permanently out of scope on both sides of
this story: CNA only ever needs to \emph{consume} \texttt{.xnb} files produced by real
XNA/MonoGame/FNA tooling, never to produce its own.

\subsection{A real hardening pass: three more heap-buffer-overflows found by fuzzing, not review}

The reader set's own closing phase --- deliberately sequenced last, specifically so hardening
work would land against an already-complete, already-correct reader set rather than a moving
target --- found three further genuine memory-safety bugs that ordinary code review had not
caught, all through the same technique: deterministic fuzz-mutating a real, valid fixture's
entire byte stream and running it through the actual \texttt{ContentManager::Load<T>()} path,
not a synthetic unit test written to exercise one function in isolation. \cnaclass{Texture2D}/%
\cnaclass{Texture3D} / \cnaclass{TextureCube}'s own readers never cross-checked their file's
declared byte count against what the texture's own width, height, and depth actually implied
--- fixed by throwing a real \texttt{ContentLoadException} the moment an uncompressed level's
byte count disagrees with $\mathit{width} \times \mathit{height} \times 4$, rather than
trusting the file and reading past the end of a too-small buffer. A closely related bug in
\texttt{Texture3DReader}'s own compressed-volume path had never actually been exercised by any
prior test at all: it decompressed an entire multi-slice 3D texture as though it were one
single 2D image, a bug that had been sitting dormant, unreachable by any code path a
non-adversarial fixture would take. Separately, \texttt{DxtUtil::DecompressDxt1} / \texttt{3}/%
\texttt{5} each accepted a \texttt{dataSize} parameter specifically meant to bound how much
compressed data they were allowed to read, but never actually checked against it --- a
parameter that existed in the signature purely as documentation, not enforcement, until this
pass. All three were confirmed fixed under a real AddressSanitizer/UndefinedBehaviorSanitizer
build, the same standard this book's own earlier chapters hold every other sanitizer finding
to.

\subsection{Custom \texttt{.xnb} readers use a process-wide registry; loose and \texttt{.cnj} readers do not}

An earlier shorthand in this chapter needs a correction: \texttt{RegisterTypeReader<T>} is
\emph{not} the extension point for a custom \texttt{.xnb}. \texttt{Load<T>()} checks for an
\texttt{.xnb} before consulting its per-manager loose-reader table, and
\texttt{LoadXnbAsset()} gives the binary file's own reader table to the static
\cnaclass{ContentTypeReaderManager}. A custom binary reader instead registers a canonical
reader-name factory in that global registry. CNA has no reflection fallback, whereas FNA first
tries its factory map and can otherwise reflect the named managed type, so this registration is
public and \texttt{NOXNA}-tagged in CNA rather than FNA's internal AOT fallback.

The registry starts empty on purpose. \texttt{ContentManager}'s constructor does \emph{not}
populate it, and neither does \cnaclass{Game}; otherwise a test that clears the global state could
not exercise the genuine ``unregistered reader'' failure path. A real application must register
the reader families it intends to use before any \texttt{.xnb} load. CNA supplies one explicit,
idempotent umbrella call for every implemented built-in family (but deliberately not arbitrary
closed generic collection readers):

\begin{lstlisting}
#include "CNA/Internal/Xnb/XnbBuiltInReaders.hpp"

CNA::Internal::Xnb::RegisterAllBuiltInXnbReaders(); // once, before any .xnb load

ContentTypeReaderManager::AddTypeCreator(
    "MyGame.Content.GameLevelDataReader",
    [] { return std::make_unique<GameLevelDataReader>(); });

ContentManager content(nullptr, "Content");
GameLevelData level = content.Load<GameLevelData>("level1");
\end{lstlisting}

The custom-reader integration test really writes that minimal \texttt{level1.xnb}, registers the
factory, and loads it through \texttt{ContentManager}; omitting the registration yields the
named \texttt{ContentLoadException}. This is the route a port of
\texttt{prime31/Nez}'s independent \texttt{BitmapFontReader} must take. CNA deliberately has no
equivalent to .NET's reflection-generated \texttt{ReflectiveReader<T>}: content built around one
must be rebuilt with an explicit writer/reader pair, then supplied through a matching C\texttt{++}
factory.

This global registry has deliberately different replacement and lifetime rules from the
per-manager tables. \texttt{AddTypeCreator()} keeps the \emph{first} factory for an exact name
and silently ignores later registrations; \texttt{CreateReader()} calls the retained factory for
one fresh reader per \texttt{.xnb} file, owned by that file's \texttt{ContentReader}.
\texttt{ClearTypeCreators()} removes every family for every manager and is consequently a test
isolation tool, not a runtime reload API. Registration and clearing have no synchronization in
the current C\texttt{++} map, so finish them before concurrent asset loads. There is also no
empty-name or empty-factory validation: the manifest test deliberately stores a null factory and
then observes \texttt{IsRegistered()} report true; attempting to create through that entry would
invoke an empty \texttt{std::function} rather than yield a normal missing-reader diagnostic.

\texttt{RegisterTypeReader<T>}, by contrast, changes only one \texttt{ContentManager}'s
loose-file/\texttt{.cnj} reader map. It owns the supplied \texttt{unique\_ptr} as a
\texttt{shared\_ptr} and silently overwrites an existing reader for the same C\texttt{++} type;
it accepts a null pointer, which later reaches the map's explicit ``reader is null'' load error.
It neither changes the global \texttt{.xnb} registry nor evicts an asset already cached under
that type/name, so call \texttt{Unload()} before expecting a replacement reader to affect a
previously loaded generic asset. No located test directly registers and replaces a loose reader.

\texttt{RegisterCnjLoader<T>(typeName, factory)} is safer but has its own narrower contract. On
its first successful call for a type with no reader, it creates the one generic \texttt{.cnj}
reader; later distinct names select separate factories inside that same reader. Empty names,
empty factories, a pre-existing non-generic reader, and an exact duplicate name all fail fast,
and the focused tests cover those cases plus recursive texture loading. Do not subsequently
replace that generated reader with \texttt{RegisterTypeReader<T>}: current CNA leaves the named
factory table behind, so already registered and even later accepted names become unreachable
through the replacement reader. This is an untested implementation boundary, not a supported
way to layer two loose-reader mechanisms. Copying a \texttt{ContentManager} shares its current
loose-reader pointers but copies its named \texttt{.cnj} factories, as the later
\texttt{Game::Content} section explains.

\subsection{\cnaclass{ContentReader} is a one-shot XNB object-graph session, not a reusable file reader}
\label{sec:content-reader-contract}

Every real XNB load eventually creates a \cnaclass{ContentReader} over the body beginning
immediately after the ten-byte container header. Its first operation, \texttt{ReadAsset<T>()},
parses the type-reader table at the \emph{current} stream position, reads the shared-resource
count, deserializes one root object, then reads every shared object and finally invokes its
queued fixups. The constructor comment currently says that both the header \emph{and} table have
already been consumed, which contradicts the implementation and the manager's live call site:
only the header has been consumed. Calling \texttt{ReadAsset<T>()} a second time does not rewind
or reuse the prior table; it treats whatever bytes follow the first asset as another table.
Use one new reader for one body and one top-level asset.

Although FNA makes this a sealed class with an internal constructor, CNA's C\texttt{++} class,
constructor, and the initialization/read methods are public and it is not final. That wider
surface is not a promise that the object is independently long-lived. The reader stores raw,
non-owning pointers to both stream and manager. Its inherited \cnaclass{BinaryReader} uses the
default \texttt{leaveOpen = false}: destroying or closing the reader closes the supplied stream
but never deletes it. The manager-created stack reader is therefore safe only because its stack
\cnaclass{MemoryStream} outlives it. A standalone caller must keep both raw referents alive,
must not retain a \texttt{ContentReader\&} beyond its callback, and must account for the stream
being closed on reader destruction. Neither the focused tests nor the public API prevent a
dangling manager/stream or concurrent use of the mutable reader state.

Initialization creates a fresh reader instance for every serialized table entry through the
process-global factory registry, checks CNA's extra strict serialized-version rule, and only then
calls \texttt{Initialize()} on every instance. FNA reads but does not enforce reader versions.
The two-pass construction is useful: a reader may assume its peers have all been created when its
initializer runs. There is a C\texttt{++}-specific lifetime caveat, however. CNA passes that
initializer a local \cnaclass{ContentTypeReaderManager} which is destroyed as soon as
initialization completes; a custom reader must use the reference synchronously and must not store
it. FNA retains its manager as a field of the ContentReader for the reader session. The fresh CNA
reader instances themselves are also destroyed when the session ends, so an asset must not retain
a pointer/reference to its decoder.

Object dispatch is 1-based: zero is a null/default object, while positive index $n$ selects table
entry $n-1$. For a default-constructible C\texttt{++} result, zero returns \texttt{T\{\}}; with
an existing instance it returns that instance instead. A non-default-constructible \texttt{T}
with no existing value has no C\#-style \texttt{default(T)} representation and throws
\cnaclass{ContentLoadException}. A bad reader/result pairing instead exposes
\texttt{std::bad\_any\_cast}; CNA does not normalize every object-graph failure. Direct
\texttt{ReadObject} and \texttt{ReadRawObject} overloads can bypass the 1-based dispatch, but
CNA lacks FNA's no-argument \texttt{ReadRawObject<T>()} lookup overload. Root success is not a
transaction: a later shared-resource parse or fixup can throw after the reader has already made
arbitrary reader-side changes.

Shared resources deliberately have a second phase. A positive reference index queues a typed
fixup; index zero queues nothing. After the root returns, CNA reads \emph{all} shared values in
file order, then runs each resource's fixups in file/index order. This correctly supports forward
and cyclic graph references, but it also means a callback observes a fully-read shared section,
not an incrementally available one. A positive index above the declared count produces a content
load error. A negative index instead takes the same silent no-fixup branch as zero, because the
code tests only \texttt{index > 0}. A wrong typed shared value reaches
\texttt{std::bad\_any\_cast}; current FNA turns that mismatch into its content-load error. The
focused tests prove one healthy fixup and zero, but not a negative index, bad type, callback
throw, forward/cyclic graph, or partial-side-effect case.

Disposal tracking is narrower than the constructor documentation promises. CNA records a result
only when its \emph{static} C\texttt{++} type is \texttt{std::shared\_ptr<U>} for a
\texttt{U} derived from \cnaclass{IDisposable}, and only when an explicit callback was supplied.
The normal \cnaclass{ContentManager} XNB path supplies no callback; despite the header's statement
about a manager fallback, the live implementation has no such call. Type-erased shared-resource
reads deliberately skip tracking altogether. FNA instead performs a runtime IDisposable test and
falls back to its owning ContentManager. No located CNA test exercises either a recording callback,
the documented fallback, or a disposable shared resource, so do not use the reader as a general
content-disposal coordinator.

\texttt{ReadExternalReference<T>()} has two separate CNA restrictions. An empty serialized
reference returns \texttt{std::nullopt}; a nonempty one needs a live manager, resolves relative to
the containing logical asset name, and then enters the ordinary \texttt{Load<T>()} candidate and
cache path. Relative upward escape is rejected, but an absolute reference still escapes through
the manager's unrestricted absolute-path route described in \S8.4. The declaration looks generic,
but the implementation is explicitly instantiated only for \cnaclass{Texture2D} and
\cnaclass{TextureCube}; another \texttt{T} compiles against the declaration but has no linked
definition. FNA's method is genuinely generic and returns \texttt{default(T)}; CNA's
\texttt{optional} return is the necessary value-type distinction. Existing tests cover only the
Texture2D sibling, empty, relative-escape, and null-manager paths.

Finally, \cnaclass{XnbReadLimits} is not a universal admission policy on the current
\texttt{develop} source. Type-reader and shared-resource counts are checked; collection and
decoded-pixel limits work when a particular built-in reader calls the corresponding helper.

Three declared limits have gaps: \texttt{maxStringBytes} and
\texttt{maxObjectNestingDepth} have no live consumer, while \texttt{maxFileSize} is consulted
only on the LZX decompression path. An uncompressed XNB is first read wholesale by
\cnaclass{ContentManager}, and deeply nested object dispatch or a nested generic type-reader name
has no reader-level depth guard. Treat the defaults as partial defensive checks, not proof that
every untrusted XNB has a file, string, allocation, or stack-depth bound. No located focused test
proves those three advertised limits on this branch.

\subsection{\cnaclass{ContentTypeReader} is a value-erased adapter, not a runtime type system}
\label{sec:content-type-reader-contract}

CNA keeps the familiar template name \texttt{ContentTypeReader<T>} for a game author's typed
base class. Its separate, \texttt{NOXNA} \cnaclass{ContentTypeReaderBase} exists because C\texttt{++}
cannot give both the non-template and template forms the same unqualified name as C\# can. A
concrete reader implements the protected typed \texttt{Read(ContentReader\&, optional<T>)}; the
base translates that call to public \texttt{ReadUntyped(ContentReader\&, any)}. The stored target
type is only a caller-supplied canonical XNA \emph{name} string. CNA has neither reflection nor a
runtime \texttt{Type} identity, and it does not verify that the string, the registered table name,
the template \texttt{T}, and the value actually returned by the reader agree. The eventual
\texttt{any\_cast} is the real check, and a mismatch exposes \texttt{std::bad\_any\_cast}, not a
uniform content-load exception.

For a copy-constructible \texttt{T}, the erased payload is a literal \texttt{T}. For a move-only
\texttt{T}, it is instead \texttt{shared\_ptr<T>}, because \texttt{std::any} itself requires a
copy-constructible held type. The normal indexed \texttt{InnerReadObject<T>()} path contains the
matching compile-time unwrap and therefore loads bare move-only roots correctly. The public direct
\texttt{ReadObject<T>(reader)} and \texttt{ReadRawObject<T>(reader)} overloads do \emph{not}:
they always cast the returned \texttt{any} to bare \texttt{T}. For a move-only value they therefore
reach \texttt{bad\_any\_cast}; their overloads taking an existing value try to put that bare value
in \texttt{any} and cannot be instantiated. This affects both \cnaclass{SoundEffect} and
\cnaclass{TextureCube}, not only the former. Use ordinary indexed dispatch for those types; the
direct-reader overloads are currently reliable only for a copy-constructible target (or a reader
whose declared \texttt{T} is already a copyable handle such as \texttt{shared\_ptr<Texture3D>}).

An existing instance is likewise a transported value, not an observable in-place update of the
caller's object. CNA moves it into \texttt{optional<T>}, lets the reader return a replacement
value, then returns that value to the caller. In particular, no production CNA call site consults
\texttt{getCanDeserializeIntoExistingObjectProperty()}: normal \texttt{ContentManager} loading
starts without one and caches its completed result. Only \texttt{ListReader} and
\texttt{DictionaryReader} advertise true, but a direct caller still receives a new C\texttt{++}
container value. The list result appends decoded items after the supplied values; the dictionary
result clears its supplied entries first. \texttt{ArrayReader} advertises the default false yet
accepts an explicitly supplied vector and resizes it to the file count, a deliberate safety
departure from FNA's unchecked array indexing. No collection test proves the public
\texttt{ContentReader} overloads, a real manager reload, or the distinction between a returned
replacement and mutation of a caller-owned container.

Collection genericity is also deliberately finite. FNA's per-file manager uses reflection and
\texttt{TargetType} to find the element reader from the current table during \texttt{Initialize()}.
CNA instead requires each closed \texttt{ArrayReader}, \texttt{ListReader},
\texttt{DictionaryReader}, or \texttt{NullableReader} registration to carry canonical names for
its element readers. At every collection read it creates those readers afresh from the global
factory map; they are neither initialized from the current file nor checked against a serialized
version. This is sound only for the currently stateless built-ins, as the source comment says.
The umbrella registration deliberately excludes arbitrary closed generics; only SpriteFont's three
known list shapes are pre-registered. A custom collection must register its exact outer
combination and every value-type element reader before loading, rather than expecting a
reflection-like fallback.

For \texttt{shared\_ptr} elements the collection consumes one indexed object dispatch per item,
allowing the file table to select a concrete subtype; non-\texttt{shared\_ptr} elements use the
manually named direct reader. All three counted collections check the configured element limit
before allocation or reserve, and the focused tests cover unsigned overflow, negative counts, and
one above-limit count. They do not cover reference-shaped elements, a stateful custom element
reader, factory exceptions/null returns, or duplicate dictionary keys. The latter diverges from
FNA particularly: FNA uses \texttt{Dictionary.Add} and throws for a duplicate, while CNA uses
\texttt{unordered\_map::emplace} and silently retains the first value.

The built-in marker reader for the general EffectReader is the other intentional branch of this
framework. It consumes no input and always gives a named content-load error for compiled platform
shader bytecode. This is a precise scope boundary, not a generic reader fallback. Tests prove its
registration and direct throw, plus healthy custom registration and selected collection behavior;
none exercises incorrect \texttt{any} boxing, the move-only direct-overload trap, target-name
disagreement, initializer lifetime, or the global registry's null-returning factory.

\section{The resolution order, precisely}

The earlier short three-way description is useful, but it hides two consequential facts: a
candidate that exists is selected \emph{before} CNA knows whether its reader can consume it, and
there is no retry with a lower-priority candidate after that reader fails. On a cache miss, the
generic template and each of the \cnaclass{Texture2D}, \cnaclass{SoundEffect}, and
\cnaclass{TextureCube} specializations use the same selection sequence. Written directly from
\texttt{ContentManager.hpp}, with \texttt{base = BuildAssetPath(assetName)}, it is:

\begin{lstlisting}
if (exists(base + ".xnb"))
    return LoadXnbAsset<T>(base + ".xnb");  // before a local reader is even required

reader = the per-manager LooseFileContentTypeReader<T>;
if (exists(base))
    return reader.Read(base, content);       // literal path wins among loose candidates
if (exists(base + ".cnj"))
    return reader.Read(base + ".cnj", content);
for (const auto& ext : reader.GetExtensions())
    if (exists(base + ext))
        return reader.Read(base + ext, content); // first listed existing extension wins
return reader.Read(base, content);           // reader reports the eventual missing/invalid path
\end{lstlisting}

The first successful generic result then enters its strong type-plus-normalized-name cache;
\cnaclass{Texture2D} records its weak backend entry; and move-only \cnaclass{SoundEffect} and
\cnaclass{TextureCube} perform the sequence on every call. Those cache rules were covered above,
but they matter here because a later call for a cached name does not re-evaluate newly created,
removed, or repaired candidates.

\subsection{A candidate is terminal; it is not a successful probe}

The first line has deliberately stronger meaning than ``try XNB first.'' It appends
\texttt{.xnb} to the complete logical name regardless of whether that name already has a dot or
an extension. Thus \texttt{Load<Texture2D>("art/logo.png")} tests
\texttt{art/logo.png.xnb} first, then (if no such file exists) reads the literal PNG. Conversely,
the usual way to load \texttt{art/logo.xnb} as XNB is
\texttt{Load<Texture2D>("art/logo")}. Passing \texttt{"art/logo.xnb"} tests
\texttt{art/logo.xnb.xnb}; if that second file is absent, it hands the original XNB bytes to the
ordinary loose Texture2D reader instead of invoking the XNB parser. A dot in a logical name is
not special to the resolver: \texttt{"Flag.en-US"} quite intentionally permits
\texttt{Flag.en-US.xnb}, \texttt{Flag.en-US.cnj}, and reader extensions.

If the suffixed XNB exists, the manager immediately opens, parses, decompresses, and dispatches
it by its own type-reader table. A malformed header, unsupported LZ4 compression, unregistered
XNB reader, failed LZX decode, or root-object type mismatch is therefore terminal; CNA does not
then try \texttt{base}, \texttt{base.cnj}, or a native extension. This happens even when the
manager has no local \texttt{LooseFileContentTypeReader<T>}: XNB dispatch is process-wide and
file-driven, as the registration section established. The focused XNB test proves a valid
\texttt{fixture.xnb} wins over a same-named \texttt{fixture.cnj}; no located test deliberately
places a broken XNB beside a healthy lower-priority candidate, but the control flow makes the
no-fallback result direct.

The same terminal rule applies below XNB. \texttt{exists(base)} accepts a literal file without
asking whether its extension belongs to \texttt{reader.GetExtensions()}; then the unconditional
\texttt{base.cnj} check runs before that reader's native list. Once either file exists,
\texttt{reader.Read()} is called exactly once. A bad \texttt{.cnj}, a corrupt image, a directory,
or a custom reader which rejects the selected path does not cause a second probe. The final bare
path is not a success indication either: it is deliberately returned to the reader so that its
own open/decode diagnostic is preserved. Consequently, the header's short statement that reader
extensions are tried ``if assetName has no file extension'' is only a user-facing convention, not
the literal algorithm: extension candidates are appended after any missing literal name,
including one containing dots.

\subsection{Literal files and \texttt{.cnj} sidecars are selected by the name you pass}

The ordering between the two loose candidates is easy to misread. An extensionless call such as
\texttt{Load<Texture2D>("sprites/hero")} chooses \texttt{sprites/hero.cnj} before
\texttt{sprites/hero.png}; that lets a valid sidecar override the default native decode. An
explicit existing literal call chooses the literal first instead:

\begin{lstlisting}
// Given hero.png and hero.cnj (whose sourceFile is hero.png):
Texture2D native  = content.Load<Texture2D>("sprites/hero.png"); // literal PNG
Texture2D sidecar = content.Load<Texture2D>("sprites/hero");     // hero.cnj, then its sourceFile
\end{lstlisting}

This is not merely explanatory: \texttt{CnjCacheIsolationTests} loads precisely that pair and
observes that the second result has the sidecar color-key transformation while the explicit PNG
retains its original pixels. The two calls also have distinct textual Texture2D cache keys.
There is no general ``an explicit extension disables XNB'' rule, however: the extra
\texttt{hero.png.xnb} check still occurs before the literal PNG.

The global \texttt{.cnj} probe does not consult the reader's extension list. A custom reader
whose \texttt{GetExtensions()} returns only \texttt{.foo} will still receive
\texttt{name.cnj} when that file exists, and must either understand or reject it. Built-in
readers make different choices after receiving it: texture, sound, and cube readers recognize a
\texttt{sourceFile} envelope; self-contained readers validate their own expected CNJ type; and
a reader which treats its path as a native stream has no automatic JSON adapter. A CNJ
\texttt{sourceFile} is a new, safely checked logical \texttt{Load} call, so it starts this whole
sequence again (including an XNB sibling of the source file), rather than being a direct native
file-open bypass.

\subsection{The built-in native-extension matrix is ordered and type-specific}

Only after a missing literal and a missing \texttt{.cnj} does the reader's own ordered list
matter. The current built-ins are deliberately not one universal ``asset extension'' registry:

\begin{description}
\item[\cnaclass{Texture2D}] \texttt{.png}, \texttt{.jpg}, \texttt{.jpeg}, \texttt{.bmp},
\texttt{.gif}, \texttt{.tga}, \texttt{.tif}, \texttt{.tiff}, then \texttt{.qoi}.
\item[\cnaclass{TextureCube}] \texttt{.dds} only; \texttt{std::shared\_ptr<Texture3D>} has
only self-contained \texttt{.cnj}, not a native volume-image format.
\item[\cnaclass{SoundEffect}] \texttt{.wav}; \cnaclass{Song} uses \texttt{.mp3},
\texttt{.ogg}, \texttt{.wav}, \texttt{.flac}, \texttt{.opus}, \texttt{.aac}, and
\texttt{.wma}, in that order.
\item[\cnaclass{Video}] \texttt{.mp4}, \texttt{.ogv}, \texttt{.webm}, \texttt{.mkv},
\texttt{.avi}, then \texttt{.mov}; its loose reader is not registered in Emscripten, Android,
or MinGW builds.
\item[\cnaclass{Model}] \texttt{.cnj}, \texttt{.gltf}, then \texttt{.glb}. The leading
\texttt{.cnj} is redundant after the manager's global sidecar probe, but does not alter the
result: a same-named CNJ beats glTF/GLB, while the runtime-glTF test proves a missing CNJ falls
through to \texttt{basic.gltf}.
\item[\cnaclass{SpriteFont}, \cnaclass{Effect}, \cnaclass{AnimationClipEXT}, and
\cnaclass{Curve}] self-contained \texttt{.cnj} only. The NOXNA
\cnaclass{SkinnedModelEXT} reader instead declares \texttt{.skinnedmodel.json}.
\end{description}

The list is an existence priority, not a content-sniffing policy. For example, when both a
\texttt{music.wav} and \texttt{music.ogg} exist, \cnaclass{Song} chooses the WAV even if its
decoder later rejects it; it does not retry Ogg. A \cnaclass{Model} likewise chooses a present
\texttt{.gltf} before \texttt{.glb}. The focused resolver tests cover a healthy native texture,
a healthy CNJ texture, the CNJ-over-native extension precedence, and the missing-CNJ glTF path.
They do not cover explicit-XNB names, an invalid sidecar beside a healthy native file, literal
files with unsupported extensions, directory candidates, or first-extension failure followed by
a valid later extension. Applications that need such recovery must choose and validate a concrete
path themselves, then expose it through a reader whose contract supplies that policy.

\subsection{\texttt{RootDirectory} is a base, not a sandbox or cache namespace}

The word ``root'' is a convenience, not a containment guarantee. CNA's
\texttt{BuildAssetPath()} returns the raw asset name when the root is empty and otherwise uses
\texttt{std::filesystem::path(rootDirectory) / assetName}, without rejecting an absolute name,
normalizing dot segments, canonicalizing a symlink, or checking that the result remains below the
configured directory. On the usual path rules, the important cases are:

\begin{lstlisting}
root = "Content"
"sprites/logo"     -> "Content/sprites/logo"
"../shared/logo"   -> "Content/../shared/logo"  // filesystem traversal can escape
"/srv/game/logo"   -> "/srv/game/logo"          // absolute right side replaces the base
\end{lstlisting}

An application may deliberately choose an absolute \texttt{RootDirectory} or direct file name,
but it must not treat either as a security boundary. A caller-controlled \texttt{assetName}, a
native file symlink below the root, or an in-root path containing \texttt{..} can reach outside
it. FNA likewise permits a rooted \texttt{RootDirectory} and its raw-asset fallback tries the
caller-given name, so strict root confinement is not an XNA/FNA compatibility promise. If content
names come from untrusted data, validate a relative, canonicalized allow-list before calling
\texttt{Load}; CNA's ordinary resolver is not that validation layer.

Its cache keys are a separate, purely textual rule. \texttt{NormalizeKey()} changes backslashes
to slashes and lowercases every character, but does not include \texttt{RootDirectory}, remove
\texttt{.}/\texttt{..}, resolve an extension, or canonicalize the filesystem. Thus
\texttt{"Sprites\\Logo"} and \texttt{"sprites/logo"} intentionally share a key, while
\texttt{"textures/../logo"} and \texttt{"logo"} can name the same file yet occupy two cache
entries. Conversely, on a case-sensitive filesystem two distinct files named \texttt{Logo} and
\texttt{logo} collapse to one cache identity, with the first loaded value winning. The generic
cache also keys by requested C\texttt{++} type; Texture2D has the same textual rule in its own
weak cache; move-only SoundEffect and TextureCube have no cache to alias.

Changing the root is consequently not a content switch for assets already looked up under the
same logical name. The setter only stores a new string, so this sequence returns the Theme A
model twice until eviction:

\begin{lstlisting}
content.setRootDirectoryProperty("ThemeA");
Model themeA = content.Load<Model>("hero");

content.setRootDirectoryProperty("ThemeB");
Model stillThemeA = content.Load<Model>("hero"); // generic cache key is still "hero"

content.Unload();
Model themeB = content.Load<Model>("hero");
\end{lstlisting}

The same setter does not clear the separately lazy content manifest, so
\texttt{GetContentManifest()} can also describe the old root until an explicit
\texttt{RefreshContentManifest()}. This applies independently of the cache cases above; it is
not a hot-reload mechanism. No located test changes \texttt{RootDirectory}, probes aliasing, or
loads an absolute/traversing asset name.

The two nested-reference paths need to be distinguished from this broad rule. A \texttt{.cnj}
\texttt{sourceFile} is robustly narrower: it rejects an absolute field, traversals, symlink
escapes, another \texttt{.cnj}, and implicit sidecar cycles by comparing weakly-canonical paths;
the focused safety tests cover each boundary. \texttt{ContentReader::ReadExternalReference<T>()}
instead rejects only a relative reference whose normalized logical form starts above the root.
An absolute reference is not rejected before it is passed to \texttt{ContentManager::Load()}, so
it follows the unrestricted asset-name path just described; the tests cover the relative
\texttt{..} rejection but not that absolute bypass. Song and Video XNB readers are wider again:
they normalize their embedded media path lexically but perform no root check, so either traversal
or an absolute media reference can name a file outside the content root. These are
source-established boundaries, not failure-injection reproductions.

\section{Direct loading: the shape of Chapter~\ref{ch:first-game}'s smallest program}
\label{sec:direct-loading}

The one-line construction in Chapter~\ref{ch:first-game}'s minimal game ---
\texttt{Texture2D("assets/logo.png", getGraphicsDeviceProperty())} --- is the third, simplest
path this chapter describes: \texttt{"assets/logo.png"} is a literal, directly loadable file
path, resolved without any \texttt{.cnj} involvement when the literal exists. It remains the
simplest path for a small, from-scratch CNA project. The resolver does still probe the distinct
\texttt{"assets/logo.png.xnb"} candidate first; it falls through to the literal file when that
compiled sibling is absent, not after probing a sidecar or every native extension.

\section{ContentManager: constructing it and calling Load}

The class every asset ultimately passes through, read directly from
\texttt{ContentManager.hpp}, has three constructors: \texttt{explicit
ContentManager(IServiceProvider*)}; a second form additionally taking
\texttt{const std::string\& rootDirectory}; and a \texttt{NOXNA}-tagged no-argument
\texttt{ContentManager()} that defaults \texttt{RootDirectory} to \texttt{"Content"} --- plus
the small set of methods a game actually calls day to day:

\begin{lstlisting}
// A Game already owns one ContentManager, built for it -- LoadContent() is where
// a real game reaches for it, per Chapter 5's ordering constraint:
ContentManager& content = getContentProperty();
content.setRootDirectoryProperty("Content");

auto logo = content.Load<Texture2D>("sprites/logo");   // no extension in the name
auto font = content.Load<SpriteFont>("fonts/hud");

content.Unload();  // evicts this manager's caches; retained asset values remain valid
\end{lstlisting}

\texttt{Load<T>(const std::string\& assetName) -> T} is a template, not a virtual dispatch ---
the name may be extensionless or an existing literal file. On a cache miss it first probes the
name-plus-\texttt{.xnb}, then the literal, then name-plus-\texttt{.cnj}, and only then its
type-specific native-extension list; the preceding section gives the terminal-candidate rule.
Two
\texttt{NOXNA} extension points exist for cases the built-in readers don't cover:
\texttt{RegisterTypeReader<T>} (taking a
\texttt{std::unique\_ptr<LooseFileContentTypeReader<T>>}) for a whole new
loose-file type, and \texttt{RegisterCnjLoader<T>(name, CnjLoaderFn<T>)} for a new named
\texttt{.cnj} ``type'' string resolving to an existing C\texttt{++} type --- the mechanism
\S\ref{sec:cnj} already named as the reason a game never needs to invent its own ad-hoc JSON
format for a custom asset type.

\subsection{\texttt{Load<T>()} has a success-only cache write, not one universal failure type}

The short Doxygen promise that \texttt{Load<T>()} ``throws \texttt{ContentLoadException} if the
asset cannot be loaded'' is a useful description of many deliberately validated content errors,
but it is not a complete C\texttt{++} exception contract. The template begins by rejecting a
disposed manager with \texttt{std::runtime\_error}; it does not reject an empty
\texttt{assetName} at all. An empty name therefore follows the ordinary resolution logic and its
eventual exception depends on the selected reader (or, with no reader for \texttt{T}, becomes the
ordinary ``no reader registered'' \texttt{ContentLoadException}). This differs from current FNA,
whose public \texttt{Load<T>} rejects a null or empty name with
\texttt{ArgumentNullException} and a disposed manager with \texttt{ObjectDisposedException}
before it looks in its cache.

CNA does deliberately normalize many content-domain failures to
\texttt{ContentLoadException}: an absent or null per-manager reader, a malformed XNB header,
unsupported compression or reader version, an unregistered XNB reader name, invalid type-reader
or shared-resource indices, malformed \texttt{.cnj} envelopes, and a known wrong \texttt{.cnj}
type all take that route. The focused XNB tests exercise malformed magic, both unsupported
compression-flag forms, an unregistered reader, and a declared file length larger than the real
file; the focused CNJ tests exercise envelope and type validation. Those tests establish useful
diagnostics for bad content, not a catch-all conversion layer around every operation below
\texttt{Load<T>()}.

Several meaningful failures intentionally remain their original C\texttt{++} exception. A
missing native image reached through either a direct texture load or a \texttt{.cnj}
\texttt{sourceFile} reaches the image decoder and throws \texttt{std::runtime\_error}; the
dedicated source-file test asserts that exact propagation. A real XNB \cnaclass{Song} whose
embedded companion media file cannot be found reaches the public load call as
\texttt{System::IO::FileNotFoundException}, likewise covered end to end. A custom loose reader
or a \texttt{RegisterCnjLoader} factory is ordinary application C\texttt{++} code and is called
without a wrapper, so an exception it throws is also the exception its caller sees. Finally, XNB
root-object dispatch uses \texttt{std::any\_cast<T>}; asking for a \texttt{T} different from the
root reader's actual result can therefore surface \texttt{std::bad\_any\_cast}, and truncated
reader payloads can surface \texttt{System::IO::EndOfStreamException}. Neither a root-type
mismatch, an empty name, a throwing custom callback, nor a failed-then-retried load has a located
\texttt{ContentManager} integration test yet.

\Needspace{10\baselineskip}
Callers that want one diagnostic boundary should make it explicitly rather than assuming the
content exception is exhaustive:

\begin{lstlisting}
try {
    auto level = content.Load<GameLevelData>("levels/intro");
    StartLevel(level);
} catch (const ContentLoadException& error) {
    ShowContentDiagnostic(error.what());      // validated content-format/configuration problem
} catch (const std::exception& error) {
    ReportUnexpectedAssetFailure(error.what()); // decoder, companion file, or custom reader
}
\end{lstlisting}

There is one reassuringly narrow cache rule, with an important qualification. The generic
\texttt{loadedAssets\_} entry is assigned only after \texttt{LoadXnbAsset()} or the loose
reader has returned a \texttt{T}; a failed top-level read therefore does not poison that
type-plus-normalized-name entry, and the next call attempts the read again. Texture2D follows
the same ``result first, weak-cache write second'' order, while move-only SoundEffect and
TextureCube have no manager cache at all. This is not a transaction for arbitrary reader code:
a reader may successfully call \texttt{cm.Load} for another asset before it later fails, thereby
caching that nested asset, and an expired Texture2D weak entry is erased before its replacement
load is attempted. Applications needing all-or-nothing multi-asset loading must hold and publish
their own aggregate only after every individual load succeeds; \texttt{ContentManager} has no
loading sentinel, rollback, or cycle-detection protocol.

\subsection{One manager assumes serialized operations and stable reader registration}

The same absence of a loading sentinel is also a concurrency contract. A live
\texttt{ContentManager} contains ordinary \texttt{std::unordered\_map}s for generic assets,
weak textures, loose readers, and named CNJ factories; an ordinary \texttt{std::vector} and
boolean for its lazy manifest; a \texttt{std::string} root; and non-atomic raw device/provider
pointers plus a non-atomic disposed flag. Neither the header nor implementation contains a mutex,
atomic guard, reader/writer lock, or ``currently loading'' table around any of them. Thus two
threads which overlap a cache miss, \texttt{Load()} and \texttt{Unload()}, load and registration,
manifest refresh and manifest inspection, or a root/device/disposal change and a load have an
unsynchronized read/write of ordinary C\texttt{++} state. That is a data race and undefined
behavior, not merely a chance of decoding an asset twice. Even a cache hit should not be promoted
to a supported parallel-load API: it still observes the unsynchronized manager state and may
reconstruct or use a graphics backend whose own thread-affinity contract is separate.

Current FNA does not supply a contrary per-manager guarantee. Its public \texttt{Load<T>} reads
and writes an ordinary \texttt{Dictionary<string, object>} without a manager-level lock; the
\texttt{ContentManagerLock} in its source protects only FNA's static weak list of managers. The
two implementations differ in their formats and exception types, but neither source establishes
``call one ContentManager from arbitrary loading threads'' as an XNA/FNA compatibility promise.
No located CNA content test starts a thread, uses a sanitizer race detector, or overlaps any of
these operations.

There are important single-threaded reentrancy cases too. A custom CNJ factory or loose reader
receives \texttt{ContentManager\&} and can call it again. A different nested asset may load and
remain cached even if the outer reader later throws. A nested request for the same uncached
\texttt{(T, normalizedName)} finds no provisional entry, recursively enters the same reader, and
has no cycle check to stop eventual stack exhaustion. Calling \texttt{Unload()} from such a
reader clears the maps at that instant, but the suspended outer \texttt{Load<T>} writes its own
result into the cache after \texttt{Read()} returns; calling \texttt{Dispose()} there similarly
sets the disposed guard only after clearing, while the already-running outer call can still return
and write its result. Neither operation is a reentrant cancellation barrier.

Reader replacement is narrower and more dangerous. \texttt{Load<T>} obtains a raw pointer to the
\texttt{shared\_ptr} held inside its type-reader map, dereferences it, and calls \texttt{Read()}
without retaining another local \texttt{shared\_ptr}. If that reader calls
\texttt{RegisterTypeReader<T>} for its own \texttt{T}, the map assignment can destroy the reader
object while its member function is still executing. This is an untested lifetime hazard even on
one thread, not a supported hot-swap mechanism. A normal registration replacement outside an
active read remains subject to the earlier cache rule: it affects only a later cache miss after
\texttt{Unload()}.

The reliable application discipline is consequently deliberately boring: finish all reader
registration and graphics-device/root configuration before the loading phase; serialize every
mutable manager operation (Load, Unload, Dispose, registration, root/device changes, and manifest
refresh) through one owner thread or a reentrancy-aware loading coordinator; never replace a
reader from its own callback; and make recursive references acyclic with different logical names.
Publish fully loaded asset values to worker threads afterwards rather than sharing the manager as
a general concurrent cache. A plain non-recursive external mutex around every public call is not
automatically sufficient, because legitimate nested loads would deadlock and it cannot make a
self-replacing active reader safe.

\subsection{A service provider is stored, not consulted, in current CNA}

The two \texttt{IServiceProvider*} constructors look deliberately XNA-shaped, but their live
CNA contract is narrower than their header comment suggests. Both constructors merely store the
raw pointer, retain the field's \texttt{"Content"} root default unless the caller supplies a
root, and register the built-in readers. \texttt{getServiceProviderProperty()} simply returns
that stored address. There is no \texttt{IServiceProvider::GetService()} call anywhere in
\texttt{ContentManager.cpp}: registering an \texttt{IGraphicsDeviceService} in a
\texttt{GameServiceContainer} does \emph{not} make a standalone manager discover a graphics
device. The current Doxygen promise that the provider is ``used to resolve graphics and other
services'' is therefore stale implementation documentation, not an additional setup route.

FNA has the opposite lazy dependency rule. Its public constructors reject a null provider; the
first code path that needs a graphics device asks \texttt{ServiceProvider} for
\texttt{IGraphicsDeviceService}, throws \texttt{ContentLoadException("No Graphics Device
Service")} if it is absent, and caches the returned device. CNA accepts
\texttt{ContentManager(nullptr)} --- many parser-only tests intentionally use it --- but a
GPU-backed reader must instead find the device previously set by CNA's explicit method. The
direct video-reader test makes this boundary especially clear: its successful fixture first calls
\texttt{setGraphicsDevice(gd)}, while its paired no-device case throws
\texttt{ContentLoadException}; neither case asks a provider.

For a standalone manager, retain the explicit association even if a service container is useful
to the rest of the application:

\begin{lstlisting}
GameServiceContainer services;
ContentManager assets(&services, "Content"); // retrievable metadata; no lookup occurs
assets.setGraphicsDevice(device);             // required before a GPU-backed Load

auto logo = assets.Load<Texture2D>("sprites/logo");
\end{lstlisting}

\texttt{setGraphicsDevice()} records only another raw address; it neither transfers ownership
nor follows later service-container registrations. A reader which never asks
\texttt{getGraphicsDeviceInternal()} can work without this call, but that is a property of that
specific reader, not evidence that service resolution occurred. Conversely, model, texture,
effect, font, or video paths may ask for the device during their own construction, so attach it
before the first such load and keep it alive for the manager's use. \texttt{Game} avoids the
standalone trap by a different route: it default-constructs \texttt{Content\_} with no provider
and immediately calls \texttt{Content\_.setGraphicsDevice(GraphicsDevice\_)} in its constructor.
\texttt{ResourceContentManager} does not repair this difference; its provider-taking constructor
only delegates to the same base constructor and its embedded-resource stream operation remains a
documented CNA stub. No located test supplies a non-null provider to \texttt{ContentManager} or
proves provider-based device discovery.

\subsection{\cnaclass{ResourceContentManager} is a surface-only stub, not an alternate content root}

The similarly named derived class deserves a sharper warning than that final sentence gives it.
In current CNA it is \emph{not} a working way to load an embedded asset and it is not a stream
back-end selected by ordinary \texttt{Load<T>()}. Its whole C\texttt{++} surface is one public
constructor, \texttt{ResourceContentManager(IServiceProvider*)}, and one protected virtual
\texttt{OpenStream} overload taking a const string reference. The constructor stores the same raw,
unconsulted provider through \cnaclass{ContentManager}; it accepts null, supplies no resource
object or resource name, retains the base \texttt{"Content"} root, and has no member state of its
own. Its only method ignores \texttt{assetName} and unconditionally throws:

\begin{lstlisting}
throw std::runtime_error(
    "ResourceContentManager::OpenStream is not implemented in CNA.");
\end{lstlisting}

That exception is intentionally not \cnaclass{ContentLoadException}; it reports an unimplemented
API surface, not a missing or malformed asset. Since the method is protected, ordinary game code
cannot call it directly. A derived class may call or override it, but that alone cannot turn the
object into a content source.

The reason is visible in the complete CNA call graph: no source path calls the derived class's
\texttt{OpenStream()}, and none of \cnaclass{ContentManager}'s generic or specialized
\texttt{Load} paths calls a virtual stream hook. They use the filesystem candidate sequence from
\S8.4 and open their own file streams directly.
Thus a \texttt{ResourceContentManager} instance can still load an ordinary loose file exactly as
its base class can (subject to the same reader, root, device, cache, and disposal rules), because
that inherited load does \emph{not} reach the throwing method. Conversely, overriding
\texttt{OpenStream()} in a subclass does not redirect an inherited \texttt{Load<T>()}; those
templates are not virtual stream consumers. A subclass would need a separate loading API or an
intentional change to the base loading architecture.

This is materially unlike the current FNA/XNA-shaped implementation. FNA requires both an
\texttt{IServiceProvider} and a non-null \texttt{System.Resources.ResourceManager}; its override
looks up the exact logical resource name, accepts only a \texttt{byte[]} value, and returns a
buffer-visible \texttt{MemoryStream}. Missing or non-binary entries become
\texttt{ContentLoadException}. FNA's ordinary \texttt{ReadAsset<T>()} reaches the virtual
\texttt{OpenStream()} first (then its own raw-file fallback), so its
\cnaclass{ResourceContentManager} really does participate in normal \texttt{Load<T>()}. CNA has
neither the required resource-manager constructor nor that virtual dispatch seam; its earlier
API-coverage document correctly labels the class a stub, despite the class itself compiling.

No CNA test constructs this class, calls the throwing method through a test-only derived probe,
or proves that inherited loose loads bypass it. Treat embedded-resource support as
\texttt{needs\_human}, not as an opportunistic reader-registration task: a real C\texttt{++}
implementation must choose an embedded-resource abstraction and ownership model, decide whether
to add the FNA-compatible resource-manager constructor or a deliberately NOXNA equivalent, wire
the base loader through a stream abstraction without regressing live filesystem behavior, and add
binary/missing/non-binary/lifetime tests. Until that public architectural decision is made, use an
ordinary \cnaclass{ContentManager} for CNA's supported loose, CNJ, and XNB paths rather than
instantiating this subclass for a capability it does not provide.

\subsection{\cnaclass{TitleContainer} is an independent direct-file helper, not a ContentManager stream hook}
\label{sec:title-container-contract}

\cnaclass{TitleContainer} has a much smaller, separate job from either content-manager class:
its sole public operation is the static \texttt{OpenStream} function. It normalizes every
backslash in the supplied name to a forward slash, resolves a non-rooted name against the
process-global \cnaclass{TitleLocation}, and returns a uniquely owned read stream. It does not
know a requested asset type, an XNB reader, a content root, or a resource manager. In particular,
a repository-wide source search finds no call from either content-manager class to
\cnaclass{TitleContainer}; ordinary \cnaclass{ContentManager} \texttt{Load<T>()} calls continue
to form candidates from their own \texttt{RootDirectory} and open filesystem streams directly.
Changing CNA's title-location setter therefore does not redirect a game's content load, and
changing a content root does not redirect \texttt{OpenStream()}.

The default title base is initialized once, on the first getter: CNA asks SDL3 for its application
base path and falls back to the then-current working directory only when SDL supplies no path. SDL3
documents that returned base-path pointer as a cached, const pointer; copying it into the CNA
string does \emph{not} create an SDL allocation which this code must free. The chosen string then
remains fixed even if the working directory changes. CNA additionally exposes a NOXNA public
setter which accepts any string without existence, absoluteness, or canonicalization checks. Both
accessor spellings return a const reference to that one mutable static string, so a later setter
can invalidate a held reference; neither initialization nor setting has synchronization. Configure
a custom title base once, before other threads obtain paths, and retain a copy rather than a
returned reference if another component might reconfigure it. Current FNA instead exposes an
internal, getter-only title-location property delegated to its platform layer, so CNA's setter is
a C\texttt{++}-specific test/launcher extension, not portable XNA application surface.

Resolution is lexical rather than a containment or security policy. A rooted name becomes a
lexically normalized C\texttt{++} filesystem path directly; a relative name is appended to the
title base and then lexically normalized. On Windows, a drive letter followed by a slash is also
rooted; on every build, an initial slash is rooted. No canonicalization, prefix check, or symlink
check follows. Thus \texttt{"../outside.dat"} can leave the configured title directory, and a
symlink inside it can reach elsewhere. An empty name resolves to the base directory itself. This
helper is appropriate for trusted application-controlled paths, not for confining a user-supplied
filename. Its backslash conversion is a convenience for a logical relative name, not an
authorization check.

On ordinary platforms CNA first performs a filesystem existence check on the resolved path, then
opens a read-only stream. A missing path produces a generic runtime error that names the resolved
filename. Filesystem-status failures and an existing directory or unreadable file can instead
expose their filesystem or stream exception. The helper logs both the original name and the fully
resolved path at Info level, which is useful while packaging but can disclose a local installation
path in ordinary logs. Android adds an intentionally separate fallback: when the normal filesystem
check fails, it asks SDL to load the normalized relative name first and then the resolved name. Its
returned data are copied into
\cnaclass{MemoryStream} before the SDL buffer is freed, so the stream does not borrow SDL memory.
That Android-only conversion narrows \texttt{size\_t} to CNA's signed \texttt{intcs} without a
range check, however; an asset larger than that maximum is outside its established safe contract.

This differs in both shape and failure boundary from current FNA's direct
\texttt{File.OpenRead}: FNA has no public mutable title location and lets the managed file API
choose its normal file/directory/access exception. It also reinforces why
\cnaclass{TitleContainer} cannot repair the embedded-resource stub in \S8.6: it supplies a
one-off direct stream for an application path, while CNA's inherited content loads do not consult
any stream hook at all.

The four focused CNA tests establish much less than their names imply. The relative and absolute
cases assert only that a non-null stream is returned, not that the expected bytes can be read. The
test labelled ``normalizes backslashes'' actually passes \texttt{"sub/file.txt"}, with a forward
slash, so it never exercises the conversion it describes. The missing-file case checks only the
broad \texttt{std::runtime\_error}. No located test covers parent traversal, symlinks, an empty
or directory name, access failures, the resulting log text, Android asset loading or its size
limit, initial SDL/fallback selection, title-location reference lifetime, or concurrent global
mutation. The tests also set the global title path to fixed temporary names without restoring it.
Treat it as shared process configuration and isolate it in any new tests; do not treat these four
happy-path probes as a sandbox or platform-packaging test.

\subsection{\texttt{Unload()} evicts manager caches; it is not a universal asset destructor}

The shortened comment in many XNA examples --- ``unload the content'' --- is useful only if its
ownership boundary is kept explicit. CNA's live \texttt{ContentManager::Unload()} has exactly two
operations: it clears the generic \texttt{loadedAssets\_} map and the special
\texttt{textureCache\_} map. It does not walk the returned objects and call a common
\texttt{Dispose()} method, because the map holds type-erased C\texttt{++} values rather than one
uniform managed-object base. Nor does it clear reader registrations, the root directory, graphics
device pointer, or the separately maintained content-manifest snapshot. It is an eviction of this
manager's lookup state, not an instruction to invalidate every value a game has already received.

For ordinary copyable \texttt{T}, the generic cache key is the pair of \texttt{typeid(T)} and the
normalized logical asset name. A second matching \texttt{Load<T>()} returns the stored
\texttt{std::any} value; clearing the map drops only the manager's copy. A caller-held
\texttt{std::shared\_ptr} consequently keeps its model, effect, or other shared object alive after
\texttt{Unload()}. The real avatar wardrobe-hotswap example depends on precisely this rule: it
keeps its current \texttt{SkinnedModelEXT} in a member, calls \texttt{Unload()} to evict the old
base-avatar lookup, then loads a fresh base asset without dangling the model/renderer it is still
using during the transition.

Three specializations are deliberately different from that generic strong cache:

\begin{description}
  \item[\cnaclass{Texture2D}.] Its table contains only weak references to the GPU backend and
    optional CPU pixel shadow. Keeping a returned \texttt{Texture2D} value alive keeps that
    backend alive; dropping all such values lets it free even if the content manager itself is
    still alive. \texttt{Unload()} removes the weak lookup entry as well. The focused real-XNB
    test intentionally retains its first texture through \texttt{Unload()}, then proves the
    next load builds a \emph{different} backend; it does not assert that the retained first
    texture became invalid, because it did not.
  \item[\cnaclass{SoundEffect} and \cnaclass{TextureCube}.] Both types are move-only, so neither
    can enter the generic \texttt{std::any} cache. Every \texttt{Load} decodes a fresh,
    independently owned instance; \texttt{Unload()} has no manager cache entry through which to
    release either one. For \cnaclass{SoundEffect}, this avoids one caller's disposal cascade
    silently affecting another caller's playback.
\end{description}

The cache tests establish two concrete, bounded facts: overwriting a generic XNB on disk is
invisible to a second load until \texttt{Unload()} clears its cache, while a retained
\texttt{Texture2D} gets a newly constructed backend on the post-unload load. They do not test a
complete cross-type shutdown protocol, and no located test exercises content-manager destruction
or a load attempted after disposal.

\texttt{Dispose()} itself simply calls \texttt{Unload()} once and then makes later
\texttt{Load<T>()} calls throw \texttt{std::runtime\_error}; a later \texttt{Unload()} does not
clear that disposed guard or make the manager reusable. The C\texttt{++} destructor is defaulted,
not an implicit call to this public method. This is why an application needing the explicit cache
eviction point should call \texttt{Unload()} deliberately, and why a game which wants the
post-disposal contract described in Chapter~\ref{ch:game-loop} must call \texttt{Game::Dispose()}
rather than rely solely on scope exit. The manifest is intentionally independent again:
\texttt{GetContentManifest()} returns its old point-in-time scan after an unload until
\texttt{RefreshContentManifest()} is requested; neither method checks the disposed flag in the
current source. Treat those \texttt{NOXNA} methods as diagnostics, not as a cache-lifetime API.

\subsection{\texttt{Game::Content} replacement copies a manager; it does not replace one}

There is one deceptively ordinary setter in \cnaclass{Game} whose C\texttt{++} translation has a
much stronger consequence than its C\# name suggests. Game constructs its member
\texttt{Content\_}, then calls \texttt{Content\_.setGraphicsDevice(GraphicsDevice\_)}. Its public
\texttt{setContentProperty(const ContentManager\& value)} is only this assignment:

\begin{lstlisting}
void Game::setContentProperty(const ContentManager& value)
{
    Content_ = value;
}
\end{lstlisting}

\texttt{ContentManager} declares no copy or assignment operation of its own, so C\texttt{++}
generates memberwise copying here. The root directory, disposed flag, manifest snapshot, generic
asset values, weak texture entries, and reader/loader tables are all copied; a reader table holds
shared pointers, while its graphics-device and service-provider fields are raw pointers copied as
raw addresses. This is not a transfer of manager identity or ownership. In particular, assigning
a newly constructed standalone \texttt{ContentManager} overwrites Game's already-configured
graphics-device pointer with null; the next \texttt{Load<Texture2D>()} or
\texttt{Load<TextureCube>()} reaches \texttt{getGraphicsDeviceInternal()} and throws. Assigning a
manager configured for a different device instead leaves Game's content pointing at that external
device, which can become dangling if its owner goes away. Assigning a disposed manager transfers
the disposed flag too, so all subsequent loads fail immediately.

Current FNA makes a materially different operation: its \texttt{Game.Content} property rejects
null, then stores the supplied \texttt{ContentManager} reference. No cache or raw device pointer
is cloned. CNA's reference parameter naturally cannot be null, but its assignment is still not
the same replacement operation. A repository-wide search found no CNA call site for this setter
and no test that copies a content manager, replaces a game's content, checks an assigned device,
or assigns a disposed manager. Treat it as an untested compatibility boundary rather than an
ordinary way to switch content roots.

For the common configuration task, preserve Game's existing manager and configure it in place:

\begin{lstlisting}
auto& content = getContentProperty();
content.setRootDirectoryProperty("OtherContent"); // keeps Game's GraphicsDevice association
\end{lstlisting}

Use a separate \texttt{ContentManager} directly only when its graphics-device lifetime and its
asset ownership are deliberately controlled by the caller. Do not use
\texttt{setContentProperty()} merely to change \texttt{RootDirectory}; it creates a snapshot with
the source manager's pointer and cache state instead of preserving the target game's live state.

\begin{sourcenote}
\textbf{A worked example: asking the content root what files it saw.} Rather than walking a
content tree independently, tooling can use CNA's real, \texttt{NOXNA}-tagged inventory:
\texttt{ContentManager::GetContentManifest()} scans the content root lazily on its first call
(or a caller can invoke the public \texttt{RefreshContentManifest()}) and returns one
\cnaclass{ContentManifestEntry} per logical asset name, reading directly from
\texttt{ContentManifestEntry.hpp}:

\begin{lstlisting}
const auto manifest = content.GetContentManifest(); // value copy: stable across a later refresh
for (const ContentManifestEntry& entry : manifest) {
    std::cout << entry.relativePath << ": ";
    if (entry.hasXnb) {
        std::cout << ".xnb candidate exists";
    } else if (!entry.nativeExtensions.empty()) {
        std::cout << "native candidate (" << entry.nativeExtensions[0] << ")";
    } else if (entry.hasCnj) {
        std::cout << ".cnj candidate exists";
    }
    std::cout << "\n";
}
\end{lstlisting}

Each \cnaclass{ContentManifestEntry} exposes exactly the three booleans/lists this chapter's
resolution-order section depends on --- \texttt{hasXnb}, \texttt{hasCnj}, and
\texttt{nativeExtensions} --- plus, when a \texttt{.xnb} file is present and readable,
\texttt{xnbReaderNames}: the canonical reader-type names its own type-reader table references,
letting a companion method, \texttt{GetXnbReaderUsageSummary()}, aggregate across an entire
content tree which reader types are actually exercised and whether
\cnaclass{ContentTypeReaderManager} currently has a registered reader for each one --- a real,
runnable first inventory for ``which reader names occur in my compiled XNA content'' without
reading any individual \texttt{.xnb} file by hand. The next subsection gives the important
limits before treating that inventory as a loadability verdict.
\end{sourcenote}

\subsection{The manifest is an unsorted best-effort inventory, not a resolver or health check}

The deliberately changed word ``candidate'' above matters. The manifest is additive
introspection only: \texttt{Load<T>()} and \texttt{ResolveAssetPath()} still make their own live
\texttt{std::filesystem::exists()} checks and do not consult it. A row says that a regular file
with that final extension was seen below the root; it does not prove a reader for the requested
\texttt{T} exists, that the native extension is one that reader accepts, that a GPU device is
attached, that a CNJ envelope is valid, or that the XNB object can deserialize. Thus an XNB row
still ranks ahead of a native/CNJ candidate in the ordinary resolver, but a malformed XNB can make
the real \texttt{Load} fail rather than fall through to a displayed sibling. The manifest must
not be used as a dry-run or as a way to change resolution precedence.

The reader-name column is best-effort in a narrower way. For an exact lower-case
\texttt{.xnb} extension, the scan reads the entire file and inventories only an uncompressed,
well-formed header/table. An unopened or malformed file, and every compressed file (LZX as well
as currently unsupported LZ4), remains \texttt{hasXnb = true} with an empty
\texttt{xnbReaderNames} vector. There is no status or error field distinguishing those cases
from an XNB that genuinely names no readers, and the usage summary omits that blank entry
altogether. The planned compressed-reader inventory remains unimplemented even though normal
LZX \emph{loading} exists. Similarly, \texttt{isRegistered} asks the global factory map anew
for each summary call: registering a name changes that boolean without a rescan, while new files
or changed reader-name tables need \texttt{RefreshContentManifest()}. As the earlier registry
audit showed, ``registered'' means only that a map key is present; it does not validate that a
stored factory is callable.

Neither order nor scan completeness is a deterministic contract. Directory traversal order feeds
the \texttt{nativeExtensions} list, then an \texttt{unordered\_map} supplies the manifest and a
second \texttt{unordered\_map} supplies the usage summary; none is sorted. Tooling which writes
a report or diff should make and sort its own value copy by \texttt{relativePath} (and sort native
extensions/reader names as needed), rather than treating the current order as stable. Extension
classification is byte-exact too: \texttt{asset.XNB} is recorded as a native \texttt{.XNB}
extension, not as \texttt{hasXnb}; a dotless file contributes an empty native extension. No
located test covers order, case variants, dotless names, or multiple native extensions.

Finally, the scanner has no public error result and no explicit entry, depth, or total-byte scan
budget. A missing/inaccessible root produces a successful-looking empty snapshot; permission
denials are skipped where the iterator can skip them, and a later iteration error can leave a
partial scan marked built. Every uncompressed XNB is read wholesale before its table is parsed.
\texttt{GetContentManifest()} returns a const reference to the manager's internal vector, not a
value snapshot: the vector object remains owned by the manager, while a refresh can invalidate
its element references, pointers, and iterators and replace what a held vector reference observes.
Copy it before retaining, sorting, or passing it beyond the serialized inspection phase described
above. These are diagnostic-tooling limits, not reasons to feed untrusted trees to the method as
a bounded validator.

\subsection{Audio and video: the \cnaclass{SoundEffect} / \cnaclass{Song} / \cnaclass{Video} readers}
\label{sec:xnb-audio}

The hardening pass above covers the texture side of the reader set; the audio side has its own
real story, worth a worked example in its own right. \texttt{SoundEffectReader} is a
line-by-line port of FNA's own \texttt{SoundEffectReader.cs}, but CNA's own support surface is
narrower and stated as a concrete matrix rather than an all-or-nothing claim, read directly from
the reader's own header comment:

\begin{description}
  \item[16-bit PCM.] The fast path --- CNA's \cnaclass{SoundEffect} raw-buffer constructor
        already speaks \texttt{SDL\_AUDIO\_S16LE} natively, so a 16-bit PCM \texttt{.xnb} needs
        no conversion at all.
  \item[8-bit PCM, 32-bit IEEE float, MS-ADPCM, IMA-ADPCM.] Wrapped in a minimal, synthetic
        in-memory WAV file (\texttt{CNA::Internal::Audio::BuildWavFromWaveFormatEx}, forwarding
        the real captured \texttt{WAVEFORMATEX} extension bytes verbatim) and decoded through
        \cnaclass{SoundEffect}\allowbreak{}\texttt{::FromStream}, reaching SDL3's own native
        WAV/ADPCM decoder --- CNA never had to implement a float or ADPCM decoder of its own.
  \item[XMA2.] Rejected outright with a documented \texttt{ContentLoadException} naming the
        format --- SDL3 has no XMA2 decoder either, so there is no decode path anywhere in this
        stack, and the reader says so rather than silently constructing a
        \cnaclass{SoundEffect} that would play back as noise.
\end{description}

\paragraph{A worked example: a real fixture with no coefficient table at all.}
Widening MS-ADPCM support past the original PCM16-only baseline surfaced a real, XNA-specific
gap rather than a clean conversion. A hex dump of a real MonoGame-produced
\texttt{tone\_mono\_44khz\_msadpcm.xnb} fixture shows its \texttt{cbSize} field (the format
extension's declared byte length) is \texttt{0} --- no \texttt{wSamplesPerBlock}, no coefficient
table, nothing --- matching FNA's own reader, which never captures this extension for any
non-XMA2 format either. IMA-ADPCM tolerates this: SDL3's own decoder can derive
\texttt{wSamplesPerBlock} from \texttt{nBlockAlign} when it is missing. MS-ADPCM cannot ---
SDL3's decoder (\texttt{SDL\_wave.c}'s \texttt{MS\_ADPCM\_Init}) requires an explicit,
valid coefficient table or it fails outright. The fix synthesizes one, using the same standard
preset coefficients \cnaclass{WaveBank}'s own ADPCM path already relies on, plus a
\texttt{samplesPerBlock} value computed directly from \texttt{nBlockAlign} via the MS-ADPCM
``Standards Update'' formula every encoder (XNA's own included) follows:

\begin{lstlisting}
uint16_t ComputeMsAdpcmSamplesPerBlock(uint16_t blockAlign, uint16_t channels) {
    const uint32_t ch = channels == 0 ? 1u : channels;
    const uint32_t blockHeaderBits = ch * 7u * 8u;
    const uint32_t blockBits = static_cast<uint32_t>(blockAlign) * 8u;
    const uint32_t availableBits = blockBits > blockHeaderBits ? blockBits - blockHeaderBits : 0u;
    const uint32_t blockDataSamples = availableBits / (4u * ch);
    return static_cast<uint16_t>(blockDataSamples + 2u);   // +2: the block's own two header samples
}
\end{lstlisting}

This only ever runs when the \texttt{.xnb} genuinely supplied no usable extension of its own
(\texttt{cbSize} below the real 32-byte minimum a coefficient table needs) --- an XNB that
\emph{does} carry a real extension is forwarded verbatim, unmodified.

\paragraph{A C\texttt{++}-specific architectural gap this widening exposed.}
Reading \cnaclass{SoundEffect} through the generic reader machinery hit a real language-level
wall the texture readers never do. \texttt{ContentTypeReader<T>::ReadUntyped()}'s own job is
FNA's object-boxing glue --- box a typed \texttt{Read()} result into the type-erased
\texttt{std::any} every reader returns through --- but \texttt{std::any} requires its held type
to be \texttt{CopyConstructible}, unconditionally. \cnaclass{SoundEffect} is deliberately
move-only (its per-owner \texttt{Dispose()}-cascade tracking needs a single unambiguous owner),
so a literal \texttt{std::any(std::move(result))} for a \cnaclass{SoundEffect} result simply does
not compile. The fix branches at compile time, in the one shared base-class method every reader
already goes through, so no individual reader --- including \texttt{SoundEffectReader} itself ---
needs to know this branch exists:

\begin{lstlisting}
std::any ReadUntyped(ContentReader& input, std::any existingInstance) override {
    if constexpr (std::is_copy_constructible_v<T>) {
        // ...box/unbox T directly, exactly as every ordinary reader already does...
    } else {
        // T is move-only (e.g. SoundEffect): box/unbox as std::shared_ptr<T> instead,
        // unwrapped back out symmetrically by InnerReadObject<T>().
        std::optional<T> existing = existingInstance.has_value()
            ? std::optional<T>(std::move(*std::any_cast<std::shared_ptr<T>>(std::move(existingInstance))))
            : std::nullopt;
        T result = Read(input, std::move(existing));
        return std::any(std::make_shared<T>(std::move(result)));
    }
}
\end{lstlisting}

Several readers use a copyable value or a \texttt{shared\_ptr} handle and never touch this branch.
The bare move-only targets are currently \cnaclass{SoundEffect} and \cnaclass{TextureCube};
both depend on it. The branch still belongs in the shared base so a future move-only reader does
not need to rediscover the same wall, but the direct reader overloads described in
\S\ref{sec:content-type-reader-contract} must learn the same box/unbox convention before they can
support those targets.

\texttt{SongReader} and \texttt{VideoReader} both follow a simpler, sibling shape: neither reads
an embedded media payload at all, since real XNA \cnaclass{Song} / \cnaclass{Video} assets are
always external files (\texttt{.ogg} / \texttt{.oga} / \texttt{.qoa} for \cnaclass{Song},
\texttt{.ogv} / \texttt{.ogg} for \cnaclass{Video}) referenced by name --- both are ports of FNA's
own strip-last-four-characters-then-reprobe extension-normalization logic, verified against a
real MonoGame-produced \texttt{.xnb} together with its real vendored companion media file so the
extension probing has something genuine to find on disk.

\section{What this means for porting}

Chapter~\ref{ch:migration-guide}'s migration guide covers this in full practical detail, but the
short version, now that this chapter has given the corrected picture, is worth stating here:
porting an existing XNA/FNA game's compiled \texttt{.xnb} content is, for the specific asset
types \S\ref{sec:xnb-and-cnj-model} named as complete (textures, sprite fonts, stock effects,
sound effects, songs, and models), increasingly a matter of pointing CNA at the original,
unmodified compiled assets and letting the real binary reader do the work --- not, as an
earlier version of this book's own understanding assumed, a mandatory translation into
hand-authored JSON. For asset types the \texttt{.xnb} reader has not reached yet, or a custom
compiled \texttt{.fx} effect (permanently out of scope for the reason
Chapter~\ref{ch:shader-fx-gap} already gave), \texttt{.cnj} or a direct native-format
conversion remains the path.
