\chapter{The CnaTests Architecture}
\label{ch:cnatests-architecture}
\label{ch:verification-methodology}

Chapter~\ref{ch:testing-philosophy} in this Part covers the individual verification
\emph{mechanisms} this ecosystem relies on --- pixel tests, differential testing, the D3D9
oracle, sanitizers, the \texttt{NOXNA} build gate. This short closing chapter of Part~VIII takes
a different cut through the same material: comparing how much of that machinery actually
reaches each of the four platforms the previous three chapters covered, side by side, because
the honest answer varies more than a single ``cross-platform and verified'' claim would
suggest.

\section{Why the gradient exists, and why it is not a criticism}

None of the gaps this table names are hidden anywhere in this ecosystem's own documentation
--- every one of them was found, in this book's own research, stated plainly in the project's
own docs, exactly the way Chapter~\ref{ch:what-is-cna} described this project's
overall relationship with its own claims. The gradient itself is a predictable consequence of
where the actual development happens: this is a Linux development environment first, with
Windows reached through an elaborate but real Wine-based bridge, and Web/Android reached
through cross-compilation toolchains that can verify \emph{building} far more easily than
they can verify \emph{running correctly}, absent a real browser or a real device. A native
Linux pixel test can assert on an exact color value; an Emscripten build that cannot even
construct a graphics device has no equivalent assertion available to it at all, no matter how
carefully the surrounding C\texttt{++} is written.

This book's own coverage has exactly the same shape of gradient, worth naming rather than
leaving implicit: Windows, Web, and Android each earned a full chapter in this Part because
each has a substantial, documented, mechanically-interesting verification story to tell; macOS
has real, working input support confirmed in the project's own platform notes, but no
comparably deep verification narrative exists to expand into its own chapter, since --- unlike
Windows' Wine bridge or Android's emulator --- there is no equivalent automated or
semi-automated stand-in for a real Mac in this project's own dev loop at all.

\section{The oracle corpus, end to end}

The Linux row of the table above credits ``real differential testing against a genuine FNA
install'' in one clause, but the single strictest instance of that testing --- the D3D9 oracle
corpus under \repolink{tools/xna-oracle/} --- is worth tracing through completely at least once,
because its actual pass/fail mechanics are stricter, and its scope narrower, than ``differential
testing'' alone suggests.

Each scene in the corpus is a small, hand-authored text file. The full corpus, directly recounted
against the checked-in files rather than trusted from an older snapshot (this project's own
``re-verify a stale count'' rule, restated in Chapter~\ref{ch:what-is-cna}), currently holds
39 scenes under \repolink{tools/xna-oracle/scenes/}. \repolink{colored3d.scene}, already cited in
Chapter~\ref{ch:direct3d-backends} for its \cnaclass{BasicEffect} content, is short enough to
show in full:

\begin{lstlisting}[style=cnashell]
width=256
height=256
profile=HiDef
clearcolor=100,149,237,255
vertexcolor=true
lighting=false
primitive=TriangleList
vertex=-0.6,-0.6,0,255,0,0,255
vertex=0.0,0.7,0,0,255,0,255
vertex=0.6,-0.6,0,0,0,255,255
\end{lstlisting}

\repolink{tools/xna-oracle/CnaOracleRender.cpp} is the one piece of code that turns a scene file
into a pixel buffer, and it is deliberately backend-agnostic: it calls only the public
\cnaclass{Game} / \cnaclass{GraphicsDeviceManager} / \cnaclass{GraphicsDevice} / \cnaclass{SpriteBatch}
surface this book documents everywhere else, with no \verb|#ifdef| branch for any specific
backend. The same source file is compiled twice --- once through real XNA~4.0 under Wine
(producing the checked-in reference PNG under \repolink{tools/xna-oracle/reference/}, captured
once by hand and never regenerated except when a scene's own content changes) and once through
whichever CNA backend is under test. \repolink{scripts/xna-diff.py} then compares the two PNGs
one pixel at a time, taking the \emph{maximum} absolute per-channel delta at each pixel (not an
average, and not a whole-image error metric) and counting how many pixels exceed
\texttt{{-}{-}tolerance}. The default tolerance is \texttt{0}: an exact match, every channel, every
pixel. This is stricter than it may first sound, and the script's own documentation is explicit
about why it can afford to be: on Linux, both the CNA/D3D9 render and the real-XNA reference
render pass through the identical DXVK D3D9-over-Vulkan implementation, so a tolerance-0 diff is
measuring CNA's own correctness against XNA's own D3D9 behavior with no driver-stack difference
between the two sides to launder into the result. \repolink{scripts/run-oracle-corpus-diff.sh}
runs every scene through this comparison and is wired into the real \cnaclass{CTest} suite as
\texttt{D3D9\_XNA\_Diff} --- a genuine, permanently-enforced gate, not a one-time measurement, and
the project's own script comments say plainly that widening the tolerance to turn a red result
green ``is exactly how an authenticity project quietly becomes a parity project.''

\section{A measurement that deliberately is not a gate}

Not every comparison this project runs is meant to become a permanent CTest, and the corpus's
own cross-backend EasyGL measurement is a useful, honestly-documented example of the opposite
choice. \repolink{scripts/run-oracle-corpus-diff-easygl.sh} runs the identical scene corpus and
the identical tolerance-0 \repolink{xna-diff.py} comparison through
\repolink{tools/xna-oracle/CnaOracleRender.cpp} recompiled natively against the EasyGL backend
instead of D3D9-over-Wine --- reusing, unmodified, both the renderer and the reference images the
D3D9 gate already depends on. As of the measurement recorded in
\repolink{docs/d3d9-divergence-report.md} (against the 31-scene corpus checked in at the time; the
corpus has since grown to the 39 scenes counted above, so this specific pass/fail split is a
historical snapshot rather than a currently-reproduced number), the result was 10 of 31 scenes
pixel-perfect and 21 of 31 diverging at tolerance~0 --- every \cnaclass{SpriteBatch} scene passed
exactly, while triangle-rasterized scenes mostly did not.

The project's own explanation for why this was never promoted to a CTest the way the D3D9 gate
was is the more important finding than the raw pass count: EasyGL renders through an entirely
different GPU API and driver stack (OpenGL via Mesa, versus D3D9-over-DXVK-over-Vulkan for both
sides of the D3D9 comparison), so a tolerance-0 diff here cannot isolate a CNA correctness bug
from an ordinary rasterizer-implementation difference between two unrelated GPU drivers --- the
same confound the D3D9 methodology goes out of its way to rule out by keeping both sides of that
comparison on the identical DXVK stack. Rather than discard the measurement or silently widen the
tolerance until it passed (the one move the project's own script comments explicitly forbid), the
21 divergent scenes were histogrammed by their differing-pixel pattern instead of reported as one
flat failure count, and three distinct shapes emerged. Pattern A, 17 scenes, differs only in a
thin band of pixels at a primitive's silhouette edge with a bit-exact interior --- a rasterizer
fill-rule/pixel-center convention difference between Mesa/RADV and DXVK, not a shading bug. Five
of those seventeen are scenes deliberately built to expose CNA's per-pixel-vs-XNA's-default-
per-vertex lighting divergence (Chapter~\ref{ch:stock-effects} covers the same design decision),
but each uses a spatially uniform normal across the whole primitive, so per-pixel and per-vertex
evaluation are mathematically identical for them --- structurally incapable of detecting the gap
they were meant to probe, the same trap Chapter~\ref{ch:direct3d-backends} names for a different
scene. Pattern B, 2 scenes (\repolink{colored3d} itself among them), is whole-primitive but
imperceptible: interior pixels differ by 1--2 per channel almost everywhere, consistent with
ordinary GPU/driver floating-point rounding rather than a bug, with the same edge effect as
Pattern A layered on top at the silhouette. Pattern C, 2 scenes, is the measurement's real payoff:
\repolink{fog\_gradient\_quad} rendered as solid black across the entire primitive where real XNA
produces a smooth white-to-black gradient, and \repolink{envmap\_fresnel\_quad} rendered nearly
flat where real XNA produces a smooth per-vertex Fresnel gradient --- both genuine, large,
whole-primitive EasyGL bugs, confirmed as EasyGL-backend-local because the same two scenes render
correctly (0 differing pixels) through the D3D9 side of the identical corpus. Both are now fixed
in current source, as Chapter~\ref{ch:easygl-backend} documents in full. None of the 21 were
investigated further under this specific task, by design --- its own scope was ``record the
deltas,'' not ``fix them'' --- and each was logged with its evidence for whoever picked up the
corresponding \repolink{plan\_graphics.md} item next, which is exactly how Pattern C's two bugs
were later closed.

The methodological lesson generalizes beyond this one measurement: a pixel-diff tool with a fixed
numeric tolerance answers ``do these two images match,'' not ``is this backend correct,'' and the
gap between those two questions is exactly the shared execution stack (or its absence) between
whatever two things are being compared. The D3D9 oracle can afford tolerance~0 as a blocking gate
because both sides share DXVK; EasyGL cannot, so the same tool is reused for insight without being
promoted to a gate that would otherwise be measuring Mesa against DXVK rather than CNA against
XNA.

\section{What this means for a reader of this book}

If you are choosing a target platform for a new CNA project, or evaluating CNA for a port,
this table is the single fact most likely to change your plan: build success and behavioral
correctness are two different claims, verified to different degrees on different platforms,
and this ecosystem's own documentation is careful --- and this book has tried to be equally
careful --- to say which one it means every time it makes one. Treat a Linux-verified claim as
the strongest evidence available in this project today; treat a Windows claim as strong but
not hardware-final; and treat a Web or Android graphics claim as, at best, ``compiles,'' until
someone actually runs it where you intend to ship it.
