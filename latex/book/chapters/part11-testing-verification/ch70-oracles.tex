\chapter{Oracles: What Does ``Correct'' Mean?}
\label{ch:oracles}
\label{ch:testing-philosophy}

Almost every specific number and bug this book has cited across both volumes came from one
of a small number of testing mechanisms. This chapter gathers them into one place, because
seen individually they are backend-specific facts, but seen together they are a coherent
testing philosophy worth naming explicitly.

\section{The base layer: GoogleTest, at real scale}

CNA's own unit and integration suite (\texttt{CnaTests}) runs to roughly 4{,}370 tests at the
scale referenced throughout this book, plus a separate GPU pixel-test suite of roughly 490
tests across the four backends mature enough to support it. \texttt{sharp-runtime}, the
foundation layer covered in Chapter~\ref{ch:sharp-runtime-overview}, runs a suite of its own
numbering in the thousands. None of this is exotic --- GoogleTest, run through CTest --- but
the scale matters for what it makes possible: a change that regresses one backend's behavior
without touching another's has somewhere to actually surface.

\section{Pixel tests: the level where most of this book's bugs were actually found}

An ordinary unit test can confirm a method returns without crashing, or that a getter returns
what a setter most recently stored --- neither can catch that
\texttt{transformMatrix} was silently ignored by \cnaclass{SpriteBatch::Begin()}
(Chapter~\ref{ch:sdl-renderer}), or that a Vulkan blend-state implementation applied one
hardcoded equation regardless of what was requested (Chapter~\ref{ch:vulkan-backend}). Both
of those --- and the substantial majority of the specific, named bugs in this book's Part~IV
and Part~III chapters --- were only found by a pixel test: rendering a real frame and reading
real pixel values back, then asserting on the actual color, not merely on the absence of a
crash. This is the level at which CNA's own house style Chapter~\ref{ch:design-philosophy}
described bites hardest: a stub that silently drops a parameter compiles cleanly, passes a
crash-only test, and only fails once something reads the pixels it was supposed to affect.

\section{A worked pixel test, in the shape that actually found the bug}

The \texttt{transformMatrix} finding above is worth seeing in the actual test's own shape, not
just its conclusion, because the shape itself is the reusable lesson: draw something whose
final screen position depends entirely on the value under test, then read back specific pixels
and assert on their real color. \texttt{examples/sdlrenderer\_transform\_matrix\_test.cpp}
does exactly this for \cnaclass{SpriteBatch::Begin()}'s \texttt{transformMatrix} parameter on
the \texttt{SDL\_RENDERER} backend:

\begin{lstlisting}
// Translate every sprite by (+100, +50).
Matrix tx = Matrix::CreateTranslation(100.0f, 50.0f, 0.0f);

sb_->Begin(SpriteSortMode::Deferred, BlendState::Opaque,
           const_cast<SamplerState*>(&SamplerState::PointClamp),
           nullptr, nullptr, nullptr, tx);

// Draw a 1x1 red sprite at (0,0) -- a correct transform moves it to (100,50).
sb_->Draw(*redTex_, Vector2(0.0f, 0.0f), Color::White);
sb_->End();

// Read back real pixels, not the value a getter reports.
Color got(0, 0, 0, 0);
Rectangle reg(100, 50, 1, 1);
dev.GetBackBufferData(&reg, &got, 0, 1);
const bool ok = colourMatch(got, kRed);   // FAILS if transformMatrix was silently ignored
\end{lstlisting}

\texttt{SpriteEffects::FlipHorizontally}, applied to a second sprite under the same transform,
is the other half of the real test: it confirms the affine flip-and-transform combination
works together, not just plain translation in isolation, bringing the total to four checked
coordinates. The core mechanism, though, is this one pair: draw at a position that is only
correct if the transform was actually applied, then read the screen back at exactly that
position. No getter, no internal state inspection, and no assumption that a parameter which
was accepted was also used --- only the pixel a real player would actually see.

\section{Differential testing: a real reference, not a specification}

Chapter~\ref{ch:what-is-cna} named this as one of CNA's three most distinctive verification
mechanisms, and it is worth restating precisely here: \texttt{tools/fna-reference/} compares
CNA's behavior against a genuinely running FNA installation, not against a written
description of what FNA is supposed to do. This distinction mattered concretely in
Chapter~\ref{ch:media-system}'s \cnaclass{Song} finding --- eight audit rounds diffed against
FNA's own source and missed a real gap, because FNA's source was itself missing something
relative to the true XNA~4.0 reference. A specification, however carefully read, only tells
you what its author believed to be true; a running reference implementation tells you what
actually happens.

\section{The oracle: pixel-for-pixel against real XNA itself}

\texttt{D3D9}'s own verification, covered in full in Chapter~\ref{ch:direct3d-backends}, goes
one level further still: not a comparison against FNA, but against a genuine, running XNA~4.0
runtime, diffed at zero tolerance across a corpus that has kept growing across this book's own
successive passes --- 31 scenes, then 36, and 39 real scene files on disk as of this book's
own most recent check, every one added only once independently confirmed to diverge nowhere
from real XNA at zero tolerance. This is the strictest bar in the entire project, and it is
worth remembering that it caught two real bugs neither differential-against-FNA testing nor
ordinary pixel tests had caught: the sort-mode Z-clipping bug and the
\cnaclass{GraphicsProfile}-never-reaches-the-device bug, both covered in
Chapter~\ref{ch:direct3d-backends}.

\section{Compile-time purity: NOXNA as a build gate}

Not every verification mechanism in this project runs at test time. The \texttt{NOXNA} build
option (Chapter~\ref{ch:design-philosophy}) turns every untagged non-XNA declaration inside
the XNA namespace tree into a \texttt{[[deprecated]]} warning under \texttt{-Werror} ---
catching a specific class of drift (a project-specific extension silently leaking into the
public, supposedly XNA-faithful surface) at compile time, before a single test ever runs.

\section{Sanitizers, and where they are used}

Memory-safety and undefined-behavior sanitizers are used deliberately, not universally.
\texttt{free-direct} (Chapter~\ref{ch:freedirect-deep-dive}) has a dedicated, opt-in sanitizer
build configuration verified clean across its own full test suite, including in combination
with its optional ENet networking transport. \cnans{Microsoft::Devices::Sensors}
(Chapter~\ref{ch:devices-sensors}) had a genuine data race found by exactly this kind of
tooling --- an unguarded read of a disposal flag from a background sensor-event thread --- and
a later signed-integer-overflow bug in its own update-throttling logic was confirmed
specifically under UndefinedBehaviorSanitizer, not by inspection. Sanitizer coverage in this
project is targeted at the specific subsystems where genuine concurrency or native-interop
risk exists, rather than blanket-applied everywhere.

Two further, independent instances make the same point from different corners of this
ecosystem. \texttt{sharp-runtime} (Chapter~\ref{ch:sharp-runtime-namespaces})'s first-ever full
run of the complete sanitizer trio found real bugs no amount of prior code review had caught:
ThreadSanitizer found a genuine production deadlock (a \cnaclass{Channel} implementation
missing a \texttt{notify\_all} call, a real lost-wakeup affecting multiple blocked waiters),
AddressSanitizer found a confirmed heap-buffer-overflow in an aligned-reallocation helper, and
UndefinedBehaviorSanitizer found a genuine UB call reaching into vendored \texttt{miniz} code
from an empty vector's \texttt{.data()} pointer. And the Android sensor bridge
(Chapter~\ref{ch:android-ndk})'s own concurrency fix --- already reviewed, tested, and marked
closed --- still hid a second, deeper race that only a dedicated, later \texttt{devices-tsan}
run under real 8-thread concurrent load actually surfaced, cascading into genuine heap
corruption in a test fixture's own callback bookkeeping. Both are the same lesson from the
opposite direction of the sensor-flag race above: a fix that looks complete after careful
manual reasoning can still hide a real, low-probability race that only a sanitizer run under
genuine concurrent load will find, which is precisely why this project treats a sanitizer pass
as something to re-run against new concurrency-sensitive code, not a one-time gate a subsystem
passes once and never revisits.

\section{What CI actually covers, stated honestly}

Chapter~\ref{ch:building-cna} already gave this fact once, and it is worth
repeating here in its proper context: automated CI for this project is Linux-only and
partial, running only the Input and Devices/Sensors suites at the time of writing --- not the
full unit suite, and not the GPU pixel-test suite across any backend. Every Graphics-layer
claim in this entire book rests on suites run locally and by hand, not on a green CI badge.
There is no Windows, macOS, or Android CI at all; the Windows-targeting backends in
Chapter~\ref{ch:direct3d-backends} are verified through the Wine-based dev loop covered in
this Part's cross-platform chapters, and Android is verified against a real emulator by hand,
not automatically on every commit. This is not a criticism the project hides --- it is stated
plainly in its own README --- and it is the reason this book has consistently distinguished
``verified locally, by a specific mechanism, on a specific date'' from ``covered by CI,''
rather than treating the two as interchangeable.

\section{The golden-image workflow: regenerate, review, commit}

\texttt{CompareGoldenImage()} (\texttt{examples/common/PixelTestGame.hpp}), the shared helper
behind every golden-image test this book has cited, is worth reading for its own workflow
philosophy, not just its comparison logic. Its own header comment states the intended process
directly, and it is a real, three-step discipline rather than an implementation detail:

\begin{lstlisting}
// Set the CNA_UPDATE_GOLDEN environment variable to any non-empty value to
// instead (re)write goldenPath from the current live render and report
// [UPDATE] -- the intended workflow for an intentional rendering change: run
// once with CNA_UPDATE_GOLDEN=1 to regenerate the reference, review the new
// file with `git diff`/an image viewer, then commit it; every subsequent run
// without the env var compares against it normally.
\end{lstlisting}

The order matters as much as the mechanism: regenerate, \emph{then look at what changed}, then
commit --- never regenerate-and-commit in one motion, since that would silently launder a real
regression into the reference itself, permanently hiding it from every future comparison. A
golden-image diff failing is deliberately ambiguous by design between two very different
outcomes (an intentional rendering change the reference hasn't caught up to yet, or a real
regression), and this workflow's whole point is forcing a human decision at exactly that
ambiguity rather than automating past it in either direction.

The same helper's own comment on \texttt{tolerance} is worth citing directly too, because it
is a concrete, numbered finding rather than a general caveat: ``Exact pixel-perfect reproduction
across this project's 4 backends/drivers is already known unreliable (Task 462's own 98-file
tolerance survey) --- pass a non-zero tolerance for any golden image that isn't a single flat,
unblended colour.'' This is the same underlying fact Chapter~\ref{ch:verification-methodology}'s
own D3D9 oracle corpus treats as a hard boundary in the opposite direction: the oracle's
zero-tolerance comparison is defensible specifically \emph{because} both sides of it run through
the identical Wine+DXVK stack, eliminating the driver-level noise a tolerance value exists to
absorb everywhere else. A tolerance of zero is not a stricter version of a nonzero tolerance in
this project --- it is a claim about the comparison's own architecture, only true where that
architecture actually holds.

\section{A CI-only test class: skipping itself honestly instead of being silently excluded}

Chapter~\ref{ch:building-cna} and the section above already named CI's own real, partial scope.
Reading the workflow file
\texttt{.github/\allowbreak{}workflows/\allowbreak{}devices-tests.yml} directly shows a
smaller, worth-naming design choice inside that scope: two tests genuinely need real
accelerometer/gyroscope hardware neither this project's CI runners nor most developer
machines have --- and rather than
excluding them from the CI test filter (the more common approach, and the one that makes a
hardware-only test invisible in a CI run's own output), the workflow's own header comment
states the alternative directly:

\begin{lstlisting}
// The two tests that genuinely require real hardware
// (AccelerometerTests.GetCurrentValuePropertyDoesNotThrowWhenSupported,
// GyroscopeTests.GetCurrentValuePropertyDoesNotThrowWhenSupported) are not
// excluded from the filter; they are written to self-skip via GTEST_SKIP()
// when getIsSupportedProperty() is false, which is always the case on a CI
// runner with no accelerometer/gyroscope, so they show up as "SKIPPED"
// rather than needing a separate hardware-only filter.
\end{lstlisting}

The distinction is small mechanically but real in what it communicates: a test filtered out of
a CI run leaves no trace in that run's own results at all, while a test that reaches
\texttt{GTEST\_SKIP()} appears explicitly, every run, as skipped --- a standing, visible
reminder that a hardware-dependent check exists and genuinely was not run here, rather than a
silent gap a future reader of CI output would have no way to notice. The same two tests would
run for real, not skip, on a developer's own machine with the relevant sensor physically
present --- the \texttt{GTEST\_SKIP()} branches on \texttt{getIsSupportedProperty()}, the
platform's own real capability query, not on a hardcoded CI-only flag.

Input CI (\texttt{.github/workflows/input-ci.yml}) shows the same "state real coverage
honestly" instinct from a different angle: its own matrix runs the backend-agnostic input
suite headless across four graphics backends (\texttt{EASYGL}, \texttt{SDL\_RENDERER},
\texttt{VULKAN}, \texttt{BGFX}), plus a dedicated AddressSanitizer+UndefinedBehaviorSanitizer
configuration on \texttt{EASYGL} specifically --- a concrete instance of this chapter's own
earlier claim that sanitizer coverage in this project is targeted, not blanket: one backend
carries the sanitizer burden for the whole input subsystem, chosen rather than applied
everywhere, exactly the deliberate-not-universal posture this chapter's own sanitizer section
already established for \texttt{free-direct} and \cnans{Microsoft::Devices::Sensors}.

\section{The throughline}

Every mechanism in this chapter answers the same underlying question from a different angle:
\emph{how do we know this is actually true, rather than merely believed to be true?} A unit
test answers it for logic in isolation. A pixel test answers it for what actually reaches the
screen. Differential testing against FNA answers it against a real, if imperfect, reference.
The D3D9 oracle answers it against the most authoritative reference available at all. The
\texttt{NOXNA} build gate answers a narrower, structural version of the question before any
of the others even run. None of these mechanisms alone would have caught every bug this book
has named across both volumes --- it is the combination, applied unevenly and honestly
according to what each subsystem actually needed, that this chapter's title refers to as a
philosophy rather than a single technique.
