\chapter{Web and DOM Renderers}
\label{ch:web-dom-renderers}
\label{ch:canvas-ascii-backends}

These two renderers share a family resemblance --- both are 2D-only, in the same spirit as
\texttt{SDL\_RENDERER} --- but arrive there by opposite routes: \texttt{CANVAS} replaces
SDL's own rendering entirely with a browser API, while \texttt{ASCII} is, quite literally, a
thin decorator wrapped around \texttt{SDL\_RENDERER}'s own real implementation.

\section{CANVAS: real code, an honest verification ceiling}

\texttt{CANVAS} is Emscripten-only, targeting the HTML \texttt{CanvasRenderingContext2D} API
(\texttt{drawImage} / \texttt{putImageData} / \texttt{fillRect}) instead of SDL3's own 2D blit
API. The single fact that qualifies every other claim in this section: this project's own
development environment has \emph{no real browser and no real DOM}. The \texttt{node}
runtime that executes this renderer's compiled test suite provides no
\texttt{CanvasRenderingContext2D} at all, and \texttt{SDL\_Init(SDL\_INIT\_VIDEO)} itself
throws under Emscripten running in \texttt{node} --- confirmed directly, not assumed. Every
checkmark in this renderer's own documentation therefore means ``implemented, code-reviewed,
and passing structural (non-pixel) test coverage,'' not ``pixel-verified in a real browser''
--- a narrower claim than every renderer in the previous chapters, and stated as such rather
than blurred.

\subsection{Five real bugs found in an external review, before any real browser existed to test in}

An external code review found and fixed five distinct bugs purely by reasoning about Canvas
2D compositing semantics against the CSS Compositing specification, without ever running the
code in a browser:

\begin{enumerate}
  \item \cnaclass{BlendState.Opaque} cleared the \emph{entire} canvas, not just the drawn
        sprite --- a direct consequence of using \texttt{globalCompositeOperation = 'copy'}
        with no clip region, which wipes everything outside the shape actually drawn, per the
        Porter-Duff \texttt{copy} operator's own definition. Fixed by clipping to the exact
        drawn rectangle before compositing.
  \item \texttt{AlphaBlend} and \texttt{NonPremultiplied} were treated as identical, on the
        original reasoning that this renderer's own textures are never genuinely
        premultiplied --- an assumption that does not hold project-wide, since
        \texttt{SDL\_RENDERER}'s own test suite deliberately constructs premultiplied test
        data. Fixed with a real per-pixel un-premultiply pass applied only to the
        \texttt{AlphaBlend} case.
  \item RGB tint visibly darkened or lightened semi-transparent edges, traced to an
        alpha-squared error in the original multiply-plus-destination-in compositing trick,
        confirmed wrong against the CSS Compositing specification's own blend formula. Fixed
        with a direct per-pixel RGB multiply that leaves the alpha channel untouched.
  \item Invalid combinations of wrap/mirror address modes were silently skipped rather than
        raising an error --- a direct contradiction of this project's own ``throw rather than
        guess'' convention (Chapter~\ref{ch:design-philosophy}). Fixed by moving the
        validation into C\texttt{++} itself, throwing a real \texttt{std::runtime\_error}
        before the call ever reaches JavaScript at all.
  \item A cached mirrored-tile pattern was never invalidated after a pixel update --- fixed
        in two separate passes, first for an explicit \texttt{Texture2D::SetData} call, then
        again for the case of a bound \cnaclass{RenderTarget2D} whose pixels change through
        direct draws while still bound, a path that never goes through \texttt{SetData} at
        all and so was missed by the first fix.
\end{enumerate}

A closely related sixth fix: \texttt{Clear()} was blending against old canvas content under a
leftover composite mode, and permanently reset the canvas transform rather than
saving/restoring it --- both corrected together.

\subsection{Not-fully-native features, honestly labeled}

\texttt{Wrap} addressing uses a repeating \texttt{ctx.createPattern} canvas pattern, applied
only when the source rectangle actually exceeds the texture's bounds;
\texttt{Mirror} uses a lazily-built, cached $2\times2$ pre-tiled mirrored canvas. Both carry
the same real-browser verification caveat as everything else in this section. Mixed per-axis
combinations (wrap on one axis, mirror or clamp on another) throw by design, per the fix
above.

\subsection{A worked example: the un-premultiply pass, in real numbers}

The \texttt{AlphaBlend} / \texttt{NonPremultiplied} fix above (bug~2) is worth the same
hand-computed treatment the ASCII renderer's own quantizer gets below, since the actual
per-pixel formula --- read directly from \texttt{CanvasSpriteBatchRenderer.cpp}'s own
Canvas-2D-side pixel loop --- is small enough to verify by hand. A half-transparent, dark-red
premultiplied source pixel, $\text{RGBA} = (64, 32, 16, 128)$ (alpha $\approx 50\%$), is the
kind of value \texttt{SDL\_RENDERER}'s own test suite deliberately constructs, per the bug's
own root-cause description above:

\begin{lstlisting}
const inv = 255 / aa;              // aa = 128 here -> inv = 1.9921875
rr = Math.min(255, rr * inv);      // 64 * 1.9921875 = 127.5
gg = Math.min(255, gg * inv);      // 32 * 1.9921875 = 63.75
bb = Math.min(255, bb * inv);      // 16 * 1.9921875 = 31.875
// alpha (aa = 128) is read and written back completely untouched;
// data[] is a Uint8ClampedArray, so each float above is rounded/clamped to a byte on assignment
\end{lstlisting}

The un-premultiplied result, $\approx(128, 64, 32, 128)$, is close to double the original
channel values --- the pixel's true, alpha-independent color, exactly what a
\texttt{NonPremultiplied}-style source already stores directly, and exactly
why treating the two blend modes as identical (the original, buggy assumption) silently
darkened every partially-transparent \texttt{AlphaBlend} pixel by roughly the same factor as
its own alpha: without the \texttt{inv} multiply, the raw premultiplied RGB $(64,32,16)$ would
have been drawn as though it were the pixel's real, full-brightness color, when the true color
is nearly twice as bright in each channel. \texttt{Math.min(255, \ldots{})} is not a decorative
safety clamp either --- it is load-bearing for any source alpha below 128, where
\texttt{inv} exceeds 2 and an already-bright channel value can genuinely overflow past 255
before clamping.

\subsection{What real browser verification would still require}

The renderer's own documentation includes a full thirteen-item manual browser verification
checklist --- explicitly left entirely unchecked, described as ``the closest honest
equivalent to SDL\_RENDERER's own pixel-verified completeness table,'' pending a human
running it in a real browser (for instance via Emscripten's \texttt{emrun}).

\section{The former ASCII renderer: historical architecture}

\begin{sourcenote}
\textbf{Edition update.} The renderer described in this section has been removed as a public
identity. Its reusable quantizer and glyph-grid presentation logic now live in the
renderer-neutral \cnaclass{CNA::Graphics::AsciiPostProcessEffect} under
\texttt{modules/graphics-ext}; Appendix~\ref{ch:cnaext-catalog} covers the current surface. The
remaining discussion records the predecessor's design and evidence, not a selector available
in the current 46-identity / 42-family registry.
\end{sourcenote}

\texttt{ASCII} is not a real terminal or TTY renderer --- it renders inside an ordinary SDL
window, exactly like \texttt{SDL\_RENDERER}, and is architecturally, in the project's own
words, ``a thin decorator around SDL\_RENDERER's own \texttt{SdlRenderer}.'' A game
draws normally into a private offscreen target; \texttt{Present()} reads that frame back,
quantizes it into a grid of glyph-plus-color cells, and draws the resulting grid onto the
real window using the internal \cnaclass{ISpriteBatchRenderer} / \cnaclass{ITextureRenderer}
pair directly --- deliberately \emph{not} going through the public \cnaclass{SpriteFont} API,
consistent with the project's own rule that renderer internals stay below, and hidden from,
the public XNA-facing API surface.

\subsection{A genuinely distinctive claim: no blocked decisions, no environment gate}

This renderer's own completeness documentation makes a claim none of the others in this
chapter or the previous ones can: ``no BLOCKED section and no \texttt{needs\_human} gate
anywhere --- every row below is automated and pixel-verified in this dev environment\ldots
including real-window \texttt{Present()} output.'' Because it inherits \texttt{SDL\_RENDERER}'s
own implementation wholesale for everything a game actually draws --- \cnaclass{SpriteBatch},
\cnaclass{Texture2D}, \cnaclass{SpriteFont}, \cnaclass{BlendState}, \cnaclass{SamplerState},
render targets --- it also inherits that renderer's entire, exhaustively-verified completeness
table transparently, without needing to repeat it. The one partial exception:
\texttt{SetRenderTarget(nullptr)} is intercepted and redirected to the private game-target
buffer rather than the literal window backbuffer, ``so the game can never accidentally draw
straight onto the real window.''

\subsection{A separate renderer, not a toggle --- and why that was a genuinely close call}

\texttt{plan\_ascii.md}'s own design-decisions section records an alternative that was seriously
considered and explicitly not dismissed out of hand: implementing this entire feature as a
runtime toggle or \texttt{CNAEXT} extension directly on \texttt{SDL\_RENDERER}, instead of a
separate, selectable \texttt{CNA\_GRAPHICS\_RENDERER} value. The architectural case for the
toggle is real, not a straw man --- \texttt{ASCII} \emph{is}, structurally, ``\texttt{SDL\_RENDERER}
plus a present-time filter,'' per the same document's own framing: every draw call a game issues
forwards to a live \texttt{SdlRenderer} instance unmodified, and the only genuinely new
code this renderer contributes at all is a replacement \texttt{Present()}. A single boolean flag
on the existing renderer could, in principle, have delivered the identical behavior with strictly
less code --- no new CMake option, no new entry in \texttt{RendererSelection.cmake}'s
\texttt{STRINGS} list, no additional value in the then-current catalog for a reader of
Chapter~\ref{ch:backend-architecture}
to learn.

The plan's own recorded reasoning for choosing the heavier option anyway is worth stating
precisely, since it is a judgment call about discoverability rather than a technical constraint:
``discoverability and consistency with how this project already exposes renderer choice.'' A
build with \texttt{CNA\_GRAPHICS\_RENDERER} set to the former \texttt{ASCII} value was a single,
obvious CMake flag any reader of this
book's own Chapter~\ref{ch:building-cna} already knows to look for; a correct-but-buried
\texttt{SDL\_RENDERER}-plus-an-environment-variable combination is not discoverable the same
way, and would have made this renderer read as an undocumented mode of another renderer rather
than a first-class, named part of the project's own former renderer catalog. The plan document
does not present this as a closed question, either --- it explicitly flags the toggle as ``a
real, low-cost alternative worth revisiting if a toggle turns out to be more convenient in
practice,'' rather than retroactively justifying the decision actually shipped as though it were
the only reasonable one. Treating a design document's own hedged uncertainty honestly, rather
than smoothing it into false confidence after the fact, is the same discipline
Chapter~\ref{ch:project-practice} asks of every dated claim this book reproduces.

\subsection{The quantizer, and a deliberately hand-authored font}

Glyph selection works by standard luminance ranking (the usual $0.299R + 0.587G + 0.114B$
formula), mapped onto a ten-character density ramp (\texttt{" .:-=+*\#\%@"}) by linear rank ---
verified to be strictly increasing in visual density. Two runtime modes,
\texttt{BLACKWHITE} and \texttt{COLOR}, are selected via the \texttt{CNA\_ASCII\_MODE}
environment variable, with a runtime-configurable cell size (default $8\times8$) via
\texttt{SetCellSize()} / \texttt{GetCellSize()}. The glyph font itself is a deliberate,
hand-authored $8\times8$ pixel bitmap for exactly the ten ramp characters --- explicitly not
a vendored font file or classic code-page glyph set, a choice made specifically to avoid
introducing any new asset or license dependency at all. A dirty-cell diffing optimization is
explicitly not implemented, and explicitly not treated as a correctness gap either --- left
for later only if performance ever actually demands it.

\subsection{A worked example: from one pixel to one glyph}

The quantizer's own formula and ramp are precise enough to walk through by hand for a single
pixel, which makes the mapping concrete rather than only described:

\begin{lstlisting}
// A mid-brightness orange pixel, e.g. sampled from a sprite:
Color pixel(230, 126, 34, 255);

float luminance = 0.299f * pixel.R + 0.587f * pixel.G + 0.114f * pixel.B;
// = 0.299*230 + 0.587*126 + 0.114*34 = 68.77 + 73.96 + 3.88 = 146.6

const char* ramp = " .:-=+*#%@";       // 10 characters, index 0 = darkest
int rampIndex = static_cast<int>(luminance / 255.0f * 9.0f); // = 5 -> '+'
char glyph = ramp[rampIndex];
\end{lstlisting}

A luminance of 146.6 out of 255 (roughly 57\%) lands on \texttt{'+'}, the sixth character in
the ten-character ramp --- not the visual midpoint of the string by character count, but by
the ramp's own \emph{verified-strictly-increasing} visual density, which is exactly the
property the chapter's own verification claim rests on. A pure white pixel
(\texttt{luminance=255}) maps to index 9, \texttt{'@'}, the densest glyph; pure black maps to
index 0, a plain space --- background, rendered as the visual absence of any glyph at all,
which is also precisely why the \texttt{BlendState.AlphaBlend} bug above was so easy to miss
purely by inspection: a background that fails to alpha-blend and an intentionally-empty
space-character cell can look identical in a screenshot.

\subsection{One real, found-and-fixed bug}

Background fills plus glyph tinting never actually went through
\texttt{GraphicsDevice.BlendState} at all, so the underlying SDL renderer's blend mode
defaulted to a non-alpha-aware mode --- background fills were effectively invisible, because
an ``off'' glyph pixel simply overwrote the background with whatever raw black RGB value it
stored. Fixed by forcing the real \texttt{AlphaBlend} preset's factors before every grid draw,
independent of whatever \cnaclass{BlendState} the game itself had set.

\subsection{A methodology finding, not a bug}

Reading pixels back immediately after a real \texttt{Present()} call returns stale or
garbage content, because \texttt{SDL\_RENDERER}/OpenGL present via a genuine double-buffer
swap, not a copy --- there is nothing left to read where the just-presented frame was. The
fix is test-only: a \texttt{DrawQuantizedGridForTesting()} entry point that skips the swap,
paired with a \texttt{Read\allowbreak{}RealBackbuffer\allowbreak{}ForTesting()} accessor --- real game code always goes
through the genuine \texttt{Present()} path, unaffected by either.

\subsection{Input, unmodified}

Input on this renderer required zero new code at all --- verified twice, independently: once
through the existing renderer-agnostic mouse test suite, and once through a new, dedicated
input test written specifically for this renderer, passing in full.

\subsection{Two stored rectangles, only one delegated}

Neither renderer overrides \texttt{SetViewport()}, so a custom public viewport never remaps its
2D output. CANVAS also inherits the empty scissor and rasterizer hooks: both public values are
stored-only. ASCII is asymmetrical because it delegates \texttt{SetScissorRect()} to the inner
SDL renderer but does not delegate \texttt{ApplyRasterizerState()}. The rectangle therefore
clips the off-screen game target before ASCII quantizes it to cells whenever its size is
positive, regardless of the public \texttt{ScissorTestEnable} Boolean; a non-positive rectangle
disables the SDL clip. No dedicated ASCII test currently distinguishes those pixels. This is
composition faithfully inheriting SDL\_Renderer's own state bug, not a separate quantizer rule.

\subsection{Persistent 2D targets, but no presentation-usage policy}

Both products ignore the renderer preserve Boolean yet keep browser-canvas or SDL target
storage persistent. Shared binding therefore makes exact Discard overwrite an explicit 2D
target with black, while Preserve and Platform leave its color alone. ASCII's empty/null bind
is special: it redirects to its private game target, but never consults the presentation
parameter's usage value. Its off-screen test proves a Preserve target survives that redirection;
CANVAS has only source evidence because the native non-Emscripten implementation is a no-op
and no real browser was available. Neither product supports cube targets or MRT. See
\S\ref{sec:backend-rendertarget-usage-matrix}.

\section{Both renderers are 2D-only by explicit design, not by omission}

Every renderer documented in the previous three chapters implements the full renderer interface,
\cnaclass{IGraphicsRenderer}, 3D pipeline included, even where a given hardware
target turns out to have real gaps in that support (Chapter~\ref{ch:backend-architecture}
covers several). \texttt{CANVAS} and \texttt{ASCII} are architecturally different: neither one
\emph{attempts} 3D at all, and this is enforced in code, not merely asserted in prose.

Clear calls illustrate why ``the renderer throws for 3D'' does not automatically describe the
public API. Both products report no depth/stencil support, so
\cnaclass{GraphicsDevice}\texttt{.Clear} masks those bits before dispatch: depth/stencil-only is
a silent FNA-faithful no-op and a target-containing request performs the ordinary colour clear.
Canvas then overwrites the active browser context; ASCII delegates to its SDL-rendered
off-screen target. The direct combination hooks below still throw when tests call the renderer
itself, but public code cannot reach those throws through the masked path
(\S\ref{sec:backend-clear-matrix}).

\subsection{ASCII: a dedicated test proves every 3D entry point throws}

\texttt{AsciiGraphicsBackend} forwards every 3D-pipeline method it does override directly to
the wrapped \texttt{SdlRenderer}'s own existing \texttt{ThrowNo3D()} calls, rather than
re-declaring the same throw logic a second time --- a design decision the renderer's own plan
document (\path{plan_ascii.md}, Phase~G7) records explicitly as ``same net behavior, less
code.'' The dedicated \path{ascii_throwno3d_test.cpp} exists purely to prove this forwarding
is complete and correct, by calling each reachable 3D entry point on a real, live renderer
instance and checking that it actually throws:

\begin{lstlisting}
auto& renderer = static_cast<AsciiGraphicsBackend&>(dev.GetRenderer());

check(Throws([&] { renderer.ClearColorAndDepth(0, 0, 0, 1, 1.0f); }), "ClearColorAndDepth throws");
check(Throws([&] { renderer.SetDepthTestEnabled(true); }),            "SetDepthTestEnabled throws");
check(Throws([&] { renderer.CreateVertexBuffer(3); }),                "CreateVertexBuffer throws");
check(Throws([&] { renderer.CreateOcclusionQuery(); }),                "CreateOcclusionQuery throws");

check(!renderer.SupportsDepthStencil(), "SupportsDepthStencil() is false");
check(renderer.CreateTexture3D(4, 4, 4, false, 0) == nullptr, "CreateTexture3D returns nullptr");
\end{lstlisting}

Seventeen checks in total cover three distinct failure shapes rather than one uniform rule.
Twelve directly-reachable entry points throw a real \texttt{std::runtime\_error}:

\begin{itemize}
  \item the six \texttt{Clear*} overloads;
  \item \texttt{SetDepthTestEnabled}, \texttt{SetBlendEnabled}, and
        \texttt{SetDepthWriteEnabled};
  \item \texttt{CreateVertexBuffer}, \texttt{CreateIndexBuffer16}, and
        \texttt{CreateOcclusionQuery}.
\end{itemize}

\texttt{SupportsDepthStencil()} instead returns \texttt{false}, since it is a capability query,
not an action (the same ``ask, don't catch'' shape Chapter~\ref{ch:sdl-renderer} documents for
\texttt{SDL\_RENDERER}'s own \texttt{SupportsCapability} overrides). Four other factories
return \texttt{nullptr}:

\begin{itemize}[nosep]
  \item \texttt{CreateTexture3D};
  \item \texttt{CreateTextureCube};
  \item \texttt{CreateRenderTargetCube};
  \item \texttt{CreateEffectRenderer}.
\end{itemize}

None has an ASCII-specific override. All four fall through to the shared base-class defaults,
which already return \texttt{nullptr}, so adding local overrides would only duplicate
behavior the base class already provides for free.

There is one important exception to that otherwise honest query behavior:
\texttt{AsciiGraphics}\allowbreak\texttt{Renderer} also never overrides the public
\texttt{SupportsCapability(GraphicsCapability)} method, whose shared default returns
\texttt{true}. It therefore reports \texttt{true} for five unsupported entries.
\texttt{ThreeD}, \texttt{CustomEffects}, and \texttt{OcclusionQuery} are three.
The two state entries --- \texttt{MultiSample}\allowbreak\texttt{AntiAliasing} and
\texttt{Anisotropic}\allowbreak\texttt{Filtering} --- are the other two.
The calls above prove that 3D operations throw, the custom-effect
factory returns \texttt{nullptr}, and the query factory forwards to SDL renderer's throw.
The two state paths are equally concrete.
\texttt{ApplyMultiSample}\allowbreak\texttt{Count} forwards to SDL renderer's explicitly
always-zero implementation. ASCII has no
\texttt{ApplySampler}\allowbreak\texttt{State} override at all, so it inherits the base no-op
instead of forwarding sampler state to its inner renderer. The internal
\texttt{SupportsDepthStencil()} check in the test is truthful; the public capability enum
currently is not for these five entries. Chapters~\ref{ch:graphicsdevice}
and~\ref{ch:backend-architecture} show the required caller-side guard.

The test deliberately does \emph{not} exercise three further methods:

\begin{itemize}[nosep]
  \item \texttt{DrawColoredPrimitives};
  \item \texttt{DrawIndexedColoredPrimitives};
  \item \texttt{DrawInstancedPrimitivesEx}.
\end{itemize}

Its own comments explain why honestly rather than silently skipping them: each needs a real
vertex-buffer renderer reference, but \texttt{CreateVertexBuffer} and
\texttt{CreateIndexBuffer16} already throw (Checks~J/K above), so no real vertex or index
buffer can ever exist on this renderer to construct that argument with. They are structurally
unreachable via any real call path a game could take, not merely untested by omission ---
confirmed correct by code review instead, since all three forward to the same wrapped inner
renderer with the identical one-line pattern as every other method in the file.

\subsection{CANVAS: the identical contract, without a dedicated test}

\texttt{CanvasRenderer} follows the exact same shape, documented directly in its own
header rather than in a standalone test file: the ``inherently-3D-only pure virtuals'' ---
\texttt{ClearColorAnd\allowbreak{}Depth} and its five siblings, the vertex/index buffer factories,
\texttt{DrawColoredPrimitives} --- throw via \texttt{ThrowNo3D()}, while the remaining
3D-only surface (\texttt{Draw*Ex} / \texttt{DrawInstanced\allowbreak{}PrimitivesEx},
\texttt{CreateIndex\allowbreak{}Buffer32}) is left on
\cnaclass{IGraphicsRenderer}'s own shared defaults, as are the five factories for
\texttt{Texture3D}, \texttt{TextureCube}, \texttt{RenderTargetCube},
\texttt{OcclusionQuery}, and \texttt{EffectRenderer}. The header comment names its own
precedent directly: this is ``confirmed against \texttt{SDL\_RENDERER}'s own precedent of
not overriding these either (Phase~C7)'' --- the same reasoning \texttt{SDL\_RENDERER} itself
established first, that \texttt{ASCII} then reused by wrapping \texttt{SDL\_RENDERER}
verbatim, and that \texttt{CANVAS} arrived at independently for its own, unrelated
implementation. Three separate renderers, two of them with no code relationship to each other
at all, converge on one shared answer for exactly the same reason: reimplementing a throw the
base class already provides for free would be new code with no new behavior.

Unlike \texttt{ASCII}, no dedicated \texttt{canvas\_throwno3d\_test.cpp} exists to exercise
this behavior end-to-end against a live instance --- the claim rests on the header's own
design-rationale comment plus code review, not on an executed test, a narrower verification
claim consistent with the rest of this renderer's own ``structural, not pixel-verified''
ceiling described earlier in this chapter. A future session adding one would only need to
port \texttt{ascii\_throwno3d\_test.cpp}'s own pattern across, substituting
\texttt{CanvasRenderer} for \texttt{AsciiGraphicsBackend} --- the two renderers' checks
would be close to identical, since both ultimately assert the same
\cnaclass{IGraphicsRenderer}-level contract.
