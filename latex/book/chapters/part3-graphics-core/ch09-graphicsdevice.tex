\chapter{GraphicsDevice and the Rendering Pipeline}
\label{ch:graphicsdevice}

\cnaclass{GraphicsDevice} is the hub every other class in this Part draws through. This
chapter covers its own 887-line header in full: every constructor, every property, every
overload of every method it exposes, the resource base class (\cnaclass{GraphicsResource})
every texture, buffer, and state object inherits, and the disposal ordering discipline that
keeps a multi-backend rendering pipeline from ever calling into an already-destroyed graphics
context. Three worked examples run throughout the chapter --- a minimal clear-and-present loop,
a render-target round trip, and a raw, no-\cnaclass{SpriteBatch} two-triangle scene drawn
directly through \texttt{DrawPrimitives} --- and the last of those was actually built and run
against CNA's \texttt{SOFTWARE} backend for this book, producing the real, unedited screenshot
in Figure~\ref{fig:ch09-drawprimitives}.

\section{Construction: one real constructor, one CNA addition}

\cnaclass{GraphicsDevice} inherits \texttt{System::Object} and \texttt{System::IDisposable},
is non-copyable and non-movable, and offers exactly two constructors:

\begin{description}
\item[\texttt{GraphicsDevice(GraphicsAdapter\& adapter, GraphicsProfile graphicsProfile, const PresentationParameters\& presentationParameters)}]
  the real XNA constructor. \texttt{adapter} names which physical/logical display adapter to
  bind to (Chapter~\ref{ch:graphicsdevice}'s own \S\ref{sec:adapter-displaymode} covers
  \cnaclass{GraphicsAdapter} in full); \texttt{graphicsProfile} is \texttt{Reach} or
  \texttt{HiDef}; \texttt{presentationParameters} carries back-buffer width/height/format,
  depth-stencil format, multisample count, and presentation interval. This is the constructor
  \cnaclass{GraphicsDeviceManager} calls internally when your \cnaclass{Game} subclass first
  creates its device --- ordinary game code essentially never calls it directly.
\item[\texttt{GraphicsDevice()}]
  \texttt{NOXNA} --- a parameterless constructor for headless/no-window contexts (unit tests,
  the golden-image screenshot tooling this chapter itself uses, and any tool that needs a real
  \cnaclass{GraphicsDevice} without a real \cnaclass{Game} driving it).
\end{description}

Six events match FNA's surface exactly: \texttt{Disposing}, \texttt{DeviceLost} (never actually
raised on desktop --- Chapter~\ref{ch:direct3d-backends} explains the one backend,
\texttt{D3D9}, where device loss is even a meaningful concept), \texttt{DeviceReset},
\texttt{DeviceResetting}, \texttt{ResourceCreated}, \texttt{ResourceDestroyed} (both covered in
depth in \S\ref{sec:resource-lifetime} below).

\section{Private implementation: window, backend, and virtual-resolution lifecycle}
\label{sec:private-lifecycle}

The public surface above is a thin shell over eight private methods this chapter's original
scope never traced. They are not callable from game code, but reading them directly (rather
than guessing from their names) explains real, observable behavior the public API alone
doesn't --- most notably how Chapter~\ref{ch:game-loop}'s own \texttt{NOXNA
PresentationMode} enum (\texttt{Letterbox} / \texttt{Overscan} / \texttt{Stretch}/%
\texttt{NativeBackBuffer} / \texttt{FixedHeightDynamicWidth}) actually reaches the graphics
backend.

\begin{description}
\item[\texttt{createOrAttachWindow()}] under the \texttt{HEADLESS} / \texttt{SOFTWARE}
  compile-time backend selection, never creates a real window at all --- \texttt{window\_}
  stays \texttt{nullptr} unconditionally, which is exactly why this chapter's own screenshot
  tooling (\S\ref{sec:worked-drawprimitives}) needs no display server at all. Otherwise, three
  paths are tried in order: a runtime \texttt{PresentationParameters::HeadlessEXT} opt-in
  (honest about its own limits --- only a backend that can genuinely run without a swap chain,
  D3D12 at the time of writing, supports this; a backend that can't, like EasyGL, whose GL
  context is bound to a window, throws from its own constructor instead of silently
  papering over the request); an explicit externally-supplied window handle via
  \texttt{PresentationParameters::DeviceWindowHandle}; or, the common case, a real
  \texttt{SDL\_CreateWindow} call (falling back to $1024\times768$ if the requested back-buffer
  size is unset), whose handle is then published to both \texttt{Input::TextInputEXT} and
  \texttt{Input::Mouse} so text input and mouse capture target the right window.
\item[\texttt{createBackend()}] builds a \texttt{GraphicsBackendCreateArgs} struct from the
  current \cnaclass{PresentationParameters} and wires a \texttt{deviceEventCallback} that
  drives the real \texttt{Lost} / \texttt{Resetting} / \texttt{Reset} events and
  \texttt{deviceStatus\_} transitions named back in \S\ref{sec:property-surface} --- the same
  callback \texttt{D3D9} alone actually invokes.
\item[\texttt{destroyNativeResources()}] tears the backend down first (via
  \texttt{unique\_ptr::reset()}), then destroys the SDL window only if this device created it
  (\texttt{ownsWindow\_}) --- clearing \texttt{TextInputEXT} / \texttt{Mouse}'s own window-handle
  fields first if they still point at the window about to be destroyed, so neither subsystem is
  left holding a dangling handle.
\item[\texttt{UpdateViewportFromWindow()}] resyncs \texttt{Viewport} after a window resize:
  it asks the backend for its own reported viewport size first, falling back to
  \texttt{SDL\_GetWindowSize} only if that yields nothing, and --- a subtlety worth stating
  precisely --- compares the result against \emph{its own last-recorded} width/height, not
  against \texttt{Viewport}'s current dimensions. The distinction matters: a game may have set
  a custom sub-region \texttt{Viewport} (split-screen rendering, for instance) that legitimately
  differs from the full back buffer, and comparing against \texttt{Viewport} directly would
  silently stomp that custom viewport back to full-window size on the very next
  \texttt{Present()} even though no real resize occurred.
\item[\texttt{SetVirtualResolution(width, height)}] is the actual mechanism behind
  Chapter~\ref{ch:game-loop}'s \texttt{PresentationMode} feature: it stores the requested
  logical resolution, writes it into \texttt{PresentationParameters}' own back-buffer
  width/height, forwards it to the backend (which is free to render at a different physical
  resolution and scale/letterbox/crop the result per whichever \texttt{PresentationMode} the
  game selected), and finally calls \texttt{UpdateViewportFromWindow()} to resync.
\item[\texttt{SetPresentationMode(mode)}] simply forwards the mode value to the backend ---
  all the actual scaling-mode logic (letterbox black bars vs.\ overscan cropping vs.\ plain
  stretch vs.\ a fixed native back buffer) lives entirely on the backend side of this call, not
  in \cnaclass{GraphicsDevice} itself.
\item[\texttt{applyPresentationParametersToWindow()}] applies the real SDL-level consequences
  of a presentation-parameter change --- \texttt{SDL\_SetWindowFullscreen} and
  \texttt{SDL\_SetWindowSize} --- and is deliberately non-fatal about the fullscreen call
  specifically: a headless/virtual-display test environment (Xvfb) may not support fullscreen
  switching at all, so a failed \texttt{SDL\_SetWindowFullscreen} just clears the SDL error and
  continues, since the requested state is already stored in \texttt{PresentationParameters}
  regardless of whether the window server could honor it.
\item[\texttt{applySamplerStatesToBackend()}] pushes all sixteen
  (\cnaclass{SamplerStateCollection::MaxSamplers}) sampler slots' filter/address-mode/max
  anisotropy settings to the backend --- called before every draw-call family in this chapter,
  which is why \S\ref{sec:property-surface}'s \texttt{SamplerStates} property never needs an
  explicit ``apply'' call of its own from game code.
\end{description}

\section{The property surface}
\label{sec:property-surface}

Nineteen properties cover the device's full observable state, grouped below by what they
govern rather than listed flat.

\subsection{Identity and lifecycle}

\texttt{IsDisposed} (bool, get-only), \texttt{GraphicsDeviceStatus} (get-only ---
\S\ref{sec:adapter-displaymode} covers the enum), \texttt{Adapter} (get-only reference to the
\cnaclass{GraphicsAdapter} this device was created against), \texttt{GraphicsProfile} (get-only
--- real XNA fixes this at construction; see \texttt{SetGraphicsProfileEXT} in
\S\ref{sec:noxna-helpers} for CNA's one narrow, internal exception to that), and
\texttt{PresentationParameters} (both a mutable and a const-reference overload, so a caller can
either read the current settings or mutate them in place before a \texttt{Reset()}).

\subsection{Display}

\texttt{DisplayMode} (get-only) reports the adapter's current \cnaclass{DisplayMode} ---
\texttt{Width} / \texttt{Height} / \texttt{Format} plus a computed \texttt{AspectRatio}
(\S\ref{sec:adapter-displaymode}).

\subsection{Shader-stage bindings}

Four properties expose the sampler/texture slots a shader reads from:
\texttt{Textures} / \texttt{SamplerStates} for the pixel shader stage,
\texttt{VertexTextures} / \texttt{VertexSamplerStates} for the vertex shader stage. Each is a
mutable-reference-returning getter onto a \cnaclass{TextureCollection} or
\cnaclass{SamplerStateCollection} --- both support integer indexing
(\texttt{device.getTexturesProperty()[0] = \&myTexture;}), and neither has a corresponding
\texttt{set} property, since the collection itself is what's mutated, not replaced wholesale.

\subsection{Pipeline state objects}

\texttt{BlendState}, \texttt{DepthStencilState}, and \texttt{RasterizerState} each follow the
same three-overload shape: a mutable-reference getter, a \texttt{const}-reference getter, and a
\texttt{void set...(const T\&)} setter that copies the given state object into the device's own
live state (Chapter~\ref{ch:state-objects} covers all three types' own field-by-field meaning
in full --- this chapter only covers how \cnaclass{GraphicsDevice} exposes them).
\texttt{ScissorRectangle} (a \cnaclass{Rectangle}) and \texttt{Viewport} (a \cnaclass{Viewport})
follow the simpler get/set-by-value shape. \texttt{BlendFactor} (a \cnaclass{Color}),
\texttt{MultiSampleMask} (an \texttt{int} bitmask), and \texttt{ReferenceStencil} (an
\texttt{int}) round out the fixed-function state XNA exposes directly on the device rather than
through a state object.

\subsection{Index buffer}

\texttt{Indices} (get-only \texttt{const IndexBuffer*}, plus the separate
\texttt{setIndicesProperty(const IndexBuffer*)} setter) is XNA's original property-style
binding for the currently-bound index buffer. \S\ref{sec:vertex-index-binding} below covers why
this property and the newer \texttt{SetIndexBuffer} / \texttt{GetIndexBuffer} / \texttt{Indices()}
method trio (all NOXNA additions) end up meaning the same thing through three different
call spellings.

\begin{sourcenote}
\textbf{A recurring internal detail, worth flagging here because it recurs throughout
Part~IV:} \texttt{deviceStatus\_} (backing \texttt{GraphicsDeviceStatus}) is only ever driven
away from \texttt{Normal} by the \texttt{D3D9} backend's real device-lifecycle callback
(Chapter~\ref{ch:direct3d-backends}) --- every other backend never touches it, so
\texttt{GraphicsDeviceStatus} stays \texttt{Normal} for the whole life of the process on any
other backend.
\end{sourcenote}

\section{Clear, Present, Reset}
\label{sec:clear-present-reset}

\subsection{Clear}

Four overloads, only two of which are real XNA:

\begin{description}
\item[\texttt{Clear(const Color\& color)}] clears the color buffer only, to \texttt{color}.
\item[\texttt{Clear(ClearOptions options, const Color\& color, float depth, int stencil)}]
  the full XNA form --- \texttt{options} is a bitwise-OR of \texttt{ClearOptions::Target}/%
  \texttt{DepthBuffer} / \texttt{Stencil} (\S\ref{sec:clearoptions} below), \texttt{depth} is the
  depth-buffer clear value in \texttt{[0,1]}, \texttt{stencil} is the stencil-buffer clear value.
\item[\texttt{Clear(float r, float g, float b, float a)}] \texttt{NOXNA} (though under-tagged
  in the header itself --- see the audit note below) --- a convenience equivalent to
  \texttt{Clear(Color(r,g,b,a))} without constructing a \cnaclass{Color} at the call site.
\item[\texttt{Clear(const Color\& color, float depth)}] \texttt{NOXNA} --- clears color and
  depth together without needing to spell out \texttt{ClearOptions::Target |
  ClearOptions::DepthBuffer} at every call site. This is the overload the worked example in
  \S\ref{sec:worked-drawprimitives} below actually uses.
\end{description}

FNA's \texttt{Clear(ClearOptions, Vector4, float, int)} overload (color as a \texttt{Vector4}
rather than a \texttt{Color}) is the one XNA overload genuinely missing.

\subsection{Present and Reset}

\texttt{Present()} exists only in its no-argument form --- FNA's 3-argument
\texttt{Present(Rectangle?, Rectangle?, IntPtr)} overload (source/destination rectangles and an
override window handle) is absent. \texttt{Reset()} comes in four overloads:
\texttt{Reset()} (re-applies the current \cnaclass{PresentationParameters} unchanged),
\texttt{Reset(const PresentationParameters\&)}, \texttt{Reset(const PresentationParameters\&,
GraphicsAdapter\&)}, and a fourth \texttt{NOXNA} pointer-adapter overload,
\texttt{Reset(const PresentationParameters\&, GraphicsAdapter*)}, that accepts \texttt{nullptr}
to mean ``keep the current adapter'' without requiring a caller to look one up just to pass it
back unchanged.

\begin{sourcenote}
\textbf{From the FNA-fidelity audit (\texttt{docs/graphicsdevice-fna-audit.md}):} the three
concrete gaps against FNA's public surface are the \texttt{Present} 3-arg overload, the
\texttt{Clear(ClearOptions, Vector4, ...)} overload, and \texttt{GetRenderTargetsNoAllocEXT}.
Several convenience overloads and aliases (the two extra \texttt{Clear} forms above, plus
\texttt{SetIndexBuffer} / \texttt{GetIndexBuffer} / \texttt{GetVertexBuffer} aliases) exist without
their expected \texttt{NOXNA} tag --- a real, specific instance of
Chapter~\ref{ch:design-philosophy}'s \texttt{NOXNA}-discipline being imperfectly applied, worth
knowing about if you are relying on the \texttt{NOXNA} build check to catch every non-XNA
member mechanically.
\end{sourcenote}

\begin{sourcenote}
\textbf{\texttt{PresentationParameters} is requested state, not proof of active presentation
timing.} Both \texttt{Reset(pp)} and the separate presentation-parameter setter store the
caller's interval. Immediate maps to~0, One to~1, and Two to~2. Each path calls the backend's
swap-interval hook, but that virtual is allowed to do nothing. Vulkan inherits the no-op
after construction; four non-presenting or
browser/legacy products also ignore it, while several active GPU backends collapse
\texttt{Two} to ordinary VSync. D3D9 is the only Direct3D exact mapping, but interval~2 is
invalid in windowed D3D9 and CNA does not preflight that restriction. SDL Renderer and
EasyGL submit the numeric~2 without being able to guarantee that the driver accepts it. A
successful property round trip therefore establishes only what CNA retained, not what the
driver or compositor accepted. The complete fourteen-product matrix and actual test boundary
are in \S\ref{sec:backend-swap-interval-matrix}.
\end{sourcenote}

\begin{sourcenote}
\textbf{The same warning applies independently to color format, depth/stencil format, and
fullscreen.} \texttt{Reset(pp)} stores the complete object first. It then attempts the SDL
window's fullscreen and size changes, reapplies virtual resolution/MSAA/present interval, and
calls \texttt{UpdatePresentationFormatEXT()} last. That virtual has an empty default; D3D9 is
its only override. Thus a later read of
\texttt{PresentationParameters.BackBufferFormat} or \texttt{DepthStencilFormat} proves what
the caller requested, not what native attachment exists. \texttt{DepthFormat::None}, for
example, still leaves an always-allocated depth attachment on Software, Vulkan, WebGPU, SDL
GPU (when a combined format is supported), and D3D11/12. Likewise,
\texttt{IsFullScreen == true} survives even when SDL rejected the window transition. See
\S\ref{sec:backend-presentation-format-matrix} before using these properties as capability
queries.
\end{sourcenote}

\section{Render targets}
\label{sec:render-targets}

Four methods manage what the device currently renders into, all absent from the chapter's
original scope and covered here for the first time:

\begin{description}
\item[\texttt{void SetRenderTarget(RenderTarget2D* renderTarget)}] binds a single 2D render
  target, or restores the back buffer when \texttt{renderTarget} is \texttt{nullptr}. Every call
  --- including unbinding --- resets \texttt{Viewport} and \texttt{ScissorRectangle} to the new
  target's (or the back buffer's) full dimensions, matching FNA's own
  \texttt{SetRenderTargets} behavior exactly (a previously-set viewport or scissor rectangle
  never survives a render-target switch; see \texttt{ResetViewportAndScissorForRenderTarget} in
  the private implementation section below).
\item[\texttt{void SetRenderTarget(RenderTargetCube* renderTarget, CubeMapFace cubeMapFace)}]
  binds one face of a cube render target as the active target.
\item[\texttt{void SetRenderTargets(const std::vector<RenderTargetBinding>\& renderTargets)}]
  binds multiple render targets simultaneously (multiple render target / MRT rendering) ---
  each \cnaclass{RenderTargetBinding} pairs a render target with which face to use if it's a
  cube map.
\item[\texttt{std::vector<RenderTargetBinding> GetRenderTargets() const}] returns the currently
  bound bindings; an empty vector means the back buffer is currently the target. This is the
  allocating counterpart to \texttt{GetRenderTargetsNoAllocEXT}, the one confirmed FNA-parity
  gap named in the audit note above --- FNA's own \texttt{GetRenderTargetsNoAllocEXT} writes
  into a caller-supplied array to avoid a per-call heap allocation; CNA's \texttt{GetRenderTargets}
  always allocates a fresh \texttt{std::vector}.
\end{description}

\subsection{Worked example: a render-target round trip, and a real bug it found}
\label{sec:worked-rendertarget}

The program below exercises every method in this section for real on the \texttt{SOFTWARE}
backend: it draws an orange/gold triangle into an offscreen 128$\times$128
\cnaclass{RenderTarget2D}, uses that backend's current-framebuffer interpretation of
\texttt{GetBackBufferData} (\S\ref{sec:backbuffer-readback} below) to confirm the render
target's own pixels \emph{while it is still bound}, restores the back buffer with
\texttt{SetRender\allowbreak Target(nullptr)}, confirms via
\texttt{GetRender\allowbreak Targets()} that the back
buffer really is active again, draws a second, unrelated scene into the back buffer, and
finally tries to draw the offscreen render target's own contents back into the main scene as a
small inset --- the classic render-to-texture pattern behind minimaps, portals, and
post-processing effects alike. The readback line is a backend-specific diagnostic, not a
portable XNA/FNA idiom: six CNA products read the active render target here, five would read
the actual back buffer instead, one synthesizes only its last clear, and two throw. The
complete matrix is in \S\ref{sec:backend-readback-matrix}.

\begin{lstlisting}
RenderTarget2D offscreen(dev, 128, 128);
dev.SetRenderTarget(&offscreen);
dev.Clear(Color(60, 20, 80, 255), 1.0f);
fx.Apply();
DrawTriangle(dev, offscreenTri);   // the orange/gold triangle

// SOFTWARE-specific diagnostic: its readback follows the active framebuffer.
Color centerPixel(0, 0, 0, 0);
dev.GetBackBufferData(&Rectangle(64, 64, 1, 1), &centerPixel, 0, 1);
// centerPixel reads R=255 G=144 B=0 A=255 here -- correct, matches the
// triangle just drawn.

dev.SetRenderTarget(nullptr);                     // restore the back buffer
assert(dev.GetRenderTargets().empty());           // confirmed true

dev.Clear(Color(20, 45, 45, 255), 1.0f);
fx.Apply();
DrawTriangle(dev, mainTri);                       // the teal main scene

SpriteBatch batch(dev);
batch.Begin();
batch.Draw(offscreen, Rectangle(146, 20, 90, 90), Color::White);
batch.End();
\end{lstlisting}

Figure~\ref{fig:ch09-rendertarget-roundtrip} is the real, unedited result --- and it demonstrates
a real, verified gap rather than a clean success. The numeric check above confirms the render
target itself was drawn into correctly (\texttt{R=255 G=144 B=0}, matching the triangle's
interpolated color at that point); \texttt{GetRenderTargets()} confirms the back buffer was
correctly restored; the teal main-scene triangle renders correctly. But the inset --- where
\texttt{offscreen}'s own real, just-verified pixel content should appear --- is blank white
instead.

\begin{sourcenote}
\textbf{A real bug, found live while writing this worked example, not copied from an existing
issue tracker.} \texttt{SoftwareGraphicsBackend.cpp}'s \texttt{SoftwareSpriteBatchBackend::Draw}
(the \texttt{SOFTWARE} backend's implementation of every \cnaclass{SpriteBatch} draw call)
recognizes its texture argument via \texttt{dynamic\_cast<const SoftwareTextureBackend*>(\&texture)}.
A \cnaclass{RenderTarget2D}'s backend object, however, is a \texttt{SoftwareRenderTargetBackend}
--- a sibling class that separately implements \texttt{IRenderTargetBackend} (itself derived
from \texttt{ITextureBackend}), not a subclass of \texttt{SoftwareTextureBackend} itself. The
\texttt{dynamic\_cast} therefore fails silently, \texttt{texture0} ends up null, and the
rasterizer's own texture-sampling code (which re-derives the same \texttt{dynamic\_cast} a
second time, at the point it actually needs pixel data) treats a null texture as ``draw
untextured'' --- exactly the blank white quad in the figure. Tellingly, the raw
\texttt{DrawPrimitivesEx} / \texttt{DrawIndexedPrimitivesEx} paths (\S\ref{sec:draw-calls}) that
\cnaclass{GraphicsDevice}'s own \texttt{DrawUserPrimitives} family ultimately calls into
\emph{do} guard against exactly this case --- they throw a \texttt{std::runtime\_error} when
\texttt{TextureEnabled} is set but \texttt{texture0} is null --- so this is a real, specific
inconsistency between two code paths that should both refuse silently-wrong output the same
way, not a documented, intentional limitation. It affects only the \texttt{SOFTWARE} backend
specifically (the one this book's own screenshot tooling uses); this book takes no position on
whether the same gap exists on any of the twelve backends Part~IV covers, since verifying that
would require testing each one directly, which is outside this chapter's scope.
\end{sourcenote}

\subsection{Multiple render targets: where MRT is (and is not) real}
\label{sec:worked-mrt}

\texttt{SetRenderTargets} accepts a \texttt{std::vector<RenderTargetBinding>} specifically to
support multiple-render-target (MRT) rendering --- a single draw call writing to several
render targets at once (a deferred-rendering G-buffer, writing albedo/normal/depth in one
pass, is the classic use case):

\begin{lstlisting}
RenderTarget2D albedoTarget(dev, 512, 512);
RenderTarget2D normalTarget(dev, 512, 512);

const std::vector<RenderTargetBinding> gbuffer = {
    RenderTargetBinding(&albedoTarget),
    RenderTargetBinding(&normalTarget),
};
dev.SetRenderTargets(gbuffer);
// ... a shader writing to SV_Target0 and SV_Target1 draws into both at once ...
dev.SetRenderTarget(nullptr);
\end{lstlisting}

Whether this code actually writes to \emph{both} targets in one draw call, however, depends
entirely on which backend compiled it --- and this is worth stating precisely rather than
assuming uniform behavior, per \S\ref{sec:worked-rendertarget}'s own reminder that this
chapter's screenshot tooling exposed a real backend-specific gap once already this chapter.
\cnaclass{IGraphicsBackend}'s own base implementation of \texttt{SetRenderTargets} is
documented directly in its header comment: ``Default: binds the first target via
\texttt{SetRenderTarget2D}; backends with MRT support should override'' --- in other words,
a backend that never overrides it silently binds only \texttt{rts[0]} and drops every
additional target with no error or warning at all. Reading each backend's own
\texttt{.cpp} directly rather than assuming: \textbf{EasyGL} genuinely overrides it, with a
real multi-attachment framebuffer path handling \texttt{count > 1} distinctly from the
single-target case (Chapter~\ref{ch:easygl-backend} covers this backend's own feature depth
further); the \textbf{SOFTWARE} backend this chapter's own screenshots use does
\emph{not} override it at all, and therefore silently falls back to the single-target default
--- a real, verified, currently-uncorrected limitation of this one backend, not a general CNA
constraint. This is precisely why the MRT code sample above is left unscreenshotted in this
chapter: running it against \texttt{SOFTWARE} would render only into \texttt{albedoTarget} and
silently produce nothing in \texttt{normalTarget}, which would misleadingly look like a
successful MRT demonstration to a reader who couldn't see the backend-specific caveat --- the
source-level finding here is the honest way to convey this, not a screenshot that would need a
paragraph of caption disclaiming what it doesn't actually show.

\section{Vertex and index buffer binding}
\label{sec:vertex-index-binding}

\begin{description}
\item[\texttt{void SetVertexBuffer(const VertexBuffer* vertexBuffer)}] binds a vertex buffer
  into the singular slot used by every draw, or unbinds it with \texttt{nullptr}.
\item[\texttt{void SetVertexBuffer(const VertexBuffer* vertexBuffer, int vertexOffset)}] binds
  the same singular slot. The public signature promises an explicit starting offset, but the
  current implementation leaves that parameter unnamed and discards it.
\item[\texttt{void SetVertexBuffers(const std::vector<VertexBufferBinding>\& vertexBuffers)}]
  stores as many as sixteen multi-stream descriptions and also selects the first description's
  buffer as the singular draw slot.
\item[\texttt{std::vector<VertexBufferBinding> GetVertexBuffers() const}] returns the currently
  stored multi-stream descriptions by value. The warning below explains why this is not always
  the same thing as the singular slot actually used for geometry.
\item[\texttt{void SetIndexBuffer(const IndexBuffer* indexBuffer)}] binds an index buffer, or
  unbinds with \texttt{nullptr}. This is a plain method alongside the older
  \texttt{Indices} / \texttt{setIndicesProperty} property pair from
  \S\ref{sec:property-surface} --- both ultimately write the same
  \texttt{currentIndexBuffer\_} field, so which spelling to use is purely a matter of whichever
  reads more naturally at a given call site.
\item[\texttt{const VertexBuffer* GetVertexBuffer() const}] returns the vertex buffer bound in
  slot~0 (the first slot \texttt{SetVertexBuffer} / \texttt{SetVertexBuffers} populates).
\item[\texttt{const IndexBuffer* GetIndexBuffer() const}] returns the currently bound index
  buffer --- functionally identical to reading the \texttt{Indices} property.
\item[\texttt{const IndexBuffer* Indices() const} / \texttt{void Indices(const IndexBuffer*)}]
  a third, method-call spelling of the exact same binding, present alongside the property and
  the \texttt{SetIndexBuffer} / \texttt{GetIndexBuffer} pair --- three ways to say the same thing,
  a real (if harmless) redundancy in the header rather than a documentation simplification.
\end{description}

\begin{sourcenote}
\textbf{The two binding surfaces are not synchronized.} The singular setter changes only
\texttt{currentVertexBuffer\_}; it neither replaces nor clears
\texttt{currentVertexBuffers\_}. Conversely, \texttt{SetVertexBuffers(\{\})} stores an empty
vector but does not clear the old singular pointer, because that assignment happens only when
the incoming vector is non-empty. Thus \texttt{GetVertexBuffers()} can report an old list after
\texttt{SetVertexBuffer(\&newMesh)}, or an empty list while \texttt{GetVertexBuffer()} and an
ordinary draw still use the old mesh. An instanced draw after the first sequence can combine
the new singular mesh with an old per-instance buffer from the stale list.

FNA keeps one binding array and makes both setter families update it; its offset-taking setter
also retains the supplied offset. CNA's
\path{VertexBufferBindingTests.cpp} does not catch the split: despite its
``GetVertexBuffers contract'' heading, it constructs and copies a standalone
\texttt{std::vector<VertexBufferBinding>} without constructing a
\cnaclass{GraphicsDevice} or calling either setter.
\end{sourcenote}

\section{Draw calls: concrete overloads where FNA has generics}
\label{sec:draw-calls}

\subsection{Buffer-backed draws}

Three methods share this shape, all present with FNA-matching signatures and all drawing from
whatever vertex/index buffers are currently bound per \S\ref{sec:vertex-index-binding}.

\texttt{DrawPrimitives} takes \texttt{primitiveType}, \texttt{vertexStart}, and
\texttt{primitiveCount}.

\texttt{DrawIndexedPrimitives} adds \texttt{baseVertex}, \texttt{minVertexIndex}, and
\texttt{numVertices} ahead of its own \texttt{startIndex}/\texttt{primitiveCount} pair.

\texttt{Draw\allowbreak{}Instanced\allowbreak{}Primitives} takes the identical parameter list
as the indexed method, with a trailing \texttt{instanceCount} added.

\subsection{What DrawInstancedPrimitives actually forwards}
\label{sec:graphicsdevice-instancing}

The minimal current call shape, used by the public EasyGL and Vulkan regressions, is:

\begin{lstlisting}
device.SetVertexBuffers({
    VertexBufferBinding(&meshVertices, 0, 0),
    VertexBufferBinding(&instanceWorlds, 0, 1),
});
device.SetIndexBuffer(&meshIndices);
effect.Apply();
device.DrawInstancedPrimitives(
    PrimitiveType::TriangleList,
    /*baseVertex=*/0, /*minVertexIndex=*/0, /*numVertices=*/4,
    /*startIndex=*/0, /*primitiveCount=*/2, /*instanceCount=*/3);
\end{lstlisting}

This compiles like XNA's multi-stream idiom, but CNA forwards a narrower contract.
CNA scans the stored binding vector and passes the backend only the \emph{first} non-null
buffer whose instance frequency is greater than zero. \path{GpuDrawParams} contains that one
backend pointer; it has no field for the actual frequency, either binding's offset, or any
additional stream. Frequencies 1,
2, and 100 are consequently indistinguishable, every consumed stream starts at offset zero,
and a third stream is never visible to the draw backend. FNA instead passes its complete
native binding array, including every offset and frequency, before issuing the instanced draw.

The effect contract is narrower too. EasyGL can bind both caller declarations to a custom
\cnaclass{ShaderEffect}, advancing the instance attributes with divisor one. Vulkan, BGFX,
WebGPU, and D3D9/11/12 use CNA-owned instancing shaders, generally interpreting the instance
record as one 64-byte world matrix rather than letting the applied effect define arbitrary
streams. EasyGL's stock-effect branch issues an instanced GPU call but binds no instance
attributes, so the same geometry is overdrawn; its public two-instance pixel proof
deliberately uses a custom effect.

There is no \cnaclass{GraphicsCapability} value for hardware instancing. FNA asks its native
driver and throws \texttt{NoSuitableGraphicsDeviceException} when support is absent; CNA
cannot be queried equivalently. Seven GPU backends implement a real instanced callback,
SDL GPU and Software inherit the shared \texttt{std::runtime\_error} default, and a missing
positive-frequency binding produces different results even among the seven implementations
(one ordinary draw, repeated identical geometry, or no draw). The complete outcome and
test-evidence matrix is in Chapter~\ref{ch:backend-architecture},
\S\ref{sec:drawex-instancing-matrix}.

\subsection{User-primitive draws: the generics-to-overloads translation}

FNA's \texttt{DrawUserPrimitives<T>} / \texttt{DrawUserIndexedPrimitives<T>} generic methods ---
which in C\# work against any \texttt{struct} implementing \texttt{IVertexType} --- become, in
CNA, a fixed set of concretely-typed overloads. This is a direct consequence of C\texttt{++}
template instantiation requiring concrete call sites rather than C\#'s runtime generic
dispatch, and it is the same underlying constraint behind \texttt{GetBackBufferData}'s
narrowing to \texttt{Color} only (\S\ref{sec:backbuffer-readback} below has no generic
pixel-format element type either).

\texttt{DrawUserPrimitives} comes in six overloads: a raw \texttt{const void* vertexData}
form (assumed \cnaclass{VertexPositionColor} packed layout, stride 16 bytes); a second raw form
taking an explicit \texttt{const VertexDeclaration\&} for any other layout; and four
concretely-typed forms, one per real XNA vertex struct this chapter's own worked example uses
--- \cnaclass{VertexPositionColor}, \cnaclass{VertexPositionColorTexture},
\cnaclass{VertexPositionTexture}, and \cnaclass{VertexPositionNormalTexture}. Every overload
shares the same trailing parameters --- \texttt{vertexOffset} (starting vertex within the
supplied array) and \texttt{primitiveCount}.

\texttt{DrawUserIndexedPrimitives} is the same idea with an index array added, and existing in
more overloads as a result: a raw \texttt{void*} / \texttt{void*} form; four typed forms
(the same four vertex types above) each with 16-bit (\texttt{std::uint16\_t}) indices; the same
four typed forms again with 32-bit (\texttt{std::uint32\_t}) indices; and two more raw forms
taking an explicit \texttt{VertexDeclaration} with 16-bit and 32-bit indices respectively ---
eleven overloads in total, matching FNA's own generic method's two index-width instantiations
times its \texttt{IVertexType}/explicit-\texttt{VertexDeclaration} split.

\begin{sourcenote}
Reusable byte scratch buffers (\texttt{userVertexScratch\_} / \texttt{userIndexScratch\_}, in the
private section below) back every \texttt{DrawUserPrimitives} / \texttt{DrawUserIndexedPrimitives}
call --- the raw bytes are staged into a transient vertex/index buffer sized from the scratch
buffer's already-grown capacity, avoiding a fresh heap allocation on every draw call once that
capacity has stabilized. This is purely an implementation detail (nothing about it is
observable from calling code), but it explains why the very first \texttt{DrawUserPrimitives}
call in a game's lifetime is measurably slower than every subsequent one at the same or smaller
size --- a real, if minor, warm-up cost worth knowing about before mistaking it for a
per-frame regression.
\end{sourcenote}

\subsection{How World/View/Projection actually reach the draw call}
\label{sec:extract-matrices}

\texttt{SetCurrentEffect} above covers half of the real per-draw pipeline --- how
\texttt{FillGpuDrawParams()} reaches the active effect's lights, fog, and material colors ---
but there is a second, separate half specifically for the three matrices every effect
implementing \cnaclass{IEffectMatrices} carries, worth naming because it is not exposed as a
public method at all: a small anonymous-namespace free function in \texttt{GraphicsDevice.cpp}
itself, \texttt{ExtractMatrices(const Effect*, Matrix\&, Matrix\&, Matrix\&)}, called at the top
of every one of \texttt{DrawPrimitives} / \texttt{DrawIndexedPrimitives} /
\texttt{DrawUserPrimitives} / \texttt{DrawUserIndexedPrimitives}'s real implementations (seven
call sites in total). Its own logic is short enough to state exactly: default all three
matrices to identity, then \texttt{dynamic\_cast<const IEffectMatrices*>(effect)} --- if that
succeeds, overwrite the three defaults with the effect's own \texttt{World} / \texttt{View}/%
\texttt{Projection} properties; if it fails, the identity defaults simply stand.

Every effect \cnaclass{GraphicsDevice} can actually have bound as \texttt{currentEffect\_} in
practice --- all five stock effects (Chapter~\ref{ch:stock-effects}), \cnaclass{ShaderEffect}
(Chapter~\ref{ch:shader-fx-gap}), and \texttt{PbrEffect} (Chapter~\ref{ch:webgpu-backend}) ---
implements \cnaclass{IEffectMatrices}, so the identity-matrix fallback branch is not something
any of CNA's own built-in effects ever actually triggers; it exists purely as the same defensive
default-rather-than-crash pattern Chapter~\ref{ch:backend-architecture} already named as a
project-wide design choice, applied here to a \texttt{dynamic\_cast} rather than a virtual
method's own default body. The one real, checkable consequence worth knowing: a fully custom
\cnaclass{Effect} subclass a game writes itself, if it deliberately does \emph{not} implement
\cnaclass{IEffectMatrices} (perhaps a screen-space post-process effect with no meaningful
World/View/Projection concept at all), draws with a silent identity transform on all three ---
not an error, and not a crash, simply geometry rendered exactly as authored in clip space with
no further transformation applied.

\subsection{NOXNA draw-adjacent helper}

\texttt{NOXNA static int PrimitiveVerts(PrimitiveType primitiveType, int primitiveCount)}
mirrors FNA's internal (never publicly exposed) \texttt{PrimitiveVerts()} helper, converting a
primitive count to the vertex count it requires (three per triangle for
\texttt{TriangleList}, two more per additional triangle for \texttt{TriangleStrip}, and so on).
Exposed publicly here so calling code and tests can validate a vertex array's size before
issuing a draw call, rather than only discovering a too-small array via a backend-level
out-of-bounds read. Throws \texttt{System::InvalidOperationException} if \texttt{primitiveType}
is unrecognized.

\section{Back-buffer readback}
\label{sec:backbuffer-readback}

Three overloads of \texttt{GetBackBufferData} advertise copying pixels out of the back buffer
into caller-supplied \cnaclass{Color} storage: the plain form
(\texttt{Color* data, int elementCount}); a start-index form
(\texttt{Color* data, int startIndex, int elementCount}) for writing into the middle of a
larger caller-owned array; and a rectangle-scoped form
(\texttt{const Rectangle* rect, Color* data, int startIndex, int elementCount}) that reads only
a sub-region of the back buffer when \texttt{rect} is non-null, or the entire back buffer when
it's \texttt{nullptr}. All three are the same narrowing-to-\texttt{Color} pattern
\S\ref{sec:draw-calls} already named for \texttt{DrawUserPrimitives} --- FNA's own generic
\texttt{GetBackBufferData<T>} has no CNA equivalent for any element type other than
\cnaclass{Color}.

\textbf{The method name is not a uniform CNA contract.} The shared wrapper forwards the
rectangle directly to \texttt{IGraphicsBackend::ReadBackbuffer}; the backend decides which
image those coordinates address. Six products read the \emph{currently bound render target}
when one exists, five always read the real window backbuffer/swapchain, \texttt{HEADLESS}
synthesizes the last global clear color, and \texttt{SDL\_GPU}/\texttt{D3D12} inherit the
interface's throwing default. FNA, by contrast, always calls its actual
\texttt{FNA3D\_ReadBackbuffer} path regardless of the current render-target binding. Therefore
the earlier worked example's bound-target probe is useful on \texttt{SOFTWARE}, but it is not
portable evidence that a generic CNA render target was rendered correctly. There is no single
universal pixel-verification route across all fourteen products: use a backend's real
\cnaclass{RenderTarget2D::GetData} support where documented, or first draw the target back to
the window and probe the actual backbuffer on a product that supports it. The full target,
coordinate-space, and evidence matrix is in
Chapter~\ref{ch:backend-architecture}, \S\ref{sec:backend-readback-matrix}.

The C\texttt{++} pointer surface also makes the caller responsible for more bounds safety than
the signatures suggest. The implementation rejects null \texttt{data}, a stored
backbuffer format incompatible with four-byte \cnaclass{Color}, and an
\texttt{elementCount} smaller than \(w\times h\). It does \emph{not} reject a negative
\texttt{startIndex}, check that the allocation contains
\(\texttt{startIndex}+w\times h\) elements, validate the rectangle against the image being
read, or protect the signed \(w\times h\) multiplication from overflow. In particular,
\texttt{elementCount} is not the number of pixels the method elects to copy: every call
writes exactly \(w\times h\) colors starting at \texttt{startIndex}. A safe caller validates
non-negative coordinates/dimensions and offset, checked multiplication/addition, target
bounds, and the complete allocation capacity before entering this API.

Every real, unedited screenshot this chapter embeds is produced on its named, tested backend
through a \texttt{NOXNA} helper used by the book's own tooling:
\texttt{Save\allowbreak{}Back\allowbreak{}Buffer\allowbreak{}Screenshot\allowbreak{}EXT()}
(\texttt{tools/cna-screenshot-infra/} here, not part of CNA) reads the whole image through
\texttt{GetBackBufferData(Color*, int)} and encodes the returned colors as PNG. That known
configuration is materially narrower than assuming the pattern works everywhere. A one-pixel
debug probe has the same preconditions:

\begin{lstlisting}
// Only after checking this backend reads the intended image and that
// (x,y) lies in the coordinate space reported for that image:
Color pixel(0, 0, 0, 0);
const Rectangle probeRegion(x, y, 1, 1);
dev.GetBackBufferData(&probeRegion, &pixel, 0, 1);
// pixel now holds that backend's observable image at (x, y).
\end{lstlisting}

\section{NOXNA helper and diagnostic methods}
\label{sec:noxna-helpers}

A cluster of methods exist purely to support tooling, testing, and backend-internal plumbing
--- none are part of real XNA, and every one is tagged \texttt{NOXNA} in the header:

\begin{description}
\item[\texttt{void OnResourceCreated(System::Object* resource)}] fires the
  \texttt{ResourceCreated} event; called by \cnaclass{GraphicsResource}'s own constructor
  (\S\ref{sec:resource-lifetime}).
\item[\texttt{void OnResourceDestroyed(const std::string\&, System::Object*)}] fires
  the \texttt{ResourceDestroyed} event; called by \cnaclass{GraphicsResource}'s own
  \texttt{Dispose} (\S\ref{sec:resource-lifetime}).
\item[\texttt{void AddResourceReference(GraphicsResource*)}] registers a resource for the
  device's own disposal-ordering guarantee (\S\ref{sec:resource-lifetime}).
\item[\texttt{void RemoveResourceReference(GraphicsResource*)}] unregisters it
  (\S\ref{sec:resource-lifetime}).
\item[\texttt{std::size\_t GetTrackedResourceCount() const}] returns how many resources are
  currently tracked and not yet disposed --- debug/test use only.
\item[\texttt{void SetDepthTestEnabled(bool)} / \texttt{SetBlendEnabled(bool)} /
  \texttt{SetDepthWriteEnabled(bool)}] narrow, direct toggles for three specific pieces of fixed-
  function state, layered on top of (not a replacement for) the full \cnaclass{DepthStencilState}/
  \cnaclass{BlendState} objects Chapter~\ref{ch:state-objects} covers.
\item[\texttt{void SetGraphicsProfileEXT(GraphicsProfile profile)}] a narrow, internal-only
  profile switch documented in the header itself as a fix for a specific ordering problem:
  \cnaclass{Game}'s own \texttt{GraphicsDevice\_} member is eagerly default-constructed
  (hardcoded to \texttt{Reach}) before \cnaclass{GraphicsDeviceManager} exists to honor a game's
  \texttt{GraphicsProfile = GraphicsProfile.HiDef} request --- called once, internally, from
  \cnaclass{GraphicsDeviceManager}'s own apply path, never as a general public runtime
  profile-switch (real XNA has none either).
\item[\texttt{void SetContextRecoveryEnabled(bool enabled)}] changes a policy for subsequent
  resource creation and uploads. Call it immediately after device construction but before
  loading content --- the device and backend necessarily already exist. On every product,
  disabling it lets a completed \cnaclass{Texture2D} upload discard its CPU pixel shadow;
  EasyGL additionally stops registering later GL resources for recreation. This saves memory
  but makes ordinary \texttt{GetData()} and partial level-0 updates fail after that shadow is
  freed. Re-enabling does not rebuild discarded shadows or retroactively register resources.
\item[Debug marker] \texttt{SetStringMarkerEXT()} requests a named GPU marker. On Vulkan with
  the debug-utils extension available, this becomes a real native debug-label command visible
  in RenderDoc/NVIDIA Nsight. D3D9 throws an explicit not-implemented error; the other twelve
  products inherit the empty hook.
\item[\texttt{IGraphicsBackend\& GetBackend() const}] returns a reference to the active backend
  interface --- the seam Part~IV's whole backend-by-backend treatment sits behind.
\item[\texttt{constexpr CNA::GraphicsBackendType GetGraphicsBackendType() const}] reports which
  backend was compiled into this build, as an enum value matching the
  \texttt{CNA\_GRAPHICS\_BACKEND} CMake option (e.g. \texttt{EASYGL}, \texttt{D3D9},
  \texttt{SOFTWARE}). Genuinely \texttt{constexpr} --- it reads a compile-time constant, not
  \texttt{this}, so it can be evaluated without a live device at all.
\item[\texttt{constexpr std::string\_view GetGraphicsBackendName() const}] the same information
  as a human-readable string (e.g. \texttt{"EASYGL"}) rather than an enum value; equally
  \texttt{constexpr} for the identical reason.
\item[\texttt{bool SupportsCapability(CNA::GraphicsCapability capability) const}] the
  recommended way to check whether the active backend (and, for device-dependent entries, the
  current runtime driver) supports a given capability --- e.g. 3D rendering on the 2D-only
  \texttt{SDL\_RENDERER} / \texttt{DX3} / \texttt{CANVAS} backends --- \emph{before} relying on it,
  rather than calling the feature and handling whatever exception results. The worked example
  below shows the current \texttt{ASCII} exception to that intended contract.
\item[\texttt{void SetCurrentEffect(Effect* effect)}] called automatically by
  \texttt{Effect::Apply()}; not meant to be called directly by ordinary game code, but included
  here because it's the exact mechanism Chapter~\ref{ch:stock-effects}'s stock-effect chapter
  and \S\ref{sec:worked-drawprimitives}'s own worked example both depend on --- the backend
  reaches the active effect's shader parameters via virtual dispatch through
  \texttt{FillGpuDrawParams()}, not through a hardcoded effect type check.
\item[\texttt{void SetPresentationParameters(const PresentationParameters\& pp)}] stores new
  presentation parameters \emph{without} triggering a full device reset --- used by
  \cnaclass{GraphicsDeviceManager} so a caller can read settings back via the
  \texttt{PresentationParameters} property after applying preferred settings, ahead of whatever
  later call actually resets the device.
\item[Legacy multisample rebuild] \leavevmode\par
  The test-only \texttt{RecreateBackendForMultiSampleCount(int)} hook tears down and rebuilds
  the active backend (same window) with a new requested multisample count.
  Its header still describes a missing manager/reset path, but that rationale is stale:
  ordinary \texttt{ApplyChanges()} now reaches the normal reset and multisample-application
  path. This older escape hatch remains in several focused tests; it is still safe only before
  GPU resources exist, because it destroys and replaces the complete backend rather than
  performing the normal resource-preserving reconfiguration.
\end{description}

\begin{sourcenote}
\textbf{Recovery is not one backend Boolean.} The framework flag changes
\cnaclass{Texture2D}'s CPU-shadow lifetime on every product even when the backend virtual is
empty. EasyGL is the sole backend that also changes a real recovery registry. D3D9 is the
awkward third case: the framework flag changes first, then its override throws
\texttt{runtime\_error}, leaving the shared texture policy changed despite the failed call.
The F9/F10 loss channel and marker behavior are separately classified in
\S\ref{sec:backend-recovery-debug-matrix}.
\end{sourcenote}

\begin{lstlisting}
// Worked example: defensively check a capability before relying on it,
// rather than calling it and handling whatever exception results --
// exactly the pattern SupportsCapability's own doc comment recommends.
// SDL_Renderer, DX3, and Canvas genuinely return false here. ASCII is also
// 2D-only, but currently inherits the base class's default-true answer.
const bool reports3D =
    dev.SupportsCapability(CNA::GraphicsCapability::ThreeD);
const bool knownAsciiFalsePositive =
    dev.GetGraphicsBackendType() == CNA::GraphicsBackendType::Ascii;

if (reports3D && !knownAsciiFalsePositive)
{
    // Safe for every currently shipped backend after the known exception above.
}
else
{
    std::printf("3D unsupported on backend: %.*s\n",
                static_cast<int>(dev.GetGraphicsBackendName().size()),
                dev.GetGraphicsBackendName().data());
    // fall back to a 2D-only rendering path instead
}
\end{lstlisting}

\begin{sourcenote}
\textbf{A second, closely related finding, discovered by directly reading every backend's own
\texttt{SupportsCapability} override rather than assuming the capability system is uniformly
reliable.} \texttt{IGraphicsBackend::SupportsCapability}'s own default implementation --- used
by any backend that doesn't override a specific capability --- returns \texttt{true}
unconditionally. That default creates more than one confirmed false positive.
\texttt{CNA::GraphicsCapability::MultipleRenderTargets} exists in the enum
specifically to let a caller check MRT support ahead of time, exactly as
\S\ref{sec:worked-mrt} above recommends, but it is never actually referenced by any backend's
\texttt{SupportsCapability} override anywhere in the codebase --- meaning
\texttt{SupportsCapability(MultipleRenderTargets)} currently returns \texttt{true}
\emph{universally}, including on the \texttt{SOFTWARE} backend, where
\S\ref{sec:worked-mrt} already demonstrated \texttt{SetRenderTargets} silently drops every
target past the first. The capability query that exists specifically to protect a caller from
this exact gap does not currently protect against it --- a real, precise, second-order finding
about the capability system's own incompleteness, not a criticism of the MRT gap itself (which
the header's own doc comment already names honestly as backend-dependent).

The same direct audit finds two further shapes. \texttt{ASCII} is 2D-only and its reachable 3D
operations forward to SDL renderer's throwing implementation, yet it has no capability
override and therefore reports \texttt{ThreeD=true}; that is why the worked example above
checks the backend type as well. \texttt{CustomEffects} likewise reports \texttt{true} on
\texttt{BGFX}, \texttt{WEBGPU}, \texttt{ASCII}, and \texttt{SOFTWARE}, despite respectively
producing an always-invalid compiled object, returning a null factory whose
\cnaclass{SpriteBatch} path rejects the effect, exposing the same null/throw combination
through the ASCII decorator, and accepting source without ever executing it. See
Chapter~\ref{ch:shader-fx-gap} for that full backend matrix. \texttt{OcclusionQuery} adds a
parallel confirmed set: WebGPU, SDL GPU, and Software inherit a null
\texttt{CreateOcclusionQuery()} factory, while ASCII forwards to SDL renderer's throwing one,
yet all four inherit the same \texttt{true} capability answer.
\end{sourcenote}

\section{Resource tracking and disposal ordering}
\label{sec:resource-lifetime}

\cnaclass{GraphicsDevice} maintains a private, non-owning
\texttt{std::vector<GraphicsResource*> resources\_}, mutated only through
\texttt{AddResourceReference} / \texttt{RemoveResourceReference} (\S\ref{sec:noxna-helpers} above)
--- both existing purely so the device can guarantee a specific disposal order.
\texttt{ResourceCreated} fires immediately after registration; \texttt{ResourceDestroyed} fires
\emph{before} de-registration, carrying a \texttt{Name} / \texttt{Tag} snapshot captured while the
resource is still valid. Removal is swap-and-pop (O(1), order not preserved) --- deliberate,
since nothing about resource tracking depends on iteration order.

The disposal sequence this buys is the single most important invariant in this chapter: calling
\texttt{GraphicsDevice::Dispose()} copies and clears \texttt{resources\_}, disposes every
tracked resource \emph{first}, and only then tears down the native backend context
(SDL/Vulkan/GL). No graphics-API call can ever be issued against an already-destroyed context,
because every resource that might issue one is disposed strictly before the context that would
receive it.

\begin{sourcenote}
\textbf{A documentation trap worth naming explicitly.} \texttt{docs/graphicsresource-fna-audit.md}
states, as an open gap, that ``device resource tracking: not implemented'' and that a
\texttt{GraphicsDeviceResetting()} callback is missing. Both claims are stale --- the resource
tracking mechanism described in this section, and the \texttt{DeviceResetting} event on
\cnaclass{GraphicsDevice} itself, both demonstrably exist in the current header. This looks
like exactly the kind of documentation drift Chapter~\ref{ch:what-is-cna} warned about: treat a
specific, checkable claim in \texttt{docs/} with the same ``verify against current source, not
memory'' discipline the project asks of itself, even when the claim comes from the project's
own documentation.
\end{sourcenote}

\subsection{Per-backend disposal caveats}

The ordering guarantee above is a CNA-wide invariant, but what actually happens to a native GPU
handle on disposal is backend-specific, and \texttt{docs/graphics-resource-lifetime.md} is
candid about the sharp edges: on \textbf{EasyGL}, disposing a bound \cnaclass{RenderTarget2D}
without first unbinding it can leave a dangling framebuffer attachment, and there is currently
no GL context-loss recovery; on \textbf{Vulkan}, destroying a render target still referenced by
an in-flight frame is undefined behavior --- there is no \texttt{vkDeviceWaitIdle} guard at
that call site; on \textbf{Bgfx}, \texttt{bgfx::destroy()} only \emph{queues} destruction for
the next \texttt{bgfx::frame()}, so \texttt{bgfx::shutdown()} must never run before every
resource backend has actually been destroyed. None of these are exercised by ordinary game code
following the \texttt{Begin} / \texttt{Draw} / \texttt{End} pattern from earlier chapters, but they
matter if your own code manages render-target lifetime manually across frame boundaries.

\section{GraphicsResource: the shared base}

Every texture, buffer, and state object in this Part inherits \cnaclass{GraphicsResource},
which itself inherits \texttt{System::Object} / \texttt{System::IDisposable} and provides
\texttt{Disposing}, a get-only \texttt{GraphicsDevice}, \texttt{IsDisposed}, a virtual
\texttt{Name}, and a raw, caller-owned \texttt{Tag} (\texttt{System::Object*}).
\texttt{ToString()} returns \texttt{Name} if set, otherwise the type name. Its protected
constructor, \texttt{GraphicsResource(GraphicsDevice* device = nullptr)}, accepts a null device
deliberately --- the four state-object classes in Chapter~\ref{ch:state-objects} each ship
static preset instances (\cnaclass{BlendState::Opaque}, \cnaclass{RasterizerState::CullNone},
and so on) that exist before any real device does, and those presets simply skip
tracking/registration/events entirely.

A subtlety worth internalizing: GPU handles are freed on \texttt{Dispose()}, not on the
C\texttt{++} destructor. The destructor does call \texttt{Dispose(false)} as a safety net, but
that path deliberately skips the \texttt{Disposing} / \texttt{ResourceDestroyed} events ---
matching the standard C\# \texttt{IDisposable} finalizer-vs-explicit-dispose distinction, now
expressed in C\texttt{++} terms. Move semantics transfer \texttt{unique\_ptr}-owned GPU state
correctly but do \emph{not} update the device's tracking-list pointer entry, which means moving
a resource that is currently tracked by a live \cnaclass{GraphicsDevice} to a new memory
address is unsafe and unsupported --- construct in place, or move before the resource is ever
registered.

\section{GraphicsAdapter, DisplayMode, and the exception types}
\label{sec:adapter-displaymode}

\cnaclass{GraphicsAdapter} exposes \texttt{CurrentDisplayMode}, \texttt{SupportedDisplayModes},
\texttt{Description}, and a static, re-evaluated-every-call \texttt{DefaultAdapter} --- do not
cache it across a call to the static \texttt{AdaptersChanged()}. Two properties are honestly
limited on this platform: \texttt{DeviceId} / \texttt{VendorId} are queried through Linux
\texttt{sysfs} where available and return \texttt{0} otherwise, while
\texttt{Revision} / \texttt{SubSystemId} are always \texttt{0} --- SDL3 has no query surface for
either. \cnaclass{DisplayMode} pairs \texttt{Width} / \texttt{Height} / \texttt{Format} with a
computed \texttt{AspectRatio}; \cnaclass{DisplayModeCollection} supports both integer indexing
and a \cnaclass{SurfaceFormat}-filtered \texttt{operator[]}. \cnaclass{GraphicsDeviceStatus} is
the three-value enum (\texttt{Normal}, \texttt{Lost}, \texttt{NotReset}) already introduced
above; \cnaclass{GraphicsProfile} is the familiar XNA \texttt{Reach} / \texttt{HiDef} pair, whose
\emph{only} backend that actually consults a real device capability structure for it is
\texttt{D3D9} (Chapter~\ref{ch:direct3d-backends}) --- everywhere else the profile is present in
the API but decorative. \cnaclass{DeviceLostException}, \cnaclass{DeviceNotResetException}, and
\cnaclass{NoSuitableGraphicsDeviceException} are all thin \texttt{std::runtime\_error}
subclasses with default and custom-message constructors.

\subsection{Multi-monitor enumeration: the Adapters list}
\label{sec:adapters-list}

\texttt{DefaultAdapter} is not the only \cnaclass{GraphicsAdapter} a game can reach: the static
\texttt{Adapters} property (\texttt{getAdaptersProperty()}) returns
\texttt{const std::vector<std::unique\_ptr<GraphicsAdapter>>\&} --- one entry per physical
display SDL3 reports via \texttt{SDL\_GetDisplays}, not merely per GPU. Reading
\texttt{GraphicsAdapter.cpp} directly confirms the lazy-population contract implied by the
class's own comment above: \texttt{getAdaptersProperty()} only calls the private
\texttt{AdaptersChanged()} builder if the internal list is still empty, so the first call in a
process populates it and every later call (barring an explicit \texttt{AdaptersChanged()}
invocation after a monitor is connected or removed) returns the same cached vector. This is
why \texttt{DefaultAdapter} itself is documented as ``re-evaluated on every call'' rather than
cached by the caller: it simply returns \texttt{*getAdaptersProperty()[0]}, so the caller-side
staleness risk is really about the vector's \emph{contents}, not about calling
\texttt{DefaultAdapter} itself too rarely.

\begin{lstlisting}
// Worked example: let the player choose which physical monitor a
// fullscreen game window opens on, rather than assuming DefaultAdapter
// (display index 0) is always the right choice.
const auto& adapters = GraphicsAdapter::getAdaptersProperty();
for (std::size_t i = 0; i < adapters.size(); ++i)
{
    const GraphicsAdapter& adapter = *adapters[i];
    const DisplayMode mode = adapter.getCurrentDisplayModeProperty();
    std::printf("Adapter %zu: %s (%dx%d)\n", i,
        adapter.getDescriptionProperty().c_str(),
        mode.getWidthProperty(), mode.getHeightProperty());
}

// Later, construct (or Reset) the device against the adapter the player
// selected rather than hardcoding GraphicsAdapter::getDefaultAdapterProperty():
// GraphicsDevice itself takes the adapter directly, both at construction
// and via Reset(presentationParameters, adapter) -- there is no separate
// GraphicsDeviceManager-level adapter selector to go through instead.
GraphicsDevice dev(*adapters[chosenIndex], GraphicsProfile::HiDef, presentationParameters);
\end{lstlisting}

\subsection{IsProfileSupported and the format-query methods: honest about what is actually checked}
\label{sec:adapter-format-queries}

\texttt{IsProfileSupported(GraphicsProfile)}, \texttt{QueryRenderTargetFormat(\ldots)}, and
\texttt{QueryBackBufferFormat(\ldots)} all exist to answer, in principle, ``will the real
hardware behind this adapter actually accept what I'm about to request, or will it need to
substitute something else?'' --- but reading their bodies directly (rather than trusting the
method names) shows this question is only genuinely answered on one backend. Each method's
source is split by an \texttt{\#ifdef CNA\_BACKEND\_D3D9}, and the source comments on the
non-D3D9 side name the reason explicitly rather than leaving it to guesswork:

\begin{description}
\item[\texttt{IsProfileSupported}] on D3D9, \texttt{GraphicsProfile::Reach} short-circuits to
  \texttt{true} unconditionally (every real D3D9 HAL device already exceeds Reach's
  \texttt{vs\_2\_0} / \texttt{ps\_2\_0} floor, so there is nothing worth querying), and
  \texttt{HiDef} is checked against a real queried \texttt{D3DCAPS9} structure. On every other
  backend, the method's own source comment (labelled \texttt{D9-101} in the codebase's internal
  task numbering) states plainly that ``an implementation here would be a hardcoded table
  pretending to be a capability query'' --- and that the project's own \texttt{plan\_dx9.md}
  explicitly refuses to do that --- so it simply returns \texttt{true} for every profile,
  unconditionally, on the other nine backends.
\item[\texttt{QueryRenderTargetFormat} / \texttt{QueryBackBufferFormat}] on D3D9, both check a
  requested \cnaclass{SurfaceFormat} against a real profile whitelist \emph{and} a real
  \texttt{IDirect3D9::CheckDeviceFormat} / \texttt{CheckDeviceType} hardware query, falling back
  to \texttt{SurfaceFormat::Color} if either check fails --- and separately clamp the requested
  multisample count to what the selected format actually supports. On every other backend,
  \texttt{QueryRenderTargetFormat} falls back to a much simpler
  \texttt{isSupportedRenderTargetFormat(format)} check with the multisample count always
  reported as \texttt{0}, while \texttt{QueryBackBufferFormat} does not even attempt that much:
  it unconditionally reports \texttt{SurfaceFormat::Color} as the selected format, regardless
  of what was actually requested.
\end{description}

The practical consequence: code that calls these methods to decide whether a fallback path is
needed will get a genuinely hardware-informed answer only when built against the D3D9 backend
(Chapter~\ref{ch:direct3d-backends}); on every other backend the answer is either a hardcoded
\texttt{true} or a simplified format check, both honestly documented as such in the source
rather than silently passed off as a real capability query. This is the same category of
finding as \S\ref{sec:worked-mrt}'s own \texttt{MultipleRenderTargets} capability gap above ---
an API surface that reads as a genuine hardware query but is only actually backed by one out of
twelve backends --- worth knowing before writing portable code that branches on either method's
return value.

\section{ClearOptions: one closed gap, one still genuinely open}
\label{sec:clearoptions}

\cnaclass{ClearOptions} is a three-value flags enum (\texttt{Target=1}, \texttt{DepthBuffer=2},
\texttt{Stencil=4}) with the full bitwise operator set hand-implemented, the same pattern seen
on \cnaclass{DisplayOrientation} in Chapter~\ref{ch:game-loop}. \texttt{ClearOptions::Stencil}
was, for a real stretch of this project's history, a confirmed no-op on EasyGL and Vulkan (Task~%
871) --- \texttt{GraphicsDevice::Clear()} never even checked the flag, and neither backend's own
stencil-clear path was reachable through the public API at all. It is fixed now, on every
backend that has a real stencil buffer to clear: \texttt{Clear()} was extended with four new
per-backend dispatch methods (\texttt{ClearStencil}, \texttt{ClearDepthAndStencil},
\texttt{ClearColorAndStencil}, \texttt{ClearColorDepthAndStencil}), and the fix surfaced a real,
independent bug on Vulkan specifically while closing it --- every one of this backend's
render-pass-creation sites had \texttt{stencilLoadOp} hardcoded to
\texttt{VK\_ATTACHMENT\_LOAD\_OP\_DONT\_CARE}, discarding whatever stencil clear value a caller
requested regardless of what \texttt{Clear()} itself now correctly dispatched. A real
methodology finding came out of testing this fix, worth knowing on its own: an initial
same-frame test (stamp a stencil value, clear it, compare, all within one \texttt{Draw()} call)
failed on Vulkan and BGFX even with the fix correctly applied, because both backends defer an
entire frame's draws into one command buffer/view whose own clear always applies once, before
that frame's draws, regardless of the order \texttt{Clear()} / \texttt{DrawXxx()} were actually
called in game code --- an artifact of this project's per-frame-batched rendering architecture,
not a discriminating test. Splitting the stamp and the clear-plus-compare across two separate
real frames fixed the test on all three hardware backends. This is a small, concrete example of
the kind of specific, checkable claim Chapter~\ref{ch:what-is-cna} promised this book would
preserve rather than round off to ``clearing works.''

\subsection{A silent no-op, not a thrown exception, for an impossible depth/stencil clear}

\texttt{Clear()}'s own real implementation carries a second, distinct wrinkle worth reading
directly from \texttt{GraphicsDevice.cpp} rather than assuming from the header alone. Before
issuing any backend call, it checks whether the currently active render target genuinely has a
real depth/stencil buffer --- via the currently bound \cnaclass{RenderTarget2D}'s own backend
when one is set, or \texttt{IGraphicsBackend::SupportsDepthStencil()} for the back buffer
otherwise --- and, if not, masks \texttt{options} down to \texttt{ClearOptions::Target} alone
before doing anything else. This is a deliberate, documented design choice with a clear
motivation: without it, plain \texttt{Clear(const Color\&)} --- which always requests
\texttt{Target\ \textbar\ DepthBuffer\ \textbar\ Stencil}, matching FNA's own single-argument
overload exactly --- would crash outright on a 2D-only backend with no depth buffer at all,
rather than degrading gracefully to the color-only clear such a backend can actually perform.

The still-open question this masking leaves behind is what happens to a caller who asks for
something narrower and more deliberate: \texttt{Clear(ClearOptions::DepthBuffer, color, 1.0f,
0)} on a backend with no real depth buffer masks down to an \emph{empty} options value, and the
call returns having cleared nothing at all, silently, with no exception and no way for the
caller to tell the difference between ``the depth buffer was cleared'' and ``there was no depth
buffer to clear, so nothing happened.'' Found running this project's own \texttt{SDL\_Renderer}
regression suite --- a dedicated audit test expects exactly this call to throw, matching the
``ask, don't catch'' philosophy \texttt{SupportsCapability} above is built around, and it
currently does not, confirmed as a genuine, pre-existing behavior rather than a regression by
reproducing it identically against an unmodified checkout. The project's own tracking leaves
the resolution deliberately open rather than picking one side unilaterally: either the test's
own expectation is the one that is wrong (a graceful, silent no-op may simply be the intended,
documented contract, mirroring how \texttt{DX3}'s own equivalent test was written from the
start to expect exactly this and check the honest internal method directly instead), or
\texttt{Clear()}'s masking itself should learn to distinguish ``nothing was requested that this
backend can't do'' from ``the caller explicitly asked for something impossible and deserves to
be told'' --- a real API-design question, not a bug with one obvious fix, left to be settled
against real XNA/FNA's own documented behavior for this exact case.

This same finding connects directly to the \texttt{SupportsCapability} discussion above, and
sharpens it: \texttt{CNA::GraphicsCapability::DepthStencilBuffer} exists in the enum, its own doc
comment describing exactly ``a real depth/stencil buffer on the currently active render
target'' --- precisely the fact \texttt{Clear()}'s own internal masking check above already
computes for itself, through a completely separate mechanism
(\texttt{IGraphicsBackend::SupportsDepthStencil()} / \cnaclass{RenderTarget2D}'s own backend,
neither of which the public \texttt{GraphicsCapability} enum value ever consults). Reading every
3D-capable backend's own \texttt{SupportsCapability} override directly confirms none of EasyGL,
Vulkan, or Bgfx has a \texttt{case} for \texttt{DepthStencilBuffer} at all --- every one falls
through to the shared default, which returns \texttt{true} unconditionally, regardless of
whether the currently active target actually has a real depth/stencil buffer or not. This is the
same exact shape as \texttt{MultipleRenderTargets}' own gap above --- another capability, in the
same eight-entry enum, declared for a caller to check ahead of time and never actually wired on
any backend that would need to answer anything other than an unconditional \texttt{true} ---
making \texttt{MultipleRenderTargets} and \texttt{DepthStencilBuffer} two confirmed-unreliable
entries so far. \texttt{ThreeD} has real false-return overrides on SDL renderer, DX3, and
Canvas, but the ASCII false positive above means it is not universally reliable either.
\texttt{CustomEffects} is now independently confirmed unreliable for the four backend-specific
shapes above, and \texttt{OcclusionQuery} has the four null/throw false positives just
identified. \texttt{WireFrame}, by contrast, has a real, dedicated \texttt{case} on both
EasyGL and Vulkan --- a hardcoded \texttt{false} on EasyGL, since GLES3 has no wireframe fill
mode at all, and a genuine runtime driver-feature check on Vulkan. The remaining entries
complete the same pattern rather than escaping it.

\texttt{MultiSampleAntiAliasing} is definitely false-positive on ASCII and Software. ASCII
forwards the request to SDL renderer, whose explicit implementation always returns zero;
Software allocates one ordinary CPU framebuffer and merely stores/reports a render target's
requested count. Vulkan, WebGPU, SDL GPU, and D3D9 all perform real device/format support
queries when a count is applied or a render target is created, and each can clamp the result
back to one sample (reported as zero), but none consults that result from
\texttt{SupportsCapability}: all four inherit unconditional \texttt{true}. BGFX is likewise
unconditional, and its default legacy-OpenGL renderer has a separately pixel-proven MSAA
resolve failure even when BGFX's format capability bit claims support. EasyGL is the one
device-dependent implementation whose capability answer performs the same live
\texttt{GL\_MAX\_SAMPLES} check as its application path. D3D11 and D3D12 can safely return
true because both reject devices below feature level~11.0, whose required RGBA8 format support
includes multisample rendering.

\texttt{Anisotropic}\allowbreak\texttt{Filtering} has three definite false positives. ASCII
never forwards \texttt{ApplySampler}\allowbreak\texttt{State} to its inner renderer; SDL GPU stores
\texttt{maxAnisotropy} but omits it from every queued command and sampler-cache key, and
Software discards every sampler parameter after validating the slot. D3D9 does issue real
anisotropic sampler states, but its capability answer never checks
\texttt{D3DCAPS9::MaxAnisotropy} (nor clamps a requested value to that cap), so its inherited
\texttt{true} is not a current-device result. EasyGL and Vulkan query their live extension or
device-feature bit; WebGPU creates a real anisotropic sampler; BGFX provides a real on/off flag
but still ignores the requested maximum; D3D11 and D3D12's accepted feature-level floor
guarantees the mapped anisotropic filter. The internal Headless backend inherits true for both
entries too, but only records the calls: it is a logic-test contract, never evidence that a
pixel-rendering implementation supports either feature. Chapter~\ref{ch:backend-architecture}
tabulates these results and the caller-side implication.

\section{Worked example: a raw two-triangle scene, no SpriteBatch}
\label{sec:worked-drawprimitives}

Every draw call in the rest of this Part goes through \cnaclass{SpriteBatch}
(Chapter~\ref{ch:spritebatch}) or \cnaclass{Model} (Chapter~\ref{ch:models-meshes}), both of
which ultimately bottom out in the same \texttt{GraphicsDevice} calls this chapter covers ---
\texttt{SetVertexBuffer}, \texttt{DrawPrimitives}, \texttt{Clear}. The program below skips both
higher-level classes entirely and calls \cnaclass{GraphicsDevice} directly, to show exactly what
they're built on. It draws two triangles --- a large, cool-toned background triangle and a
smaller, warm-toned foreground triangle with per-vertex color interpolation --- through
\cnaclass{BasicEffect} with \texttt{VertexColorEnabled} set, so no texture is involved at all.

\begin{lstlisting}
class ScreenshotDemo : public Game
{
    std::unique_ptr<GraphicsDeviceManager> gdm_;

protected:
    void Draw(const GameTime&) override
    {
        auto& dev = getGraphicsDeviceProperty();
        dev.setRasterizerStateProperty(RasterizerState::CullNone);
        dev.Clear(Color(30, 30, 60, 255), 1.0f);

        BasicEffect fx(dev);
        fx.VertexColorEnabled = true;
        fx.Apply();

        // Triangle 1: far, big, blue-ish -- background mountain shape.
        const VertexPositionColor bg[3] = {
            { Vector3(-1.0f, -0.2f, 0.8f), Color(40, 60, 160, 255) },
            { Vector3( 0.0f,  0.9f, 0.8f), Color(90, 120, 220, 255) },
            { Vector3( 1.0f, -0.2f, 0.8f), Color(40, 60, 160, 255) },
        };
        VertexBuffer vb1(dev, 3);
        vb1.SetData(bg, 3);
        dev.SetVertexBuffer(&vb1);
        dev.DrawPrimitives(PrimitiveType::TriangleList, 0, 1);

        // Triangle 2: near, tri-color -- proves interpolation + depth test
        // (nearer than triangle 1, and it partially overlaps it).
        const VertexPositionColor fg[3] = {
            { Vector3( 0.0f,  0.6f, 0.3f), Color::Red },
            { Vector3(-0.7f, -0.6f, 0.3f), Color(0, 220, 90, 255) },
            { Vector3( 0.7f, -0.6f, 0.3f), Color(240, 200, 40, 255) },
        };
        VertexBuffer vb2(dev, 3);
        vb2.SetData(fg, 3);
        dev.SetVertexBuffer(&vb2);
        dev.DrawPrimitives(PrimitiveType::TriangleList, 0, 1);

        dev.SetVertexBuffer(nullptr);
    }

public:
    ScreenshotDemo()
    {
        gdm_ = std::make_unique<GraphicsDeviceManager>(this);
        gdm_->setPreferredBackBufferWidthProperty(256);
        gdm_->setPreferredBackBufferHeightProperty(256);
    }
};
\end{lstlisting}

Figure~\ref{fig:ch09-drawprimitives} is the actual, unedited output of this program, built and
run against CNA's \texttt{SOFTWARE} backend (a CPU triangle rasterizer with real
perspective-correct interpolation and per-pixel depth testing --- this book's own coverage of
CNA's backend catalog does not yet name it, since it is used here purely as a headless
verification tool, not as one of the twelve backends Part~IV profiles). Running headlessly, with
no display and no GPU at all, it wrote a real 256$\times$256 PNG directly from the back buffer.
Two things are worth checking in the image against the code above: the background triangle is
correctly occluded exactly where the foreground triangle overlaps it (the depth test is real,
not a painter's-algorithm draw-order accident --- both triangles are submitted in the same
draw-order they'd need for a \emph{wrong}, non-depth-tested result to look identical), and the
foreground triangle's red/green/gold corners blend smoothly across its interior (real
barycentric color interpolation, not three flat-shaded sub-triangles).
